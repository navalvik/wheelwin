# R17.9T.6-D1 Player Attach API Correction

Date: 2026-08-22

Task: Correct the R17.9T.6-D1 `PlayerManager.attachPlayer` API shape without expanding recovery architecture scope.

## 1. Scope

The original D1 implementation accepted `attachPlayer(identity, runtime)`. The required API is `attachPlayer(player)`, accepting one already-constructed Player aggregate.

This correction was limited to:

- changing the PlayerManager attach API to one supplied Player object;
- preserving the supplied `player.playerId` and `player.playerIndex`;
- registering the supplied Player's identity/runtime parts in PlayerManager's existing Maps;
- updating focused tests for the corrected API contract.

## 3. Architecture Findings

PlayerManager's established storage remains two Maps:

- `_identities`: `playerId` to `PlayerIdentity`;
- `_runtimes`: `playerId` to `PlayerRuntime`.

The supplied recovery Player aggregate carries direct `playerId` and `playerIndex` fields plus its existing `identity` and `runtime`. The manager registers those existing identity/runtime objects under `player.playerId` and returns the same supplied Player object. No parallel registry was introduced.

## 4. Lifecycle Flow

Corrected attach flow:

```text
attachPlayer(player)
  -> require player
  -> require player.playerId
  -> require player.identity.playerId === player.playerId
  -> require player.runtime
  -> reject duplicate player.playerId
  -> _identities.set(player.playerId, player.identity)
  -> _runtimes.set(player.playerId, player.runtime)
  -> return the exact supplied player object
```

Normal `createPlayer()` flow was not modified.

## 5. Ownership Boundaries

- Player identity/runtime ownership remains in `PlayerManager`.
- The supplied Player object's `playerIndex` is preserved and is not generated, reassigned, or modified.
- No recovery orchestration, engine restoration, financial, persistence, reconnect, socket, session, or client ownership changed.

## 6. Risks

### Medium

The aggregate's direct `playerId` and `identity.playerId` must agree. The corrected method fails closed on mismatch rather than registering inconsistent identity data.

### Low

## 7. Recommendations

- Keep later reconstruction orchestration responsible for constructing a complete Player aggregate before calling `attachPlayer(player)`.
- Do not expand D1 with engine, persistence, financial, or reconnect logic.
