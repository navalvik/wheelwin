## 3. Architecture Findings

- The validator is a pure module owning signature + freshness validation; it was NOT modified.
- SocketGateway owns the Socket.IO server lifecycle (`initialize()` creates the `Server`, then registers the CONNECTION handler). The middleware is registered between `new Server()` and `io.on(CONNECTION)`, so it runs before any gameplay/lobby handler.
- Configuration flows through env → app.js (dotenv already loaded) → SocketGateway constructor option `telegramAuth: { botToken, maxAgeSeconds }`. No parallel configuration system was created; RuntimeConfiguration was not extended because the task scope restricts file changes to app.js wiring.

## 4. Lifecycle Flow

1. Client connects with optional `auth.telegramInitData`.
2. Middleware:
   - missing/empty initData → accept as Web guest, `socket.data.telegramUserId = null`;
   - initData present → `validateTelegramInitData({ initData, botToken, maxAgeSeconds })`;
   - valid → `socket.data.telegramUserId = result.telegramUserId`;
   - invalid → log non-sensitive reason category only, reject with `next(new Error("TELEGRAM_AUTH_FAILED"))`. No downgrade to guest.
3. CONNECTION handler proceeds unchanged for accepted sockets.

## 5. Ownership Boundaries

- Validator: unchanged owner of initData validation.
- SocketGateway: owns connection-level auth decision and `socket.data.telegramUserId` attachment.
- app.js: owns environment secret resolution (never logs/sends bot token).
- No changes to RoomLobbyBridge, lobbyProtocol, PlayerManager, RoomManager, SetupSessionLifecycle, recovery, reconnect, gameplay, financial code, or client code.

## 6. Risks

- Critical: none identified.
- High: none. Invalid Telegram credentials are fail-closed (rejected), never downgraded.
- Medium: if `TELEGRAM_BOT_TOKEN` is unset but a client sends initData, validation fails with `INVALID_BOT_TOKEN` and the connection is rejected — intentional fail-closed behavior.
- Low: rejection logging emits only the validator's reason category (e.g. SIGNATURE_MISMATCH); raw initData is never logged.

## 7. Recommendations

- Future stage: use `socket.data.telegramUserId` for CREATE_ROOM authorization and per-user room quotas (explicitly out of scope here).
- Consider promoting telegramAuth into RuntimeConfiguration if more Telegram config accumulates.
