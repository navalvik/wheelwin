## 2. `failSession()` call graph (complete)

`PaymentSessionManager.failSession(roomId, reason)` is the **only** function that sets session status via `markFailed()` / `markTimedOut()` and emits `PAYMENT_SESSION_FAILED` with a full session snapshot.

### Direct callers (code)

| Caller | File | Function | Trigger | Reason passed |
|--------|------|----------|---------|---------------|
| Deploy subscriber | `PaymentSessionManager.js` | `initialize` → handler on `GAME_CONTRACT_DEPLOY_FAILED` | Contract deploy / init / openPayments failure | `payload.reason ?? "deploy_failed"` |
| Expiry timer | `PaymentSessionManager.js` | `_onExpiry` | `paymentDeadline` elapsed while session in progress | `"payment_timeout"` |

**There are no other `failSession(` call sites in the server tree.**

### Related terminal path (does **not** call `failSession`)

| Caller | File | Trigger | Reason passed | Session marked failed? |
|--------|------|---------|---------------|------------------------|
| Create catch | `PaymentSessionManager.js` | `createAndRequest` throws | `error.message ?? "payment_session_create_failed"` | **No** — emits `PAYMENT_SESSION_FAILED` only; no `markFailed()` |

### Downstream (after `PAYMENT_SESSION_FAILED`)

| Step | File | Function |
|------|------|----------|
| Archive hint | `SessionHistoryArchiveManager.js` | `_setTerminalHint(roomId, reason)` + timeline |
| Room broadcast | `RoomLobbyBridge.js` | `_handlePaymentSessionFailed` |
| Room destroy | `RoomLobbyBridge.js` | `_closeRoom(payload.reason ?? "payment_failed")` |
| Event | EventBus | `ROOM_DESTROYED` |

## 3. Code constraint: what `payment.status: PAYMENT_FAILED` implies

From `PaymentSession.markFailed()` / `markTimedOut()`:

| `failSession` reason | Session `payment.status` | Participant unpaid seats |
|----------------------|--------------------------|---------------------------|
| `"payment_timeout"` | **`PAYMENT_TIMEOUT`** | `PAYMENT_FAILED` |
| Any other reason | **`PAYMENT_FAILED`** | `PAYMENT_FAILED` |

**Observed `payment.status: PAYMENT_FAILED` (session level) rules out `payment_timeout` as the failSession reason.**

Therefore, for both real sessions, **`failSession` was invoked with a non-`payment_timeout` reason**, and the **only coded path** for that is:

```text
GAME_CONTRACT_DEPLOY_FAILED
  → PaymentSessionManager.failSession(roomId, reason)
  → markFailed()
  → PAYMENT_SESSION_FAILED
  → ROOM_DESTROYED
```

**Exact reason string** = whatever `GameContractManager` put in `GAME_CONTRACT_DEPLOY_FAILED.payload.reason` / `deployError` (must come from archive `reason` field — not inferred here).

### Known deploy failure reason strings (from code)

| Reason (examples) | Origin |
|-------------------|--------|
| `deploy_failed` | Default adapter failure |
| `Deploy exceeded {N}ms` | Deploy wall-clock timeout |
| `deploy_exception` | Uncaught deploy error |
| `oracle_address_missing` | GameEscrow init |
| `init_game_failed` | `initGame` adapter failure |
| `open_payments_failed` | `openPayments` adapter failure |
| `game_escrow_payments_open_failed` | Catch wrapper |

## 4. Payment state transition (expected vs failed)

### Happy path

```text

  ↓
PaymentSession CREATED → WAITING_FOR_PAYMENTS
  ↓
GameContract deploy → DEPLOYED → AWAITING_PLAYER_PAYMENTS
  ↓
PAYMENT_REQUEST → seats AWAITING_PLAYER_CONFIRMATION
  ↓

  ↓
BLOCKCHAIN_PENDING → chain confirm
  ↓
PAYMENT_SESSION_COMPLETED (FULLY_PAID) → ENTRY_PAYMENT_COMPLETED
```

```text
PAYMENT_CONNECTION_READY          ✓ (reported: wallet connected / PAYMENT_READY)

  ✗ PAYMENT_CONFIRM_INTENT
  ✗ PAYMENT_TRANSACTION_CONFIRMED
  ✗ PAYMENT_SESSION_COMPLETED
  ↓
PAYMENT_SESSION_FAILED → ROOM_DESTROYED
```

## 7. Telegram WebApp vs Opera / Mi Browser

| Factor | Telegram WebApp | Opera / Mi Browser |
|--------|-----------------|---------------------|
| Wallet connect (`WALLET_CONNECT_REPORT`) | Same server path | Same server path |
| `PAYMENT_CONNECTION_READY` | Same | Same — **both can reach this** |
| Deploy failure | Client-agnostic | Client-agnostic — **not browser-specific** |
| `sendTransaction` return | In-app bridge | External app — **only matters after deploy + PAYMENT_REQUEST** |

**Conclusion:** Browser type correlates with **which devices were on mobile browser**, but the **coded terminal path for `payment.status: PAYMENT_FAILED` is server-side deploy failure**, not a Telegram-vs-browser TonConnect callback split — unless archives show deploy SUCCESS (which would contradict session status classification).

## 8. Timeout logic

| Timer | Duration (default) | Start | Expiration / fail | Session status on fail |
|-------|-------------------|-------|-------------------|------------------------|
| Wallet barrier | 5 min | Wallet session create | `wallet_connection_timeout` | Room close **without** PaymentSession failSession — **ruled out** (PAYMENT_READY observed) |
| Payment session | 5 min | `createPaymentSession` | `failSession("payment_timeout")` | **`PAYMENT_TIMEOUT`** — **ruled out** for reported session status |
| Setup Timer | 5 min from setup start | Setup start | `setup_expired` | Lifecycle **`SETUP_EXPIRED`**, not `PAYMENT_FAILED` |
| Contract deploy | 2 min | Deploy begin | `GAME_CONTRACT_DEPLOY_FAILED` | **`PAYMENT_FAILED`** via failSession |

**Could payment fail while confirmation pending?** Yes in general (`payment_timeout`). **Not consistent** with reported **`payment.status: PAYMENT_FAILED`** at session level — that points to **deploy (or other non-timeout) failSession**, not pending confirmation timeout.

## 11. Root cause classification

| Category | ROOM_bXwC | ROOM_HxV5 | Evidence |
|----------|-----------|-----------|----------|
| `payment_timeout` | **Excluded** | **Excluded** | Session status `PAYMENT_FAILED` ≠ `PAYMENT_TIMEOUT` |
| `deploy_failed` | **Primary** | **Primary** | Only non-timeout `failSession` caller |
| `transaction_failed` | Excluded | Excluded | No deploy success → no STAKE pipeline |
| `missing_confirmation` | Excluded | Excluded | Would imply timeout or partial pay; session status wrong |
| `invalid_transaction` | Excluded | Excluded | No confirm path reached |
| `missing_stake` | Excluded | Excluded | Deploy failure precedes STAKE |
| `missing_confirmation` (mobile callback) | Excluded for **these** sessions | Excluded | R17.8H mobile callback issue applies **after** PAYMENT_REQUEST |
| `other` (`payment_session_create_failed`) | Unlikely | Unlikely | Would not set session `markFailed` snapshot consistently |

### Root cause conclusion

**Both sessions failed because `PaymentSessionManager.failSession()` ran after `GAME_CONTRACT_DEPLOY_FAILED`, not because of payment confirmation timeout or missing TonConnect STAKE callback.**

Wallet connection succeeded; **contract deploy / GameEscrow activation failed** immediately afterward.

**Exact deploy error strings** for each room must be read from archive field **`reason`** (and `blockchainLifecycle.deploy.error`, `tonDeployDebug`) — **not guessed in this audit** because archive files were unavailable locally.
