## 3. Architecture Findings

### Existing Manager Conventions

All three managers follow consistent conventions:

- Plain ES classes with constructor accepting `{ logger, eventBus, ... }`.
- Runtime state stored exclusively in in-memory `Map` / `Set` fields.
- Error handling: `this._logger.error(...)` + return `null` (or `false`). No exceptions thrown.
- All three already had `hasRoom()` / `hasGame()` / `hasPlayer()` methods.
- `createRoom()`, `createGame()`, `createPlayer()` always generate new IDs.

### playerIndex Analysis

`playerIndex` is NOT stored in `PlayerIdentity` or `PlayerRuntime`. It is owned by:
- The payment domain (`PaymentSession.participant.playerIndex`)
- `room.players` array ordering (index in the array)

`PlayerManager` does not manage `playerIndex`. The `attachPlayer` API preserves `playerIndex` by not generating a replacement `playerId` and not calling `createPlayer()`.

## 6. APIs Added

### RoomManager.attachRoom(room)

- Registers a pre-constructed `Room` with an existing `roomId`.
- Does NOT generate a new `roomId`.
- Does NOT call `createRoom()`.
- Does NOT trigger Setup Session creation or `ROOM_CREATED` events.
- Validates: `room` is required, `room.roomId` is required.
- Duplicate detection: rejects if `roomId` already exists in `_rooms`.
- Also populates `_playerRoomIndex` for any players already in `room.players`.
- Returns the attached `Room` on success, `null` on failure.

### GameManager.attachGame(game)

- Registers a pre-constructed `Game` with an existing `gameId`.
- Does NOT generate a new `gameId`.
- Does NOT call `createGame()`.
- Does NOT trigger `GAME_CREATED` events.
- Validates: `game` is required, `game.gameId` is required.
- Duplicate detection: rejects if `gameId` already exists in `_games`.
- Returns the attached `Game` on success, `null` on failure.

### PlayerManager.attachPlayer(identity, runtime)

- Registers a pre-constructed `PlayerIdentity` and `PlayerRuntime` pair with an existing `playerId`.
- Does NOT generate a new `playerId`.
- Does NOT call `createPlayer()`.
- Does NOT trigger `PLAYER_CREATED` events.
- Does NOT alter `playerIndex` (not stored in PlayerManager).
- Validates: `identity` is required, `runtime` is required, `identity.playerId` is required.
- Duplicate detection: rejects if `playerId` already exists in `_identities`.
- Returns `Player.fromParts(identity, runtime)` on success, `null` on failure.

### Duplicate-Detection Helpers (pre-existing, no changes)

- `RoomManager.hasRoom(roomId)` — already existed.
- `GameManager.hasGame(gameId)` — already existed.
- `PlayerManager.hasPlayer(playerId)` — already existed.

## 7. Identity Preservation Behavior

| Identity | Preserved by | Not generated |
|---|---|---|
| `roomId` | `attachRoom` uses `room.roomId` as-is | No `_generateRoomId()` call |
| `gameId` | `attachGame` uses `game.gameId` as-is | No `_generateGameId()` call |
| `playerId` | `attachPlayer` uses `identity.playerId` as-is | No `_generatePlayerId()` call |
| `playerIndex` | Not stored in PlayerManager; preserved by not replacing `playerId` | N/A |

## 8. Duplicate Protection

All three attach APIs follow the same pattern:

1. Validate the object and its identity field are present.
2. Check `this._rooms.has(roomId)` / `this._games.has(gameId)` / `this._identities.has(playerId)`.
3. If duplicate exists: log error, return `null`, do NOT overwrite.
4. If no duplicate: register in the existing in-memory Map, return the object.

This matches the existing error-handling conventions (`createRoom` returns `null` on failure, `createGame` returns `null`, `createPlayer` returns `null`).

## 9. Risks

### Low

- **`_playerRoomIndex` population in `attachRoom`**: The `attachRoom` method populates `_playerRoomIndex` for players already in `room.players`. This is necessary for consistency (prevents a recovered room's players from being added to another room). If a player is already in `_playerRoomIndex` from another attached room, the new room's attach will silently overwrite the index entry. This is acceptable for recovery because the recovery orchestrator (future stage) will attach rooms in dependency order and validate consistency.

### Non-blocking

- **No `isRecovered` flag**: This stage does not add a recovery flag to Game/Room/Player objects. This is deferred to a later sub-stage per the task constraints.
- **No engine restore**: Engine state (GameStateEngine, PhysicsEngine, etc.) is not restored. This is deferred to later sub-stages.
