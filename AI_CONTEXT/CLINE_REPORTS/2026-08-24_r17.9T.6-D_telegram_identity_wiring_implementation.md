## 3. Architecture Findings

The R17.9T.6-C bridge already implements fail-closed CREATE_ROOM authorization via `_resolveSocketTelegramUserId(socketId)`, which calls the configured resolver and guards against throws / non-scalar values. The only missing piece was production wiring: no resolver was configured in `app.js`, so every CREATE_ROOM would fail closed even for authenticated Telegram sockets.

## 4. Lifecycle Flow

After this change:

1. Telegram Mini App → validated initData → SocketGateway stamps `socket.data.telegramUserId`.
2. Client emits CREATE_ROOM → SocketGateway emits `LOBBY_CREATE_ROOM_REQUEST { socketId }`.
3. RoomLobbyBridge resolves identity via the wired resolver:
   `SocketGateway.getIO()?.sockets?.sockets?.get(socketId)?.data?.telegramUserId ?? null`
4. Non-null → creation proceeds (one-user quota applies). Null → `ROOM_CREATION_REQUIRES_TELEGRAM`.

## 5. Ownership Boundaries

- Resolver reads ONLY authenticated socket state (`socket.data.telegramUserId`).
- No client payload, `initDataUnsafe`, query parameter, or profile data is consulted.
- No second socket registry or identity map introduced; the resolver walks the live Socket.IO registry owned by SocketGateway.
- Raw initData is never stored anywhere by this wiring.

## 6. Risks

- Critical: none.
- High: none.
- Medium: none.
- Low:
  - If a future refactor moves RoomLobbyBridge construction before SocketGateway initialization, the closure would still be safe (lazy evaluation at call time), but startup-order comments should be preserved.
  - The resolver returns whatever scalar sits in `socket.data.telegramUserId`; type guarding remains in the bridge (unchanged).

## 7. Recommendations

- None required. Optional future hardening: assert at startup (dev-only) that the resolver is configured after bridge initialization.

## 8. Changes Made

### Exact wiring point

`server/app.js`, immediately after `this._roomLobbyBridge.initialize();`:

```js
this._roomLobbyBridge.configureTelegramIdentityResolver(
    (socketId) =>
        this._socketGateway.getIO()
            ?.sockets?.sockets
            ?.get(socketId)
            ?.data?.telegramUserId ?? null
);
```

### Startup ordering (verified)

1. `this._socketGateway = new SocketGateway({...})` → `initialize(this._httpServer)` → `connectEventBus(...)` (getIO() available).
2. `this._roomLobbyBridge = new RoomLobbyBridge({...})` → `initialize()`.
3. Resolver configured (both objects exist; getIO() live).

No startup/recovery order, `server.listen()`, or SocketGateway placement changed.

### Fail-closed behavior

- Missing socket / missing `socket.data` / missing `telegramUserId` → optional chaining yields `undefined` → `?? null`.
- Resolver throw → caught by `RoomLobbyBridge._resolveSocketTelegramUserId` → null (pre-existing guard, unchanged).
- Null identity → existing rejection path `ROOM_CREATION_REQUIRES_TELEGRAM`.
