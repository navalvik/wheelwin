**Mode:** Audit only (no code changes)

**Failed sessions:** `ROOM_HxV5`, `ROOM_bXwC`

**Verdict:** Deployer wallet seqno did not advance because **deploy transactions were accepted for broadcast but failed on-chain** — public testnet evidence shows **failed 0.05 TON outbound transfers** at both failure windows while wallet balance (**~0.007 TON**) was **far below** the **0.05 TON** deploy message value. Seqno polling behaved as designed; the chain state did not advance.

## 2. Seqno polling logic (`_waitForDeployerSeqnoAdvance`)

| Property | Value |
|----------|--------|
| **File** | `server/payment/TonGameContractAdapter.js` |
| **Function** | `_waitForDeployerSeqnoAdvance({ operation, deployerAddress, sentSeqno })` |
| **Initial seqno source** | `getSeqno(deployerAddress)` immediately before signing, inside `_withDeployerSendLock` |
| **Polling interval** | `settlementTxLookupPollMs` if set on `tonConfig`, else **1000 ms** (minimum 50 ms) |
| **Maximum polls** | Until timeout; observed **24–25 polls** in failed sessions ≈ **~30 s** window |
| **Timeout** | `settlementTxLookupTimeoutMs` if set on `tonConfig`, else **30_000 ms** |
| **Final decision condition** | Success when `Number(lastSeen) > Number(sentSeqno)`; else throw `deployer_seqno_confirmation_timeout` |

**Production config note:** `loadTonConfig()` does **not** set `settlementTxLookupTimeoutMs` / `settlementTxLookupPollMs`; production therefore uses **defaults (30 s / 1 s)**, matching archive `polls=24|25`.

### Could timeout fire even if the transaction succeeded?

**Theoretically yes** — only if `getSeqno` returned a stale value or queried the wrong account/network for >30 s while chain seqno had actually advanced.

**For these sessions: no.** Public testnet data shows:

- Current seqno is still **100** (TonCenter `runGetMethod seqno` → `0x64`).
- Outbound deploy attempts at seqno **100** appear on-chain as **`status: "failed"`** transfers.
- Seqno **did not advance** to 101.

The timeout is **consistent with chain state**, not a polling false negative.

**Broadcast vs confirmation:** Code explicitly treats `sendBoc` success as non-confirming (`TonCenterTransport.sendBoc` → `BOC_SEND_SUCCESS`; confirmation requires seqno advance). This matches `deployerSeqnoConfirmation.test.js` Test 4 (“broadcast accepted, but chain never advances seqno”).

## 6. Failure category classification

| Category | Applies? | Evidence |
|----------|----------|----------|
| **A. Transaction never landed (effective)** | **Yes — primary** | On-chain events show **`failed`** transfers; seqno unchanged; no `transactionHash` in archive |

**Supported classification:** **A + insufficient balance** — transactions were propagated and appear on-chain as **failed outbound 0.05 TON transfers**; wallet seqno did not advance because execution did not succeed.

## 8. Root cause conclusion

1. **Wallet connection and payment session creation succeeded** for both rooms.
2. **Deploy pipeline started correctly** and **TonCenter accepted the deploy BOC**.
3. **On-chain execution failed** — public testnet history shows **failed 0.05 TON transfers** from the deployer to each room’s precomputed escrow address at the failure timestamps.
4. **Deployer testnet balance (~0.007 TON) was insufficient** for the configured **0.05 TON** deploy message value (plus fees).
5. **`_waitForDeployerSeqnoAdvance` correctly timed out** because seqno remained **100**.
6. **Both sessions share the same root cause:** under-funded deployer wallet on testnet, not client/browser payment failure and not concurrent deploy interference.

## 9. Recommended minimal fix direction (next stage — not implemented here)

**R17.8M — Deployer funding + preflight guard**

1. **Operational (immediate):** Fund testnet deployer `EQB83s9X…` to cover worst-case deploy cost — at minimum **> 0.05 TON per deploy attempt** plus headroom for `initGame` / `openPayments` follow-up messages and fees (recommend **≥ 0.2–0.5 TON** operational buffer on testnet).
2. **Preflight (minimal code, later):** Before `sendBoc`, read deployer balance and reject deploy with explicit `insufficient_deployer_balance` if `balance < valueTon + feeHeadroom` (no mnemonic exposure).
3. **Observability:** Surface TonAPI/TonCenter execution failure reason in `tonDeployDebug` when broadcast succeeds but seqno stalls (today only timeout string is recorded).
4. **Do not change** GameEscrow contract, payment STAKE flow, or recovery — failure is pre-`PAYMENT_REQUEST`.
