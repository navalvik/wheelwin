# R17.9T.6 Recovery Checkpoint Writer — Implementation Report

Date: 2026-08-23

Task: Implement the production RecoveryCheckpointManager (R17.9T.6) per the completed read-only architecture audit.

## 1. Scope

Implement exactly one centralized, server-authoritative checkpoint writer:

`server/recovery/RecoveryCheckpointManager.js`

plus a focused test suite:

`server/tests/recoveryCheckpointWriter.r179t6.test.js`

plus an additive wiring change in `server/app.js`.

The writer subscribes to existing authoritative lifecycle events, filters to the
approved checkpoint phases, assembles a recovery payload from authoritative
runtime owners, validates checkpoint safety, and persists a single
`RECOVERY_DATA` record per game. It never owns gameplay state, never performs
recovery, never starts recovery, never modifies gameplay state, and never emits
gameplay events.

## 3. Event Subscriptions

Subscribes to exactly two existing events (no new EventTypes created):

- `EVENT_TYPES.GAME_STATE_CHANGED` — handled by `_onGameStateChanged`.
- `EVENT_TYPES.GAME_RESULT_READY` — handled by `_onGameResultReady`.

The manager consumes only; it never emits any gameplay lifecycle event.

## 4. PRE_GAME_READY CREATE

Policy: `PRE_GAME_READY` → CREATE.

Trigger: `GameStateEngine.initializeGameState` emits `GAME_STATE_CHANGED` with
`currentState === "PRE_GAME_READY"` (post-transition).

Preconditions enforced before any persistence call:

- `GameStateEngine.getState(gameId) === "PRE_GAME_READY"` (state already
  transitioned — checkpoint is post-transition).
- `GameClockEngine.getClock(gameId).currentPhase === "PRE_GAME_READY"`
  (clock phase matches).
- `PhysicsEngine.getSimulation(gameId).runtime.state === "CREATED"`
  (no active motion).
- `InputAuthority` registry present and in safe default state
  (empty command queue / history, sequenceNumber 0).
- Configuration present and frozen.
- Exactly 3 players, unique playerIds, playerIndex set `{0,1,2}` matching the
  authoritative room/payment-session ordering.
- `clockPaused === false` (paused-clock policy — see §9).

If a record already exists at `PRE_GAME_READY`, the writer loads it and treats
the duplicate as an idempotent no-op (no second record, no overwrite).

## 5. READY UPDATE

Policy: `READY` → UPDATE.

Trigger: `GameStateEngine.transition(gameId, "READY")` emits
`GAME_STATE_CHANGED` with `currentState === "READY"` (post-transition, after
`GameClockEngine.completePreGameReadyPhase`).

Same preconditions as PRE_GAME_READY except the persisted phase rank must be
exactly `PRE_GAME_READY` (rank 1) — a monotonic guard prevents regression.
The existing record is updated in place; `recordId === gameId` is preserved and
no new record is created.

## 6. RESULT UPDATE

Policy: `RESULT` → UPDATE + terminal status.

Trigger: `EVENT_TYPES.GAME_RESULT_READY` (preferred — avoids the
WinnerActivation retry race). The writer does NOT trigger on the
`GAME_STATE_CHANGED` RESULT transition alone.

Preconditions:

- `GameStateEngine.getState(gameId) === "RESULT"`.
- `PhysicsEngine.getSimulation(gameId).runtime.state === "STOPPED"`.
- `physicsFinalAngle` and `physicsFinalTriangleAngle` are finite.
- `WinnerEngine.getResult(gameId)` read if available; `winnerId` persisted only
  when a result exists (null representation used otherwise, per the existing
  contract).
- No settlement action is performed; no financial truth is calculated.

The existing record is updated and the envelope is marked terminal via the
existing `RecoveryDataPersistence` terminal API (`status: "TERMINAL"`,
`immutable: true`). Repeated identical RESULT events are idempotent no-ops.

## 7. Payload Assembly

Assembled from authoritative runtime owners only, using fields already
supported by the Recovery Data Contract:

Identity: `recoveryRecordId` (= gameId), `roomId`, `gameId`, `contractId`,
`paymentSessionId`, `tonNetwork`, `correlationId`.

Configuration: `configuration` (frozen verbatim), `configurationHash`
(computed via the existing `computePayloadChecksum` / `stableStringify`
convention), `configurationVersion`, `traceSeed`, `snapshotHash`.

Gameplay: `gameState`, `gameStatus`, `serverTimestampAtCheckpoint`.

Players: `playerId`, `playerIndex`, `wallet`, `nickname`, `baseStake`,
`sectorCount`, `color`, `colorSector2`, `icon`, `sectorArrangement`, `age`.

Clock: `phaseStartedAt`, `clockStartedAt`, `clockPaused`,
`clockTotalPausedMs`, `awaitingResultActivation`, `resultPhaseStarted`.

Terminal physics (RESULT only): `physicsFinalAngle`,
`physicsFinalTriangleAngle`, `physicsSimulationState`.

Winner (RESULT only): `winnerId`.

No financial fields, no input history, no socket/session state, no timeout
handles, no economy object, no `resolvedAt`.

## 8. Authoritative State Sources

- `RoomManager` — room identity / player ordering.
- `PlayerManager` — player identity (wallet, nickname, color, icon, age,
  baseStake, sectorCount, sectorArrangement).
- `GameManager` — game identity / status.
- `ConfigurationEngine.getConfiguration(gameId)` — frozen configuration
  verbatim (never regenerated).
- `GameStateEngine.getState(gameId)` — authoritative game state.
- `GameClockEngine.getClock(gameId)` — phase, startedAt, paused, pausedMs.
- `PhysicsEngine.getSimulation(gameId)` — simulation state + final angles.
- `WinnerEngine.getResult(gameId)` — winner reference (read only).
- `GameContractManager` / `PaymentSessionManager` — reference identifiers
  only (contractId, paymentSessionId, tonNetwork, correlationId,
  snapshotHash).

## 9. Paused Clock Policy

If `clockPaused === true` at an approved checkpoint moment, the writer does
NOT call create/update. It logs a structured warning
(`checkpoint_skipped_clock_paused`) and returns a skipped result. Gameplay
continues. The persistence schema is not modified and no pause timing is
invented.

## 10. Physics Validation

PRE_GAME_READY / READY: require `physicsSimulationState === "CREATED"`.
Active motion fields (velocity, angular velocity, command log, active motion
flags) are never persisted.

RESULT: require `physicsSimulationState === "STOPPED"` and finite
`physicsFinalAngle` / `physicsFinalTriangleAngle`. If RESULT physics is not
STOPPED, the writer logs an error and skips the checkpoint.

## 11. Input Validation

No command history is persisted. For PRE_GAME_READY / READY the
`InputAuthority` registry must be in its safe default state (empty command
queue / accepted commands, sequenceNumber 0, default per-player state). If the
current authoritative state is incompatible, the checkpoint is aborted and
logged. `InputAuthority` is never modified by the writer.

## 12. Winner Handling

For RESULT, `WinnerEngine.getResult(gameId)` is read and `winnerId` is
persisted when available. If the result is temporarily unavailable, the
existing contract-compatible null representation is used only where the
current `RecoveryDataPersistence` validation permits it; otherwise the
checkpoint is skipped and the exact reason is logged. `resolvedAt` is never
persisted. `WinnerEngine` resolution is never invoked by the writer.

## 13. Financial Boundary

The writer obtains only existing reference values
(`contractId`, `paymentSessionId`, `tonNetwork`, `correlationId`,
`snapshotHash`). It never calculates payout, organizer amount, total pot,
payment status, settlement status, or refund state. It never calls settlement,
blockchain, or payment recovery. Financial references are references only.

## 14. Idempotency

One record per game (`recoveryRecordId === gameId`). Duplicate events for the
same phase are treated as idempotent no-ops (no second record, no overwrite).
Repeated identical RESULT events are idempotent terminal no-ops.

## 15. Monotonic Phase Guard

Local phase ranking: `PRE_GAME_READY = 1`, `READY = 2`, `RESULT = 3`. Before
any update the writer loads the current record and compares the persisted phase
rank. An older phase never overwrites a newer persisted phase:

- persisted READY + incoming PRE_GAME_READY → ignored as stale.
- persisted RESULT + incoming READY → ignored as stale.
- persisted RESULT + incoming RESULT (equivalent) → idempotent success.
- persisted conflicting RESULT → logged, no overwrite.

Persistence itself does not provide newer-phase protection; the manager
enforces it locally.

## 16. Failure Policy

Checkpoint persistence failure MUST NEVER stop gameplay, rollback gameplay,
stop the server, throw through the EventBus, emit gameplay failure events, or
invoke financial recovery / settlement. Instead:

1. catch the error;
2. produce a structured log (gameId, roomId, phase, operation, reason,
   errorType);
3. classify the error;
4. return a `failed`/`skipped` result;
5. continue gameplay.

## 17. Logging

Uses the project's existing `LoggerService`. Every skipped/failed checkpoint
includes gameId, roomId (when available), phase, checkpoint operation, reason /
error code, and persistence error type where applicable. No private keys,
secrets, full wallet credentials, or sensitive payment internals are logged.
