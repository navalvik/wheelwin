## 4. RecoveryDataPersistence Availability

Source-verified facts:

1. **Not instantiated during production startup.** `new RecoveryDataPersistence` appears only in `server/tests/*`. Production instantiates only `TonFinancialPersistence` (app.js line 1185).
2. **It is a thin synchronous wrapper** over `TonFinancialPersistence` (constructor requires a `financialPersistence` instance; no async init of its own). It can be constructed at any point after `TonFinancialPersistence.initialize()` completes (line 1190), which is synchronous.
3. **Injected into nothing today.** No manager or engine receives it.
4. **Available before gameplay becomes active:** yes — it would be constructible immediately after line 1190, long before Socket.IO/listen.
5. **`listRecoveryRecords()` safety during startup:** safe. It delegates to `listActiveRecoveryDataRecords()` over the already-restored in-memory cache; invalid records are skipped-and-logged (fail-closed per record, not server-wide). No filesystem I/O beyond what `TonFinancialPersistence.restore()` already performed synchronously in `initialize()`.
6. **Storage unavailable:** `TonFinancialPersistence.initialize()` performs directory creation/restore synchronously; a hard storage failure throws during startup and aborts boot (existing behavior — unchanged by this audit). This is the existing fail-closed posture for financial persistence and applies equally to recovery records stored under `active/recovery_data/`.
7. **Malformed/corrupt records:** `CorruptedRecordError` on restore of that record; `listRecoveryRecords()` skips invalid records with an error log. One bad record does not crash the server.
8. **Can persistence initialization block server readiness?** It is synchronous and fast (local file scan); it participates in normal blocking startup like all other sync init. No new blocking risk.

## 7. Safe Recovery Startup Order (derived)

```
after: TonFinancialRecovery.recover() completed
before: GameStartAuthorization / SocketGateway.initialize / _listen()

1. const recoveryDataPersistence = new RecoveryDataPersistence({ financialPersistence });
2. const recoveryOrchestrator = new RecoveryOrchestrator({ ...all deps... });
3. const outcome = recoveryOrchestrator.recoverAll();   // sync
4. feed outcome.summary into HealthService/DeploymentManager (future readiness field)
```

Why exactly there:
- **After financial recovery:** gameplay candidates must be classified/validated against restored financial context; financial-first mirrors synthesis §9 and prevents any interleaving with `recover()`'s cache mutations.
- **After engines/managers:** orchestrator attaches into their registries; they must exist and be initialized.
- **After SimulationLoop.start():** unavoidable in current code; harmless because recovered physics is CREATED/STOPPED (no loop membership needed) and clock arming is setTimeout-based, not loop-based.
- **Before SocketGateway:** sockets must never observe mid-reconstruction registries; also RoomLobbyBridge/GameStartAuthorization read manager state at init.
- **Before `_listen()`:** under fail-closed policy, no client byte may arrive before recovery outcome is known. Because listen is last, simple ordering achieves gating WITHOUT new gate machinery.

## 8. Client Access During Startup (current behavior)

- HTTP listener: opened ONLY at `_listen()` (line 2102 → 5304). Before that, `/health`, `/ready`, `/live`, `/startup` routes exist on the Express app but the server is not accepting connections.
- Socket.IO: attached to the same `_httpServer` in `SocketGateway.initialize(this._httpServer)` (line 1763); no transport possible before listen.
- Therefore **today no client can reach the server before ALL initialization including financial recovery completes.**
- Consequence for future integration: if `recoverAll()` is inserted before `_listen()`, then automatically:
  - no HTTP traffic during recovery ✔
  - no Socket.IO connections during recovery ✔
  - no CREATE_ROOM during recovery ✔
  - no reconnect during recovery ✔
  - readiness endpoints cannot even be polled during recovery (connection-refused), which is acceptable but means "recovery in progress" is NOT observable externally unless a future readiness field is added post-listen.
- No gating implementation exists or is needed for the ordering itself; the existing `RoomManager.attachLifecycleGate` drain mechanism remains a shutdown/drain tool, not a startup tool.

## 9. Room/Game Creation Race

Scenario: `recoverAll()` running while a client connects and issues CREATE_ROOM.

**Currently impossible** — clients cannot connect before `_listen()`, which follows everything. If a future change moved listen earlier or made recovery async-post-listen, the race analysis is:

- **Recovered Room vs CREATE_ROOM same roomId:** collision is structurally improbable-to-impossible: `RoomManager.createRoom()` generates fresh random `roomId`s (`_generateRoomId()`); it never accepts a caller-supplied ID. Duplicate protection: `attachRoom` returns null on duplicate roomId; `hasRoom` guards exist.
- **Recovered Game vs CREATE_GAME same gameId:** same — `gameId = game_${randomUUID()}`; `attachGame` returns null on duplicates; `GameManager.hasGame(gameId)` exists.
- **Real residual risk (post-listen async recovery only):** reconnect lookup (`getRoom(roomId)`, `getGameIdByRoomId`) could observe a room whose engine attachments are incomplete (room attached, configuration not yet). Mitigation belongs to policy: keep recovery strictly pre-listen (recommended), making the race unreachable.
- Existing duplicate protections inventoried (none added): `attachRoom`/`attachGame`/`attachPlayer` duplicate-null semantics; D2 idempotent-equivalent/conflict-fail-closed semantics; orchestrator's own `ALREADY_RECOVERED` detection.

## 10. Recovered Runtime Visibility

A successfully recovered candidate becomes visible through EXISTING getters immediately upon attachment (no extra publish step):

- `RoomManager.getRoom/hasRoom/getRooms` — after `attachRoom`.
- Reconnect lookup path (`getGameIdByRoomId`, `hasInitializedGameplay`) — after `attachGame` with non-CREATED status.
- `GameManager.getGames/hasGame` — after `attachGame`.
- Engine debug getters (`/debug/configuration/:gameId` etc.) — after each respective attach.
- SessionManager/Socket.IO room membership — **NOT populated**: no sockets/sessions are bound by recovery. Simply attaching aggregates IS sufficient for manager-level lookup APIs, but insufficient for live session re-binding (that is the later reconnect-integration stage).
- Players are reconstructed as `DISCONNECTED`/`IDLE` (PlayerRuntime defaults) — honest absence of connection state.

## 11. Clock / Timer Startup

Verified chain: `attachClock(clockState, { arm:false })` → cross-engine validation → `armRecoveredClock(gameId)`.

- Timers do NOT depend on SimulationLoop: arming creates exactly one `setTimeout` inside GameClockEngine. Safe before/after loop existence.
- Timers do NOT depend on EventBus subscriptions for arming: `armRecoveredClock` emits no lifecycle events (D2-verified). Phase-timeout firing later WOULD emit through the bus — hence arming must occur only after EventBus and all gameplay activation subscribers exist (they do, steps 10/16).
- GameStateActivation dependence: arming itself does not invoke activation classes; a timeout expiry later drives normal phase transitions through the standard event flow. Since EventBus + activations are initialized before the integration point, expired-clock handling post-arm behaves normally.
- Arming emits no events at arm time; the armed clock CAN fire `PHASE_TIMEOUT` later during normal operation — this is desired behavior for a resumed PRE_GAME_READY/READY game.
- Can a recovered PRE_GAME_READY/READY game become active before sockets are ready? Only in the sense that its clock may expire while dormant (players DISCONNECTED). Phase transitions would proceed event-driven with no socket consumers; players remain IDLE; no input can arrive. This is bounded and matches the "dormant until reconnect stage" model documented in D3. If this dormancy-expiry is deemed unacceptable, the alternative is to not arm until reconnect stage — a policy decision explicitly OUT OF SCOPE here; default D3 behavior (arm after validation) is compatible with pre-listen placement.

## 12. SimulationLoop Boundary

- Confirmed: RecoveryOrchestrator registers NOTHING in SimulationLoop (zero registration; no PHYSICS_STARTED emitted — D3-tested).
- No recovered state requires loop membership: CREATED (pre-game) and STOPPED (terminal) simulations are inert; loop membership arises only from PHYSICS_STARTED in normal flow.
- SimulationLoop initialization/start touches no existing games (it iterates registered simulations only).
- Future startup recovery relative to loop creation: irrelevant for correctness given CREATED/STOPPED-only restoration; current code has the loop starting earlier anyway. Recommendation: leave loop position untouched; do NOT relocate it.

## 13. Startup Failure Policy (current + recommended future)

Current startup: any thrown error in the awaited `start()` chain aborts boot (`process.exit(1)`). Sync failures likewise. There is no partial-start mode.

Recommended classification for FUTURE recovery integration (policy only, not implemented):

| Case | Policy |
|---|---|
| A. Recovery storage unavailable | MUST BLOCK SERVER STARTUP (same as financial persistence failure today; financial truth unreadable ⇒ fail-closed) |
| B. Recovery storage empty | MUST NOT BLOCK — log, continue (`summary.total === 0`) |
| C. One invalid recovery record | SHOULD LOG AND CONTINUE (persistence already skips-invalid; orchestrator reports FAILED_INVALID_RECORD) |
| D. One corrupt recovery record | SHOULD LOG AND CONTINUE (CorruptedRecordError skipped by list; optionally counted) |
| E. One recoverable candidate | Normal SUCCESS path; MUST NOT BLOCK beyond its own processing time |
| F. One candidate fails during reconstruction | SHOULD LOG AND CONTINUE (orchestrator rolls back silently; summary.failed incremented) |
| G. Mixed success/failure batch | SHOULD LOG AND CONTINUE — per-candidate independence is already implemented |
| H. Orchestrator/dependency construction failure | MUST BLOCK SERVER STARTUP (programming/wiring error, not data condition) |
| I. Recovery runtime inconsistency detected | SHOULD LOG AND CONTINUE per candidate (FAILED_CONSISTENCY + rollback); aggregate inconsistency across many candidates MAY justify NOT-READY marking (operator decision) |
| J. Slow persistence | N/A for list (in-memory post-restore); if a future async checkpoint mechanism appears, apply a startup timeout budget then mark NOT-READY rather than blocking indefinitely |

Rationale: data-level faults are per-candidate fail-closed (architecture principle); infrastructure-level faults are boot-blocking (existing convention).

## 14. Fail-Closed vs Fail-Open

Derived from WheelWin architecture, not generic practice:

- **Fail-open consequences:** server accepts new gameplay while recovery incomplete/failed. Risks: (a) reconnect lookups may miss or half-see recovered rooms/games → players permanently locked out of paid sessions; (b) new games could theoretically interleave with late-finishing recovery (currently prevented only by ordering); (c) a failed candidate's escrow obligations continue via financial recovery, but the gameplay side is invisible → support/audit ambiguity; (d) violates "recovery must be fail-closed; never invent state" spirit by proceeding as if nothing was lost.
- **Fail-closed consequences:** server does not accept traffic until recovery outcome known. Cost: startup latency proportional to candidate count (small: local file reads + in-memory attaches; milliseconds-scale). Benefit: identity correctness (a recovered roomId/gameId is fully present before any client can query it), zero duplicate-runtime risk, deterministic guarantee that readiness implies recovery settled.
- **Recommendation: FAIL-CLOSED**, implemented trivially by placing `recoverAll()` before `_listen()` (ordering-based, no new gate code). This aligns with: server-authoritative single source of truth; financial truth precedence; original-ID preservation; duplicate-runtime prevention; deterministic gameplay. Partial failure inside recovery still yields a RUNNING server (per §13 per-candidate policy) — fail-closed applies to the *boundary*, not to individual bad records.

## 15. Readiness Semantics

Current probes:
- `/health` — HealthService snapshot (`ready`, component registry, runtime counts); 503 when not ready/draining.
- `/ready` — DeploymentManager readiness (lifecycle, config, logging, monitoring, httpListening, socketListening, etc.).
- `/live` — liveness fallback.
- `/startup` — startup progress probe.

Distinctions that exist: process alive (/live) vs dependencies initialized (/health components) vs listeners up (/ready httpListening/socketListening).

Distinctions that DO NOT exist (integration gap, documented only):
- recovery completed (no component/flag);
- gameplay-available-after-recovery (no notion of recovered-candidate counts or failures);
- financial systems ready (implicit — financial recovery runs pre-listen, so readiness implies it, but it is not an explicit probe field).

Future integration should add a recovery summary field/component to HealthService/DeploymentManager providers — explicitly deferred; not implemented here.

## 16. Shutdown Interaction

Current graceful shutdown order (verified): drain wait → emit SERVER_SHUTDOWN → teardown activations/broadcasters → simulationLoop.shutdown → engines.shutdown → managers.shutdown → financialPersistence.shutdown({ checkpoint: true }) → services → logging.

Future startup-recovery interaction points (documentation only):
- Recovered runtime objects live in the SAME registries as normal runtime; all nine components' SERVER_SHUTDOWN handlers destroy them identically. No special recovery teardown needed.
- `financialPersistence.shutdown({ checkpoint: true })` persists financial checkpoints; recovery records under `active/recovery_data/` are NOT deleted by shutdown — a restart simply re-attempts them (idempotency via ALREADY_RECOVERED/conflict rules makes repeated restarts safe).
- Required future sequencing rule: recovery-record checkpoint writing (later stage) must complete BEFORE `financialPersistence.shutdown({checkpoint:true})` in the teardown order, or be part of that call's atomic write set, so a crash during shutdown cannot lose the last gameplay checkpoint.
- SimulationLoop stop and Socket.IO shutdown need no recovery awareness.

## 17. Financial Boundary

Startup recovery integration MUST NOT cause (and the orchestrator structurally cannot cause): payment reconciliation, settlement, refunds, prize distribution, blockchain writes, financial cache mutation. Verified: orchestrator preserves reference IDs only; forbidden financial-authority fields are rejected at persistence level; zero TonFinancialPersistence write invocations (D3-tested).

Ordering requirement: `TonFinancialRecovery.recover()` MUST precede gameplay recovery (financial caches restored first; gameplay validation reads payload-local references only). Beyond that, financial systems need only be *available as read-only context* — no financial initialization must follow recovery.

## 18. Reconnect Boundary

- Reconnect currently depends on RoomManager (`getRoom/hasRoom`) and GameManager (`getGameIdByRoomId`, `hasInitializedGameplay`) plus RecoveryEngine/RecoverySnapshotCache for state resync.
- Recovered runtime IS automatically discoverable by manager-level lookup (§10) — but NOT resumable: no bound sockets, no wallet sessions re-bound, players IDLE/DISCONNECTED, no RecoverySnapshotCache snapshot exists for recovered games.
- Reconnect cannot happen before startup recovery completes under the recommended ordering (pre-listen).
- Later integration stage must connect: socket/session binding, SessionWalletStore wallet-session association, player-state policy (IDLE→PLAYING where applicable), snapshot creation or equivalent state-resync source, client notification. Explicitly out of scope here.

## 19. Production Recovery Data Gap

Confirmed from D3 report and re-verified by search: **production code creates ZERO RECOVERY_DATA records.** Nothing calls `createRecoveryRecord`/`updateRecoveryRecord` outside tests.

- TECHNICALLY POSSIBLE now: full startup integration (construct wrapper + orchestrator, call `recoverAll()`, wire result into logs/readiness). It will run correctly against empty storage (summary.total === 0) and against synthetic records in staging.
- OPERATIONALLY MEANINGFUL: NO. With no production checkpoint writer, `active/recovery_data/` will always be empty in real deployments; the integration protects against nothing yet. Startup integration is therefore a *prerequisite plumbing* stage whose value materializes only after the checkpoint-writing stage lands.
- Verdict: implementable in either order technically; recommended order remains checkpoint-writing FIRST (or simultaneously), because shipping pre-listen recovery with always-empty storage adds startup surface with zero protective benefit.

## 21. Validation Strategy (future tests — NOT implemented)

1. No recovery records → clean boot, summary.total===0, readiness healthy.
2. Valid PRE_GAME_READY candidate → recovered, clock armed, dormant, zero events.
3. Valid READY candidate → recovered incl. input registry.
4. Valid RESULT candidate → terminal restore, winner==payload.winnerId, no clock.
5. Invalid candidate → skipped/logged, boot continues.
6. Expired candidate → FAILED_EXPIRED, no residue, boot continues.
7. Corrupt candidate → CorruptedRecordError path, skipped, boot continues.
8. One succeeds + one fails → independence, correct summary counts.
9. Storage unavailable → boot blocked (assert exit/failure).
10. Orchestrator construction failure (missing dep) → boot blocked.
11. CREATE_ROOM during recovery → structurally impossible pre-listen; assert no listener before recoverAll returns (test hook/spy on _listen ordering).
12. Reconnect during recovery → same impossibility assertion.
13. /health during recovery → connection refused pre-listen (documented behavior).
14. /ready during recovery → same.
15. Recovery clock arming → exactly one timeout, no lifecycle events, expiry behaves normally post-boot.
16. Zero duplicate runtime creation → attach-duplicate/idempotency assertions.
17. Zero financial side effects → spy: no TonFinancialPersistence write methods invoked during startup recovery.
18. Clean shutdown after recovered runtime exists → SERVER_SHUTDOWN destroys recovered state; second restart re-attempts idempotently (ALREADY_RECOVERED or clean re-recovery from still-present records).

## 22. Risks

- **High:** integrating startup recovery BEFORE production checkpoint writing ships → permanent empty-path code with maintenance cost and no benefit (mitigation: sequence checkpoint-writing first or together).
- **Medium:** future refactors that move `_listen()` earlier or make recovery async/post-listen silently reintroduce the §9 race (mitigation: regression test asserting ordering; comment at integration point).
- **Medium:** dormancy expiry — an armed recovered PRE_GAME_READY/READY clock may expire with no players connected, advancing the game to SELF_TEST (unrecoverable) before reconnect stage lands (mitigation: explicit policy decision in the reconnect-integration stage; possibly defer arming).
- **Low:** readiness observability gap during recovery (connection-refused instead of 503-with-reason) — acceptable for expected millisecond-scale recovery; improve later via readiness field.
- **Low:** rollback-event noise — eliminated by silent detach primitives (already implemented).

## 23. Final Verdict

- **Exact startup integration point:** in `server/app.js`, immediately AFTER `await this._tonFinancialRecovery.recover({ trigger: "server_restart", ... })` + the two deposit sync lines (current lines ~1719–1730), and BEFORE `new GameStartAuthorization(...)` / `new SocketGateway(...)` / `await this._listen()`.
