# R17.8O.4 — Setup Expiry Escrow Unwind Bridge

**Mode:** Implementation + validation  
**Date:** 2026-08-14  
**Depends on:** R17.8O.1 (`0d85a93`), R17.8O.3 (ROOM_Zsqb forensics)

---

## 1. Original bypass path

Live session **ROOM_Zsqb** exposed that R17.8O.1 unwind only ran from `PaymentSessionManager.failSession()`. Setup Timer expiry used a separate path:

```text
PARTIALLY_PAID
  ↓
SETUP_SESSION_EXPIRED
  ↓
RoomLobbyBridge._handleSetupSessionExpired()
  ↓
_closeRoom("setup_expired")          ← bypass
  ↓
SetupSessionLifecycle._onExpiry()
  ↓
RoomManager.destroyRoom()            ← also bypassed unwind
  ↓
ROOM_DESTROYED (no EMERGENCY_CANCEL)
```

Payment session still had **~128 s** remaining when Setup Timer fired (R7.70C23).

---

## 2. New Setup Expiry bridge

### RoomLobbyBridge

Before `_closeRoom("setup_expired")`, check:

- `sessionNeedsEscrowUnwind(paymentSession)` (reused O.1 helper)
- deployed contract has `contractAddress`

If true → `failSession(roomId, "setup_expired")` and return (existing O.1 flow handles cancel + refunds).

If false → unchanged `_closeRoom("setup_expired")`.

### SetupSessionLifecycle

After `SETUP_SESSION_EXPIRED` subscribers run, **defer** `RoomManager.destroyRoom()` when payment session is already `REFUND_PENDING` (O.1 unwind in progress). Without this guard, lifecycle would destroy the room synchronously after the event even when the bridge defers `_closeRoom`.

---

## 3. Updated lifecycle diagram

```text
SETUP_SESSION_EXPIRED
  ↓
sessionNeedsEscrowUnwind + contractAddress?
  ├─ NO  → _closeRoom("setup_expired") → ROOM_DESTROYED
  └─ YES → failSession("setup_expired")
              ↓
           REFUND_PENDING
              ↓
           requestPartialPaymentEscrowUnwind (O.1)
              ↓
           ESCROW_CANCEL_* → ESCROW_REFUND_*
              ↓
           PAYMENT_SESSION_FAILED
              ↓
           _closeRoom → ROOM_DESTROYED
```

Setup Timer creation / wall-clock `expiresAt` behavior (**R7.70C23**) unchanged.

## 6. Remaining limitations

- **Setup Timer still authoritative during PAYMENT** — slow verify/join can consume most of the 5 min window before stakes complete; unwind now runs on expiry but players may still lose payment time to setup clock.
- **Cancel failure** — same as O.1: room preserved, manual recovery may be required.
- **Other teardown paths** — only `setup_expired` and existing `failSession` triggers are covered; no broad `_closeRoom` central guard (optional future hardening).
- **ROOM_Zsqb funds** — on-chain cancel/refund for that session requires separate recovery (pre-O.4 deploy).
