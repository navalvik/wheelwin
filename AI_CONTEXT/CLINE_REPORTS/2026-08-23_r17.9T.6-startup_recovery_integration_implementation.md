## 3. Architecture Findings

Current startup sequence in `WheelWinApplication.start()` (source-verified):

1. Configuration, logging, health, lifecycle, operational managers.
2. Services, managers, engines, SimulationLoop, gameplay activation layer.
3. `TonFinancialPersistence` initialization (durable financial store).
4. Payment / contract / deposit / reimbursement subsystems.
5. `TonFinancialRecovery.initialize()` + `await recover({ trigger: "server_restart" })` — existing financial recovery.
6. `GameStartAuthorization` construction + initialize.
7. `RecoveryDataPersistence` construction (over `this._financialPersistence`) + `RecoveryCheckpointManager` construction + initialize (R17.9T.6 checkpoint writer).
8. **[NEW]** `RecoveryOrchestrator` construction + `recoverAll()` — startup gameplay recovery.
9. `SocketGateway` construction + `initialize(this._httpServer)` (Socket.IO attach).
10. RoomLobbyBridge, console, advertisement, monitoring, deployment health.
11. `await this._listen()` — HTTP server starts accepting connections.

Key observation: Socket.IO is attached to the HTTP server at step 9, but no client can connect until `_listen()` at step 11. Therefore the existing asynchronous `start()` sequence already provides a natural ordering gate: anything awaited/ executed before `_listen()` is guaranteed to complete before any client/socket access. No new readiness gate, no SocketGateway change, and no `listen()` change were required.

## 4. Lifecycle Flow

`process bootstrap → start() → ... → financial recovery → RecoveryDataPersistence → RecoveryCheckpointManager → RecoveryOrchestrator.recoverAll() → SocketGateway → ... → _listen() → RUNNING`

`recoverAll()` is synchronous with respect to `start()`; startup cannot proceed to SocketGateway construction until it returns.

## 5. Ownership Boundaries

- RecoveryOrchestrator remains the single candidate-recovery authority (attach, validation, silent rollback). app.js performs no rollback and no second recovery mechanism.
- RecoveryCheckpointManager remains the sole checkpoint writer.
- TonFinancialRecovery remains the sole financial recovery authority.
- app.js only constructs the orchestrator from already-existing dependencies and enforces the startup failure policy.

## 6. Risks

- Critical: none found.
- High: none found.
- Medium: recovered PRE_GAME_READY/READY clocks are armed during startup while players are disconnected (known architectural risk from the startup audit). See section 11 — observed, not worked around, not modified.
- Low: candidate failure log noise at startup for genuinely bad records (intended observability).

## 7. Recommendations

- Future stage: decide policy for recovered clocks reaching unsupported active phases (SELF_TEST/SPEED/BRAKE) with no players connected. This requires an architecture decision (e.g., connectivity-aware clock arming or startup clock suspension) and is explicitly out of scope here.
- Future stage: reconnect flow for recovered games.

## 8. Changes Made

### `server/app.js` (modified)

- Added import: `RecoveryOrchestrator`.
- Inserted the startup gameplay recovery block immediately after `RecoveryCheckpointManager.initialize()` and before `SocketGateway` construction:
  - Constructs `RecoveryOrchestrator` from existing dependencies (`recoveryDataPersistence`, room/player/game managers, configuration/state/clock/physics engines, inputAuthority, winnerEngine).
  - Construction failure → `LifecycleError("Startup gameplay recovery infrastructure unavailable: ...")` → propagates out of `start()` → process exits fail-closed (existing bottom-level catch calls `process.exit(1)`).
  - Calls `recoverAll()`.
  - `summary.discoveryFailed === true` → `LifecycleError` → startup-fatal.
  - Per-candidate `FAILED_*` results are logged (`STARTUP_GAMEPLAY_RECOVERY_CANDIDATE_FAILED`) and do NOT terminate startup. `SKIPPED_*` results are not treated as failures.
  - Summary logged as `STARTUP_GAMEPLAY_RECOVERY_COMPLETE | discovered | recovered | skipped | failed`.
  - Empty store → zero results → normal startup continues.
- No other startup code was refactored. No new fields on the application object (orchestrator kept local to `start()`).

### `server/tests/startupRecoveryIntegration.r179t6.test.js` (added)

Focused startup integration test with 12 sections (A–L), see section 12.

## 9. Startup Failure Policy (implemented)

- Infrastructure-level failure (RecoveryDataPersistence/RecoveryOrchestrator construction failure; discovery failure through the persistence layer) → startup-fatal, fail-closed. The server never becomes production-ready without authoritative startup recovery infrastructure.
- Individual candidate failure (malformed/expired/unsupported/attach/validation) → logged, non-fatal; RecoveryOrchestrator's existing per-candidate silent rollback remains authoritative; startup continues.
- Empty recovery store → normal successful startup.

## 10. Socket/Client Startup Ordering

Source-ordering test (section A of the test) asserts, by reading `server/app.js` source:

`RecoveryCheckpointManager.initialize()` < `new RecoveryOrchestrator({` < `.recoverAll()` < `this._socketGateway = new SocketGateway({` < `await this._listen();`

Since `recoverAll()` is synchronous within `start()`, no client/socket access is possible before startup recovery completes. No readiness gate was invented; the existing sequence provides the ordering.

## 11. Clock Behavior

Observed and validated in tests C, D, G, I:

- Successful PRE_GAME_READY/READY recovery: recovered clock attached and armed (`running === true`) as the final orchestrator step.
- RESULT recovery: no clock attached; deterministic winner result restored.
- Expired candidate: no clock residue.
- Known risk (not worked around): an armed recovered clock progresses toward unsupported active phases while players are disconnected. Per task instructions, GameClockEngine and RecoveryOrchestrator were NOT modified; no startup clock workaround was added. This remains an open architecture decision.
