# R18.0-B — DepositOrchestrator Error Observability

Date: 2026-08-26

Task: Expose the exact DepositOrchestrator failure that caused the R18.0 real
gameplay payment timeout (room `Seik`, game `game_eb7dbb22-c76d-4e89-a2bc-f24457289509`,
payment session `pay_17c4631b-a49f-4deb-96de-28843f4a40e1`), without changing any
payment behavior.

## 1. Problem Being Diagnosed

The forensic report
`AI_CONTEXT/CLINE_REPORTS/2026-08-26_r18.0_payment_failure_forensic.md`
established that `DepositOrchestrator.handlePaymentConnectionReady()` threw four
times in the real session, but the persisted developerLog contained only the
generic message `DepositOrchestrator PAYMENT_CONNECTION_READY failed` with no
code/message/details, making root-cause identification impossible.

## 2. Existing Error Handling (VERIFIED FROM SOURCE)

- `server/deposit/DepositOrchestrator.js:137-152` (pre-change): the catch handler
  DID pass a metadata object `{roomId, code, message}` as the second argument to
  `this._logger.error(message, fields)`.
- `server/services/LoggerService.js:133-137` forwards `(message, error, fields)`.
- `server/logging/LoggerFactory.js:65-84` (`BoundLogger.error`): a plain-object
  second argument is treated as structured **fields**, not an error.
- `server/logging/LoggingManager.js:232-318` (`write`) copies known id fields
  (`roomId`, etc.) into the record and other fields as extras.
- HOWEVER, the session-history developerLog (verified in the forensic archive)
  persists only `{at, level, source, message}` per entry — structured fields are
  stripped by the archive extraction. Therefore `code`/`message` never reached
  the forensic evidence surface.

Conclusion: the metadata existed at the call site but was not durable on the
surfaces used for post-mortem analysis.

## 3. Exact Observability Change (IMPLEMENTED)

Single change in `server/deposit/DepositOrchestrator.js` (`_boundHandler` catch):
the log message now embeds the exact failure inline, so it survives every
transport and archive extractor:

```
DepositOrchestrator PAYMENT_CONNECTION_READY failed | stage=PAYMENT_CONNECTION_READY | code=<code|UNKNOWN> | errorName=<name|UNKNOWN> | error=<message> | details=<JSON details if present>
```

Structured fields are still passed alongside (`roomId`, `stage`, `code`,
`errorName`, `errorMessage`, `details`). No control flow changed; the error is
still caught-and-logged exactly as before (fire-and-forget `.catch`); nothing is
swallowed or rethrown differently.

## 4. Safe Fields Retained / 5. Excluded

Retained: `roomId`, `stage=PAYMENT_CONNECTION_READY`, `code`,
`errorName`, `errorMessage` (inline), and `details` — safe metadata already part
of the existing `DepositOrchestratorError` contract
(`DepositOrchestratorErrors.js:20-30`), JSON-serialized only when non-null.

Explicitly excluded: private keys, mnemonics, wallet secrets, auth tokens,
cookies, authorization headers, environment variables, wallet credentials.
Only fields already present on the thrown error object and public event payload
are emitted; the existing `LogSanitizer` still runs over all output.
