- `RecoveryOrchestrator`, `RoomManager`, `GameManager`, and `PlayerManager` not modified.

## 3. Engine-by-Engine Findings

### 3.1 ConfigurationEngine

#### Current state and ownership

`ConfigurationEngine` exclusively owns:

- `_configurations: Map<gameId, frozenConfiguration>`;
- `_economies: Map<gameId, frozenEconomy>`;
- infrastructure event subscriptions;
- initialization state.

Both registries use exact `gameId` strings as keys. The engine does not own `roomId`, `playerId`, game lifecycle, persistence, or orchestration.

#### Constructor dependencies

- `logger`
- `eventBus`
- `gameCatalog`
- `randomService`

`randomService` is used only by normal configuration generation. Recovery must not call that generation path.

#### Normal creation path

```text
buildConfiguration(gameId, room, players)
  -> random traceSeed
  -> catalog colors/timers/wheel rules
  -> randomized wheel layout
  -> randomized wheel and triangle start angles
validateConfiguration(configuration)
freezeConfiguration(configuration)
commitConfiguration(configuration)
  -> _configurations.set(gameId, configuration)
  -> CONFIGURATION_READY emitted
GAME_INITIALIZED event
  -> freezeEconomy(gameId)
  -> _economies.set(gameId, economy)
```

The committed configuration includes at least:

- `gameId`
- `configurationVersion`
- `createdAt`
- `traceSeed`
- `players[]`
- `sectors[]`
- `wheel` including `startAngle`, limits, sector count, and player order
- `triangle` including `startAngle` and ratio
- `timers`
- `stake`
- `metadata.roomId`
- `metadata.catalogVersion`

The current source therefore already has configuration identity/version metadata. Integrity checksum is external: `RECOVERY_DATA.configurationHash` is a stable SHA-256 of the full configuration. `GAME_CONTRACT.snapshotHash` is a different financial-snapshot hash and must not be treated as a configuration hash.

#### Mutation and teardown APIs

- `freezeEconomy(gameId)` creates immutable derived economy state and is idempotent.
- `removeConfiguration(gameId)` deletes both configuration and economy and emits `CONFIGURATION_REMOVED`.
- `shutdown()` and `SERVER_SHUTDOWN` remove all configurations.

There is no supported mutation of a committed configuration.

#### Getter/snapshot sufficiency

- `getConfiguration(gameId)` returns the frozen configuration object.
- `getEconomy(gameId)` returns the frozen economy.
- `getDebugSnapshot(gameId)` omits sectors, players in full, timers, stake, metadata, and economy.
- `listConfigurationIds()` exposes registry keys.

`getConfiguration` is sufficient to capture the exact committed configuration for persistence. `getDebugSnapshot` is not sufficient as a recovery representation.

#### Restore capability

No dedicated restore/attach API exists.

`commitConfiguration(configuration)` is not recovery-safe because it:

1. assumes the caller has already validated and frozen the object;
2. emits `CONFIGURATION_READY`, which can activate normal lifecycle consumers;
3. does not verify `configurationHash`;
4. does not verify expected `gameId`, `roomId`, player set, or recovery record identity;
5. does not restore economy state.

The persisted full configuration can be reconstructed exactly only by validating its checksum, validating its internal structure and identities, deep-freezing a detached object, and attaching it without normal lifecycle events.

#### Mandatory recovery inputs

- persisted full `configuration`;
- `configurationHash`;
- recovery `gameId`;
- recovery `roomId`;
- persisted `configurationVersion` and `traceSeed` for cross-checks;
- authoritative reconstructed player IDs for membership validation.

Exact economy reconstruction is a separate caveat. Economy values are derived from current catalog payment rules and `frozenAt: Date.now()`. The historical `frozenAt` is not persisted. The financial snapshot contains economy facts, but D2 must not consume or modify financial authority. D2 can safely attach configuration without inventing economy; exact economy restoration requires either a validated derivation rule against the original catalog/financial references or a later cross-domain decision. Recovery must not silently derive a different economy after a catalog change.

#### Ordering, idempotency, duplicates, failure

- Must occur after Game identity exists and after the reconstructed players needed for identity validation exist.
- Must occur before Winner restoration/resolution.
- It should occur before GameState/Clock/Physics so downstream validation can compare configuration timers and phase rules.
- Duplicate `gameId` currently throws through `commitConfiguration`.
- Safe idempotency must mean: same `gameId` + same configuration hash may return the existing object; same `gameId` + different content/hash must fail closed.
- Any validation error must leave neither `_configurations` nor `_economies` partially populated.

#### D2 recommendation

Add a dedicated silent, atomic attach API. Architectural shape:

```js
attachConfiguration({
    gameId,
    roomId,
    configuration,
    configurationHash
})
```

It must validate, deep-freeze, attach atomically, emit no `CONFIGURATION_READY`, generate no random values, and reject identity/hash/version mismatch.

### 3.2 GameStateEngine

#### Current state and ownership

`_states: Map<gameId, record>` owns:

```js
{
    currentState,
    previousState,
    enteredAt,
    history: [{ state, enteredAt, reason }]
}
```

The key is exact `gameId`.

Valid states are:

```text
PRE_GAME_READY -> READY -> SELF_TEST -> SPEED -> BRAKE -> RESULT
```

`GAME_INITIALIZED` is not a GameStateEngine state. It is a GameManager lifecycle event/status. `COUNTDOWN` is not a current state.

#### Constructor dependencies

- `logger`
- `eventBus`

No constructor dependency on configuration or GameManager exists. Cross-engine consistency is enforced by lifecycle modules, not inside this engine.

#### Creation, mutation, teardown

- `initializeGameState(gameId)` creates `PRE_GAME_READY` and emits `GAME_STATE_CHANGED`.
- `transition(gameId, nextState)` enforces the forward-only table, mutates history, and emits `GAME_STATE_CHANGED`.
- `resetState(gameId)` destroys state and recreates `PRE_GAME_READY`, emitting a normal state event.
- `removeState(gameId)` deletes state without a state-change event.
- shutdown removes all state.

#### Getter/snapshot sufficiency

- `getState(gameId)` returns current state only.
- `getHistory(gameId)` returns copied history.
- `getDebugSnapshot(gameId)` returns current/previous/enteredAt/history and allowed transitions.
- internal `_createSnapshot` contains complete state record data.

Public getters are sufficient to capture the current record if `getState`, `getHistory`, and debug data are combined, but there is no single explicitly recovery-oriented snapshot. The current `RECOVERY_DATA` contract persists `gameState` and `serverTimestampAtCheckpoint`, but not `previousState`, `enteredAt` under the GameState name, or history. It persists `phaseStartedAt` from the clock.

#### Restore capability and event safety

No restore/attach API exists.

Normal methods are unsafe:

- replaying transitions emits all historical `GAME_STATE_CHANGED` events;
- those events are consumed by `WinnerActivation`, `GameplayLifecycle`, and `RecoverySnapshotCache`;
- reaching `RESULT` can schedule teardown and other terminal behavior;
- `initializeGameState` always starts at `PRE_GAME_READY` and emits an event.

Therefore recovery attachment **must not emit `GAME_STATE_CHANGED`**. The event means a live authoritative transition occurred now. Recovery is registration of already-authoritative state, not a new transition.

#### Mandatory recovery inputs

Minimum semantic restoration:

- `gameId`;
- valid persisted `gameState`;
- authoritative state entry timestamp.

The current contract does not persist `GameStateEngine.enteredAt` separately. `phaseStartedAt` may be used only if the architecture explicitly guarantees clock phase and GameState entry are the same event boundary. Current runtime can transition from both `GameplayPhaseLifecycle` phase-started events and `GameStateActivation` timeout events, so consistency must be validated rather than assumed.

History is useful for audit but not required for current transition behavior. If omitted, D2 must not invent historical transitions. A minimal recovered history may contain only the attached current state and must be explicitly marked/reasoned as recovery metadata, or history should remain empty if consumers permit it.

#### Ordering, idempotency, duplicates, failure

- Requires Game identity.
- Should follow Configuration attachment for candidate-wide validation.
- Must precede InputAuthority activation and clock scheduling validation.
- Same exact state attachment may be idempotent; conflicting duplicate must fail closed.
- Invalid state, missing timestamp, or state/clock mismatch must fail before map mutation.
- A failure after insertion requires rollback via `removeState`; atomic prevalidation is preferable.

#### D2 recommendation

```js
attachState({
    gameId,
    currentState,
    enteredAt,
    previousState = null,
    history = []
})
```

The API must validate the state and timestamps, attach silently, not replay transitions, and not emit `GAME_STATE_CHANGED` or `GAME_STATE_REJECTED`.

### 3.3 GameClockEngine

#### Current state and ownership

`_clocks: Map<gameId, record>` owns:

- phase identity (`currentPhase`);
- lifecycle flags (`running`, `paused`);
- `startedAt`, `elapsed`, `pausedAt`, `totalPausedMs`, `pauseStartedAt`;
- `phaseStartedAt`, `phaseEndsAt`, `phaseRemainingMs`;
- one `setTimeout` handle per clock;
- `awaitingResultActivation`, `resultPhaseStarted`;
- phase history;
- immutable `frozenTimers` snapshot.

The key is exact `gameId`. `timeoutHandle` is runtime-only and must always be recreated, never persisted.

#### Constructor dependencies

- `logger`
- `eventBus`
- `gameCatalog`

The engine has no direct GameStateEngine dependency. Synchronization occurs through emitted phase events and phase lifecycle consumers.

#### Creation, mutation, teardown

- `createClock(gameId)` creates a stopped empty clock and snapshots current catalog timers.
- `startClock(gameId)` starts at `PRE_GAME_READY`, schedules a timeout, emits phase-start and `CLOCK_STARTED` events.
- pause/resume/stop mutate timing and emit normal lifecycle events.
- `beginResultPhase` schedules RESULT and emits `RESULT_STARTED`.
- `removeClock` clears timeout and removes state.
- shutdown clears all clocks/timeouts.

#### Existing partial restore

`restorePhaseSchedule(gameId, { phase, phaseStartedAt, phaseEndsAt })` exists but is insufficient for restart recovery. It requires an already-existing, running, unpaused clock and restores only the phase schedule. It does not restore:

- `startedAt`;
- `running` / paused semantics from persistence;
- `totalPausedMs`, `pauseStartedAt`, `pausedAt`;
- `awaitingResultActivation`, `resultPhaseStarted`;
- `history`;
- original `frozenTimers`.

It also computes `remaining = Math.max(0, phaseEndsAt - Date.now())` and then calls `_schedulePhaseTimeout`. `_schedulePhaseTimeout` does nothing when duration is `<= 0`. The result can therefore be a clock marked running in an already-expired phase with no timeout. This is unsafe for restart restoration.

#### Getter/snapshot sufficiency

- `getClock` returns current phase, startedAt, phase schedule, elapsed, running, paused.
- `getPhaseSchedule` returns phase/start/end/running/paused.
- `getRemaining` computes wall-clock remaining time.
- `getDebugSnapshot` returns history but omits many internal fields.

No public getter returns `totalPausedMs`, `pauseStartedAt`, `awaitingResultActivation`, `resultPhaseStarted`, or `frozenTimers`. Existing getters are insufficient to create the full current recovery contract without internal access or a new snapshot API.

#### Authoritative time basis

Current engine time is based on server wall-clock `Date.now()`. Recovery must use persisted absolute server timestamps:

- `serverTimestampAtCheckpoint`;
- `clockStartedAt`;
- `phaseStartedAt`;
- configuration timer duration or persisted clock deadline.

For an unpaused phase:

```text
phaseEndsAt = phaseStartedAt + frozenDuration
remainingAtRestore = phaseEndsAt - Date.now()
```

The downtime naturally consumes phase time.

For a paused phase, downtime must not consume the remaining phase. Remaining time should be computed as of `serverTimestampAtCheckpoint`, not restore time. The current contract stores `clockPaused` and `clockTotalPausedMs` but not `pauseStartedAt` or explicit `phaseRemainingMs`. This is a real exact-state gap for global elapsed-time reconstruction. Phase remaining can be derived from checkpoint time if `phaseStartedAt` is the effective phase start and no unrepresented pause occurred, but historical elapsed cannot be reproduced exactly without the active pause start or persisted elapsed/remaining value.

#### Expired deadlines

A persisted unpaused deadline that is already expired must never be silently restarted and must never be attached as `running` without a timeout.

D2 engine behavior should return a typed failure/status such as `expired` without emitting phase completion, timeout, phase-start, or state-transition events. Deciding whether to catch up, fail the candidate, or perform terminal handling belongs to later orchestration. Under current safe eligibility rules, an active candidate whose authoritative phase expired while the server was down must fail closed unless a separately approved catch-up policy exists.

#### Mandatory recovery inputs

- `gameId`;
- `currentPhase` (must equal persisted `gameState`);
- `clockStartedAt`;
- `phaseStartedAt`;
- `clockPaused`;
- `clockTotalPausedMs`;
- `awaitingResultActivation`;
- `resultPhaseStarted`;
- `serverTimestampAtCheckpoint`;
- the exact phase timer definitions from the attached configuration (`configuration.timers`), not silently the current catalog when versions differ.

For exact paused recovery, one of `pauseStartedAt`, persisted `phaseRemainingMs`, or equivalent authoritative elapsed data is missing from the current contract. This must be reported as an architectural gap, not invented in D2.

#### Ordering, idempotency, duplicates, failure

- Requires Game identity, attached Configuration timers, and attached GameState.
- Should be attached in a non-scheduled/armed form first.
- Timer arming must occur only after all candidate engines validate successfully.
- Same exact clock may be idempotent only if no second timeout is scheduled.
- Duplicate conflicting clock must fail closed.
- Failure must clear any newly-created timeout and remove the candidate clock.
- A partially attached running clock is dangerous because it can emit lifecycle events while other engines are absent.

#### D2 recommendation

Use a two-step API or an atomic API with explicit arming control:

```js
attachClock({
    gameId,
    currentPhase,
    startedAt,
    phaseStartedAt,
    paused,
    totalPausedMs,
    awaitingResultActivation,
    resultPhaseStarted,
    serverTimestampAtCheckpoint,
    frozenTimers
}, { arm: false })

armRecoveredClock(gameId)
```

`attachClock` must emit no events. `armRecoveredClock` must refuse expired or terminal-invalid schedules and must not duplicate a timeout.

### 3.4 PhysicsEngine

#### Current state and ownership

`_simulations: Map<gameId, simulation>` owns:

```js
{
    gameId,
    parameters,
    runtime: {
        angle,
        triangleAngle,
        angularVelocity,
        triangleAngularVelocity,
        angularAcceleration,
        state,
        braking,
        selfTestActive,
        speedActive,
        brakeActive,
        brakeDurationMs,
        brakeElapsedMs,
        brakeStartWheelOmega,
        physicsStoppedEmitted,
        simulationTimeMs
    },
    commandLog
}
```

The key is exact `gameId`. The lifecycle is `CREATED -> RUNNING -> BRAKING -> STOPPED -> REMOVED`.

#### Constructor dependencies

- `logger`
- `eventBus`
- `gameClock`
- optional `metricsService`

The current implementation stores `gameClock` but restoration-relevant methods do not read it directly. Configuration is not a direct constructor dependency. Configuration start angles are supplied by `SelfTestPhaseController`. Input is applied by InputAuthority. SimulationLoop calls update.

#### Creation, mutation, teardown

- `createSimulation(gameId, parameters)` creates zero/default `CREATED` state and no events.
- `startSimulation` emits `PHYSICS_STARTED`.
- motion-control methods mutate flags/velocities and generally emit physics updates.
- stop/finalization emits `PHYSICS_STOPPED` exactly once under normal runtime flags.
- `removeSimulation` stops active simulation and removes it.
- shutdown removes all simulations.

#### SimulationLoop separation

Physics state and loop registration are separate:

- PhysicsEngine stores simulation state.
- `SimulationLoop._activeGameIds` is populated only by `PHYSICS_STARTED`.
- one global `setInterval` drives all registered active simulations.
- each tick processes InputAuthority's queue before physics update.

Attaching a simulation with `RUNNING` or `BRAKING` state does not automatically register it with SimulationLoop. Conversely, emitting `PHYSICS_STARTED` during recovery would activate ticking before candidate validation. A controlled SimulationLoop registration capability is therefore a separate dependency and must not be simulated by replaying a normal event during attachment.

#### Getter/snapshot sufficiency

`getSimulation(gameId)` exposes parameters, the major runtime fields, and copied command log. It omits internal `braking` and `physicsStoppedEmitted`. `getDebugSnapshot` is smaller. For terminal recovery, `getSimulation` provides the authoritative final angles and STOPPED state needed by the recovery contract. For exact active recovery, current snapshot/persistence is insufficient.

#### Restore capability

No attach/restore API exists.

`createSimulation` is sufficient only to create a fresh `CREATED` simulation for phases where that state is authoritatively expected. It is not sufficient for terminal STOPPED restoration.

`setPoseDegrees` is not sufficient because it:

- requires an existing simulation;
- accepts degrees while persisted final angles are radians;
- restores only two angles;
- does not restore lifecycle state;
- can emit `PHYSICS_UPDATED` for active state.

Normal `stopSimulation` is unsafe for recovery because it emits `PHYSICS_STOPPED`, causing `WinnerActivation` to start winner resolution/retry flows.

#### Reconstruction feasibility by phase

| Phase | Safe physics reconstruction from current contract? | Reason |
|---|---:|---|
| `PRE_GAME_READY` | Yes, conditional | A new `CREATED` simulation is consistent if configuration/phase validation confirms no motion began. |
| `READY` | Yes, conditional | Same as above; no self-test motion should be active yet. |
| `SELF_TEST` | No | Active angles/velocities and simulation progress are not persisted. |
| `SPEED` | No | Active angles, velocities, held-input state, command history, and tick history are not persisted. |
| `BRAKE` | No | Brake elapsed, start omega, active angles, and velocity state are not persisted. |
| `RESULT` | Yes, terminal only | Current terminal contract requires final wheel angle, final triangle angle, and `STOPPED`. |

The simulation is deterministic for a given command and fixed-step sequence, but the current recovery data does not include active command/step history. Active reconstruction must not be attempted.

#### Mandatory recovery inputs

For fresh pre-motion state:

- `gameId`;
- expected phase (`PRE_GAME_READY`/`READY`);
- default/validated physics parameters;
- configuration identity.

For terminal state:

- `gameId`;
- `physicsFinalAngle` in radians;
- `physicsFinalTriangleAngle` in radians;
- `physicsSimulationState === STOPPED`;
- parameters equal to allowed defaults/approved immutable overrides.

No historical commands should be invented. Terminal command log may safely be empty because it is not used by winner resolution, but it no longer represents historical audit data and must not be presented as a complete replay history.

#### Ordering, idempotency, duplicates, failure

- Requires Game identity and candidate phase classification.
- Terminal physics must be attached before silent winner reconstruction.
- Active loop registration, if ever eligible, occurs after InputAuthority and all validation.
- Same exact terminal state may be idempotent; different angles/state under same `gameId` must fail closed.
- Restore must set `physicsStoppedEmitted` so later cleanup/stop cannot emit a false new stop event.
- Failure after insertion must remove the simulation without calling a normal stop path that emits gameplay events.

#### D2 recommendation

```js
attachSimulation({
    gameId,
    parameters,
    runtime,
    commandLog = []
}, { emitEvents: false })
```

D2 should limit accepted runtime shapes to:

1. validated `CREATED` pre-motion state; or
2. validated terminal `STOPPED` state with finite final angles and zero motion.

It must reject `RUNNING`/`BRAKING` restoration under the current contract.

### 3.5 InputAuthority

#### Current state and ownership

`InputAuthority` owns:

- `_registries: Map<gameId, registry>`;
- `_speedInputClosed: Set<gameId>`.

Each registry owns:

- `players: Map<playerId, playerInputState>`;
- `commandQueue`;
- `acceptedCommands` history;
- monotonic `sequenceNumber`.

Each player state owns press count, held state, timestamps, cooldown, and lock state.

Identity keys are `gameId` and `playerId`. It does not own `playerIndex`.

#### Constructor dependencies

- `logger`
- `eventBus`
- `gameCatalog`
- `playerManager`
- `physicsEngine`
- `gameStateEngine`
- optional `devMode`

#### Accepted command types

Current input actions enqueue:

- `ACCELERATION_START` on press;
- `ACCELERATION_STOP` on release.

SimulationLoop later drains the queue and calls `PhysicsEngine.applyAcceleration`.

#### Creation, mutation, teardown

- `registerPlayer(gameId, playerId)` creates a default state and creates the registry lazily. It does not emit gameplay events.
- `registerPlayers` additionally calls `PlayerManager.setPlayerState(...PLAYING)` for every player.
- button handling mutates state, creates commands, and emits accepted/rejected/cooldown/limit events.
- `removeGame` removes registry and speed-closed flag.
- shutdown clears all state.

#### Getter/snapshot sufficiency

- `getPlayerInputState` exposes each player state.
- `getAcceptedCommands` exposes accepted command history.
- `hasGame` and speed-closed getters exist.
- no getter exposes pending `commandQueue` or `sequenceNumber` as a complete recovery snapshot.

Existing getters are enough to observe default/terminal player registration but not enough for exact active input restoration.

#### Recovery policy

Queued commands must be empty after `SERVER_RESTART` under the current contract. They are not persisted, and replaying unknown or stale commands could alter physics after the checkpoint. Historical accepted commands must not be fabricated.

Registered players can be derived from the already-attached D1 Player aggregates and authoritative Game/Room membership. Recovery should register the same `playerId` set without replaying inputs.

`registerPlayers` is not the preferred restore path because it mutates PlayerManager runtime state to `PLAYING`, expands ownership, and can leave partial registry state if one player registration fails. `registerPlayer` can safely create default entries one at a time, but there is no atomic whole-registry attach/validation method.

#### Phase eligibility

- `PRE_GAME_READY` / `READY`: default player input states and empty queues are safe.
- `SELF_TEST`: default input may be semantically safe, but physics is not reconstructable with current data, so the candidate still fails closed.
- `SPEED` / `BRAKE`: input state is authoritative and missing; must not recover.
- `RESULT`: input registry is not needed for winner/result correctness and may remain absent.

#### Ordering, idempotency, duplicates, failure

- Requires attached Player identities and Game identity.
- For future input acceptance, also requires GameState and Physics to exist.
- Must precede any SimulationLoop activation.
- Duplicate player registration currently returns null; same complete registry is not idempotent as a unit.
- Atomic validation must occur before insertion: exactly expected player IDs, no duplicates, all present in PlayerManager, no commands.
- A partial registry must be removed if any player validation fails.

#### D2 recommendation

```js
attachRegistry({
    gameId,
    playerIds,
    players,              // only validated default states in current D2
    speedInputClosed,
    commandQueue: [],
    acceptedCommands: [],
    sequenceNumber: 0
})
```

For D2, the API should preferably accept only a safe reset/default policy rather than arbitrary active input state. It must not mutate PlayerManager, emit input events, or accept historical commands that are absent from authoritative persistence.

### 3.6 WinnerEngine

#### Current state and ownership

`_results: Map<gameId, frozenResult>` owns:

- winning sector and player;
- `winnerPlayerId`, sector index;
- final wheel/triangle angles;
- resolution timestamp;
- trace seed and configuration version metadata;
- currently-null prize/payout fields.

The key is exact `gameId`.

#### Constructor dependencies

- `logger`
- `eventBus`
- `physicsEngine`
- `configurationEngine`
- `gameCatalog`

#### Creation, mutation, teardown

- `resolveResult(gameId)` deterministically computes from attached configuration and a `STOPPED` physics simulation.
- It is idempotent after a result exists.
- It emits `WINNING_SECTOR_RESOLVED` and `GAME_RESULT_READY`.
- `removeResult` emits `GAME_RESULT_REMOVED`.
- shutdown clears results silently.

#### Getter/snapshot sufficiency

- `getResult(gameId)` returns the complete frozen result and is sufficient for persistence while live.
- `getDebugSnapshot` is incomplete.

The current `RECOVERY_DATA` contract does not persist the full winner result. It optionally references financial `winnerId`, and terminal physics/configuration allow the winner outcome to be recomputed.

#### Restore capability and event safety

No attach/restore API exists.

Calling `resolveResult` during low-level D2 attachment is unsafe because it emits normal gameplay events. `WinnerActivation` and `ResultActivation` consume related events and can start retry/result scheduling. Recovery must not replay historical winner events while the candidate is partially reconstructed.

#### Winner restoration by game class

- Before winner determination: WinnerEngine should safely remain empty. No restore API call is needed.
- `RESULT` with exact configuration and terminal angles: winning sector/player is deterministically recomputable.
- Already-settled game: gameplay runtime generally does not need reconstruction; financial recovery owns settlement continuation.
- If a full persisted winner result is available in the future, it can be attached after validation.

The recomputed winner identity must later match authoritative settlement `winnerId` when present. That cross-domain comparison is outside D2.

`resolvedAt` is not derivable from final angles and is not currently persisted as winner metadata. Recomputing at restore time changes that historical timestamp. Therefore the **outcome** is reconstructable, but the exact historical result object is not. D2 must not claim exact timestamp restoration or invent it silently.

#### Ordering, idempotency, duplicates, failure

- Requires attached Configuration and terminal STOPPED Physics.
- Should occur after GameState/Clock classification proves the game is terminal.
- Same full result may be idempotent; a conflicting result must fail closed.
- Any silent recomputation failure must leave `_results` empty.
- No winner event should be emitted by attachment.

#### D2 recommendation

Two architectural options are safe:

```js
attachResult(result) // when a complete authoritative result exists
```

or:

```js
restoreResult(gameId, { resolvedAt }) // compute silently from config + STOPPED physics
```

The second shape requires an authoritative `resolvedAt` if exact result reconstruction is required. Since that field is absent today, D2 may support silent semantic recomputation but must expose that historical timestamp is unavailable. It must not call the event-emitting `resolveResult` path internally unless emission is explicitly suppressed.

## 4. Current Runtime State Model

### 4.1 Registry model

| Component | Primary key | Secondary key | Runtime registry | Timers/queues |
|---|---|---|---|---|
| ConfigurationEngine | `gameId` | — | configurations + economies | none |
| GameStateEngine | `gameId` | — | state records | history only |
| GameClockEngine | `gameId` | — | clock records | one `setTimeout` per running phase |
| PhysicsEngine | `gameId` | — | simulation records | command log; no own interval |
| InputAuthority | `gameId` | `playerId` | input registries | pending queue + accepted history |
| WinnerEngine | `gameId` | — | frozen results | none |
| SimulationLoop | global | `gameId` membership | active game Set | one global `setInterval` |

### 4.2 Event-driven coupling

Normal lifecycle events are not passive notifications. They activate behavior:

- `CONFIGURATION_READY` can unblock game activation consumers.
- phase-start events cause GameState transitions and physics phase controllers.
- `GAME_STATE_CHANGED(RESULT)` can schedule audit/teardown flows.
- `PHYSICS_STARTED` registers the game in SimulationLoop.
- `PHYSICS_STOPPED` triggers WinnerActivation and retry timers.
- winner events start RESULT and downstream result/settlement flows.

Therefore all D2 attach operations must be silent. Later orchestration may deliberately emit a distinct recovery-complete event after full validation, but D2 must not impersonate normal lifecycle events.

### 4.3 Current persisted recovery model

`RecoveryDataPersistence` validates these engine-relevant fields:

- full configuration + hash/version/trace seed;
- current `gameState` and `gameStatus`;
- active clock fields;
- terminal final physics angles and simulation state;
- full player recovery identity including `playerIndex`.

Important limitations:

1. Production code does not currently create/update recovery records.
2. No current `recovery_data` directory or production record exists.
3. Active physics state is intentionally absent.
4. Active InputAuthority state is absent.
5. full winner result/resolved timestamp is absent.
6. exact paused-clock `pauseStartedAt` or persisted remaining time is absent.
7. historical ConfigurationEngine economy `frozenAt` is absent.

These are data availability facts. D2 must not modify the schema; genuine missing fields are blockers/gaps for the affected recovery classes.

### 5.2 Dependency edges and reasons

| Edge | Why it exists |
|---|---|
| Recovery record -> all components | It supplies authoritative IDs, configuration, state, clock, and terminal physics inputs. |

No direct source dependency requires PhysicsEngine to wait for GameClockEngine during state insertion. Its constructor holds `gameClock`, but current physics restoration-relevant behavior does not read clock state. Candidate consistency still requires clock/state/physics phase agreement.

## 6. Recovery Ordering

### 6.1 Exact recommended ordering

For one recovery candidate:

1. Validate recovery record checksum, versions, required fields, and phase eligibility before any runtime mutation.
2. Construct Room, Player, and Game aggregates without normal creation APIs.
3. `RoomManager.attachRoom(room)`.
4. `PlayerManager.attachPlayer(player)` for each already-constructed Player aggregate.
5. Validate `room.players` order against persisted `playerIndex`; PlayerManager does not own this index.
6. `GameManager.attachGame(game)`.
7. Attach immutable configuration silently and verify configuration hash, `gameId`, `roomId`, player set, version, trace seed, and catalog metadata.
8. Attach GameState silently.
9. Attach GameClock silently and **unarmed**; validate phase/time/expiry.
10. Attach InputAuthority registry only for eligible pre-motion phases, with empty queues/default state. Do not attach active SPEED/BRAKE input.
11. Attach Physics:
    - `CREATED` for eligible pre-motion phase; or
    - terminal `STOPPED` with final angles for RESULT.
12. For RESULT only, silently attach/recompute Winner result after configuration + terminal physics. Do not emit winner events.
13. Validate the complete candidate across room/game/player/configuration/state/clock/input/physics/winner.
14. Only after successful validation, arm an eligible non-expired clock.
15. Do not register SimulationLoop for current safe D2 candidates because active motion phases are not reconstructable from the existing contract.

### 6.2 Why the example order must be corrected

The example `Room -> Game -> Player -> ...` is not ideal. Game carries player IDs, and InputAuthority depends on PlayerManager. The safe source-derived identity order is:

```text
Room -> Players -> Game
```

provided the Room aggregate is constructed with its persisted ordered player list before attachment. Player attach then makes those IDs resolvable, and Game attach follows with both parent room and player identities present.

### 6.3 Atomicity requirement

The current managers/engines do not provide a candidate transaction. D2 APIs must at minimum make each engine attachment atomic. Full multi-component rollback remains orchestration responsibility outside D2.

Until orchestration exists, D2 APIs must not autonomously start timers, simulation, winner resolution, or lifecycle events. This prevents partial runtime state from becoming active.

## 7. Recovery Safety Rules

### 7.1 SAFE TO RECOVER

#### Configuration

Safe only when the complete persisted configuration passes:

- recovery checksum validation;
- dedicated configuration-hash validation;
- ConfigurationEngine structural/catalog validation where compatible;
- exact `gameId` and `metadata.roomId` match;
- exact player set match;
- immutable freeze on attach;
- duplicate-equivalence check.

#### PRE_GAME_READY / READY

Potentially safe when all of the following are true:

- Room/Game/Players attached consistently;
- exact configuration attached;
- state and clock phase match;
- clock is not expired, or remains paused with exactly derivable remaining time;
- Physics is authoritatively `CREATED`/pre-motion;
- Input registry is default and empty;
- no winner exists;
- no normal lifecycle events are emitted during attachment.

#### RESULT terminal reconstruction

Potentially safe when:

- exact configuration exists;
- GameState is RESULT;
- terminal physics is `STOPPED` with finite final angles;
- winner is silently recomputed/attached and later validates against settlement if present;
- no RESULT/winner/physics events are replayed;
- the candidate is not already financially complete such that gameplay runtime is unnecessary.

### 7.2 MUST FAIL CLOSED

- Missing or invalid recovery record.
- Checksum, configuration hash, version, trace seed, gameId, roomId, or player-set mismatch.
- Duplicate registry identity with different state.
- More/fewer than exactly three authoritative players for WheelWin gameplay.
- Duplicate or out-of-range `playerIndex`; index/order mismatch.
- GameState/clock phase mismatch.
- Configuration timers incompatible with persisted timing.
- Unpaused deadline already expired and no approved catch-up policy.
- Paused clock whose exact remaining/elapsed state cannot be derived.
- `SELF_TEST`, `SPEED`, or `BRAKE` candidate under the current contract.
- Active Physics state requested without all authoritative runtime values.
- Non-empty queued commands requested without authoritative persisted queue data.
- RESULT without final angles or without `STOPPED` physics.
- Recomputed winner conflicts with authoritative later-stage financial winner data.
- Any candidate-wide partial attachment that cannot be rolled back before activation.

Fail closed means: no timer armed, no SimulationLoop registration, no gameplay event replay, and no exposure as a playable recovered game.

### 7.3 MUST NOT BE RECOVERED

- Setup-only rooms with no durable recovery anchor.
- Financial-only payment/settlement candidates where gameplay reconstruction is unnecessary.
- Games already destroyed or explicitly `FAILED_CLOSED`.
- Already-settled terminal games solely to recreate transient gameplay.
- Any active game for which authoritative physics/input state is unavailable.
- Any candidate requiring newly generated configuration, IDs, winner, physics values, or historical commands.

### 7.4 Duplicate attachment

For every engine:

- absent key -> validate fully, then attach;
- existing key + byte/semantic-equivalent state -> optional idempotent success returning existing state;
- existing key + any conflict -> fail closed;
- never overwrite silently;
- never schedule a second timeout or register a second loop membership.

### 7.5 Identity mismatch

The following must match exactly before engine mutation:

- recovery `gameId` = Game aggregate = every engine record = configuration `gameId`;
- recovery `roomId` = Game `roomId` = configuration `metadata.roomId` = Room aggregate;
- recovery players = Game players = Room players = Configuration players = InputAuthority players;
- persisted player index = authoritative room/player ordering; PlayerManager is not the index owner.

### 7.6 Missing/corrupted persisted state

Do not fall back to normal creation for an existing authoritative game. Do not generate configuration, start from PRE_GAME_READY, reset inputs, or create fresh physics unless that exact initial state is proven by the persisted phase contract.

### 7.7 Expired clocks

- Do not clamp to zero and leave a running unscheduled clock.
- Do not automatically emit all missed phase events.
- Do not restart the full original duration.
- Return an explicit expired result and leave the clock unarmed.
- Later orchestration decides failure/terminal handling.

### 7.8 Terminal games and resolved winners

- WinnerEngine may start empty only when winner determination had not occurred.
- RESULT requires terminal physics inputs before winner reconstruction.
- Settled games generally require financial recovery only.
- Never resolve the winner twice through normal event paths.
- Existing equivalent winner result is idempotent; conflict is fatal.

### 7.9 Partial reconstruction and stale state

Before retrying a candidate, all components previously attached for that candidate must be removed silently. Normal teardown methods that emit lifecycle events may be inappropriate for rollback. D2 APIs should either expose silent detach/rollback helpers or ensure insertion occurs only after complete local validation.

Candidate activation must be a final separate step. No low-level attach method may make partial state live.

### Existing API sufficiency summary

- **Fully sufficient restoration APIs:** none of the six engines.
- **Partially reusable:**
  - Physics `createSimulation` for proven pre-motion `CREATED` state only.
  - InputAuthority `registerPlayer` for individual default registration, but not atomic candidate restoration.
  - GameClock `restorePhaseSchedule` only for live reconnect; not restart restoration.
  - Winner `resolveResult` is deterministic but event-emitting and therefore not a safe low-level restore API.
- **Creation getters sufficient for persistence:** `ConfigurationEngine.getConfiguration`, `PhysicsEngine.getSimulation` (terminal fields), `WinnerEngine.getResult`. Clock lacks a complete recovery snapshot getter.

## 9. D1 Compatibility

### 9.1 Authoritative D1 APIs

D2 is compatible with and must use the completed D1 identity boundary:

```js
RoomManager.attachRoom(room)
GameManager.attachGame(game)
PlayerManager.attachPlayer(player)
```

The older `attachPlayer(identity, runtime)` shape documented in the initial D1 report is superseded by the correction report and current source.

### 9.2 Player aggregate requirement

`PlayerManager.attachPlayer(player)` requires an already-constructed Player aggregate whose:

- direct `player.playerId` exists;
- `player.identity.playerId` matches it;
- runtime exists;
- supplied identity/runtime objects are preserved;
- supplied `playerIndex` is not changed.

D2 does not need and must not request a PlayerManager API redesign.

### 9.3 playerIndex ownership

D2 does **not** require PlayerManager to own `playerIndex`.

`playerIndex` remains outside PlayerManager's identity/runtime Maps. It is represented by the supplied aggregate and authoritative room/payment seat ordering. D2 uses it only for cross-component validation and ordered registration. No engine except external financial seat mapping requires PlayerManager to store or generate it.

### 9.4 Identity attach versus engine attach

D1 attach APIs intentionally emit no normal creation events and reject duplicates. D2 engine APIs should follow the same pattern: preserve authoritative identity/state, attach silently, reject conflicts, and never call normal create/bootstrap event paths.

## 10. D2 Implementation Boundary

### 10.1 D2 should implement

D2 should be limited to additive runtime-engine capabilities:

1. Silent immutable configuration attachment with hash/identity validation.
2. Silent GameState attachment without transition events.
3. Full clock-state attachment in an unarmed form plus safe explicit arming/expiry result.
4. Physics attachment restricted to proven pre-motion CREATED or terminal STOPPED states.
5. Atomic safe-default InputAuthority registry attachment with empty queues.
6. Silent winner-result attach/recompute support for terminal state, subject to authoritative timestamp/data limits.
7. Duplicate-equivalence and conflict rejection in each engine.
8. Local atomicity/cleanup so failed engine attachment leaves no stale entry or timer.
9. Read-only restoration snapshots/getters where current public APIs do not expose required engine-owned state (especially GameClock).

### 10.2 Explicitly outside D2

- `RecoveryOrchestrator` implementation.
- Restart orchestration or startup sequencing changes.
- Candidate discovery.
- Multi-engine transaction/rollback coordination.
- Recovery record production/checkpoint wiring.
- Persistence schema or snapshot-format changes.
- Financial recovery or financial reconciliation.
- `PaymentSessionManager` changes.
- Blockchain recovery.
- Settlement/refund decisions.
- Reconnect integration.
- Socket/session changes.
- Client changes.
- RoomManager, GameManager, PlayerManager modifications.
- SimulationLoop active-game restoration unless separately approved; current active phases remain unrecoverable.
- New game phases or transition rules.
- Emission of normal gameplay lifecycle events during attachment.

### 10.3 Persistence gaps discovered, not implemented

The audit proves these exact-state gaps:

1. Paused clock lacks `pauseStartedAt` or explicit persisted `phaseRemainingMs`/elapsed equivalent.
2. Winner historical `resolvedAt`/full result is absent.
3. Historical frozen economy timestamp/object is absent.
4. Active SELF_TEST/SPEED/BRAKE physics and input state is absent by design.

No schema change is proposed for implementation in D2. These gaps restrict eligibility. If exact paused-clock or exact winner-object restoration is required, a later architecture decision must amend the recovery data contract before implementation of those cases.

## 11. Risks

### Critical

- **No production recovery records exist or are written.** The persistence API is implemented, but production searches found no record creation/update calls and no active recovery-data directory. D2 APIs can be implemented and unit-tested, but no real restart candidate can currently invoke them. This is a blocker for end-to-end recovery, not for isolated D2 API implementation.
- **Normal lifecycle event replay can activate gameplay/teardown/financial-adjacent flows.** Any restore API that calls current event-emitting creation/mutation methods risks timers, physics ticks, winner resolution, RESULT activation, or teardown before consistency validation.
- **Active motion phases are not reconstructable.** SELF_TEST/SPEED/BRAKE lack authoritative runtime state. Restoring them from defaults would invent state and violate determinism.
- **Partial reconstruction can become live.** A scheduled clock or registered SimulationLoop game can mutate state while other engines are missing.

### High

- **Expired clock deadlock.** Current `restorePhaseSchedule` can leave a running phase with zero remaining and no timeout.
- **RESULT event duplication.** `PHYSICS_STOPPED`/winner/result events can restart resolution or result lifecycle for a terminal game.
- **Configuration validation across catalog changes.** The full configuration persists `metadata.catalogVersion`, but current validation checks current catalog stakes/colors/icons/timer keys. A historically valid immutable configuration could be rejected after incompatible catalog changes. It must never be silently rewritten to pass current validation.
- **Input reset is unsafe for SPEED/BRAKE.** Default input state changes held counts, lock state, and accepted command history.
- **Winner exact object gap.** Outcome can be recomputed, but historical `resolvedAt` cannot.

### Medium

- **Paused-clock exactness gap.** The current contract cannot always reproduce active pause timing exactly.
- **Configuration economy gap.** Configuration can be exact while `_economies` remains absent; deriving from changed payment rules could create inconsistency.
- **Getter asymmetry.** Clock and some internal flags lack complete public recovery snapshots.
- **Rollback methods may emit events.** Existing remove/stop methods are not uniformly silent and are not designed as recovery rollback operations.

### Low

- History/command-log omission does not affect terminal winner recomputation but reduces audit equivalence.
- `GameStateEngine` history can be absent for current transition behavior, but consumers must not interpret a synthetic history as original history.

## 12. Recommendations

1. Implement D2 as silent, additive attach APIs on the existing engine owners; do not create a parallel recovery engine registry.
2. Use strict per-engine prevalidation and duplicate-equivalence checks before mutation.
3. Separate attachment from activation. Clocks remain unarmed and simulations remain unregistered until later orchestration validates the whole candidate.
4. Explicitly reject active SELF_TEST/SPEED/BRAKE restoration with the current contract.
5. Permit only proven pre-motion (`PRE_GAME_READY`/`READY`) or terminal (`RESULT` + STOPPED angles) engine shapes.
6. Do not emit `CONFIGURATION_READY`, `GAME_STATE_CHANGED`, phase events, `PHYSICS_STARTED`, `PHYSICS_STOPPED`, or winner/result events during restoration.
7. Add a complete read-only GameClock recovery snapshot API if later persistence wiring must capture engine-owned fields.
8. Treat expired clocks as an explicit non-armed result, not as a zero-duration timer or restarted phase.
9. Do not derive a new economy from changed catalog rules without later cross-domain validation.
10. Resolve paused-clock and exact winner timestamp requirements at the recovery-contract architecture level before claiming those cases are exactly recoverable.
11. Keep SimulationLoop restoration out of current D2 active behavior; add a controlled membership API only if a future approved data contract makes active physics recovery safe.
12. Preserve D1 exactly, especially `attachPlayer(player)` and external `playerIndex` ownership.

## 13. Proposed Validation Strategy

No tests are created in this audit. A future approved D2 implementation should validate:

### 13.1 Per-engine unit validation

#### Configuration

- exact object/hash survives attach;
- attached object is deeply frozen;
- no random-service call;
- no `CONFIGURATION_READY` event;
- equivalent duplicate is idempotent or explicitly rejected consistently;
- conflicting duplicate/hash/identity/version fails without stale state.

#### GameState

- each valid phase attaches directly;
- invalid phase fails;
- no `GAME_STATE_CHANGED`/rejected event;
- no transition replay;
- timestamp/history policy is explicit;
- conflict leaves original state unchanged.

#### Clock

- full active fields round-trip through a recovery snapshot;
- attachment creates no timeout when `arm:false`;
- arming creates exactly one timeout;
- duplicate arming does not create another timeout;
- expired deadline returns explicit failure and leaves no timeout;
- paused time does not consume downtime where sufficient inputs exist;
- phase/configuration timer mismatch fails;
- removal/rollback clears timeout.

#### Physics

- pre-motion CREATED attach succeeds without events;
- terminal STOPPED angles attach exactly in radians;
- terminal velocities/acceleration are zero;
- stop-emitted guard prevents duplicate `PHYSICS_STOPPED`;
- RUNNING/BRAKING attach is rejected under current contract;
- no SimulationLoop membership is created implicitly.

#### InputAuthority

- exactly three attached players registered;
- no PlayerManager mutation;
- queues/history empty and sequence zero;
- unknown/duplicate player fails atomically;
- SPEED/BRAKE arbitrary state rejected;
- no input events emitted.

#### Winner

- no result required for pre-result state;
- terminal result resolves identically from config + angles;
- no winner/result events emitted;
- duplicate equivalent result safe;
- conflicting winner rejected;
- missing historical timestamp is surfaced rather than hidden.

### 13.2 Cross-engine validation

- same `gameId` in all registries;
- configuration room/player identity matches D1 aggregates;
- GameState phase equals clock phase;
- phase-specific physics eligibility enforced;
- InputAuthority exists only where safe and contains the Game's player set;
- terminal Winner matches terminal Physics and Configuration;
- no timers/loop membership before final validation;
- failed candidate leaves all D2 engine registries clean.

### 13.3 Event isolation validation

Subscribe counters to all normal lifecycle events and assert zero emissions during attachment:

- configuration ready/removed;
- game state changed/rejected;
- clock/phase started/completed/timeout;
- physics started/updated/braking/stopped;
- input accepted/rejected;
- winner/result ready/removed.

### 13.4 Failure-injection validation

Inject failure at every ordering step and verify:

- no armed timeout;
- no SimulationLoop registration;
- no stale engine entry for the failed candidate;
- already-existing unrelated games are unchanged;
- retry cannot duplicate registration.

### 13.5 End-to-end limitation

End-to-end restart validation is blocked until a later stage writes production `RECOVERY_DATA` records and implements orchestration. D2 validation should remain focused on engine APIs and cross-engine restoration fixtures, without modifying production persistence or startup wiring.

## 14. Final Verdict

### 14.1 Existing APIs already sufficient

No audited engine currently exposes a fully sufficient SERVER_RESTART restoration API.

Limited reuse is possible:

- `PhysicsEngine.createSimulation` is sufficient only for a proven pre-motion `CREATED` simulation.
- `InputAuthority.registerPlayer` can create one default entry but is not atomic whole-game restoration.
- `WinnerEngine.resolveResult` is deterministically correct given exact Configuration + STOPPED Physics, but it emits normal events and cannot restore the exact historical timestamp.
- `GameClockEngine.restorePhaseSchedule` is live-clock-only and unsafe for expired restart schedules.

### 14.2 Missing APIs

Missing required capabilities are:

1. `ConfigurationEngine` silent immutable attach.
2. `GameStateEngine` silent state attach.
3. `GameClockEngine` full clock attach + delayed safe arming.
4. `PhysicsEngine` restricted silent simulation attach.
5. `InputAuthority` atomic safe-default registry attach.
6. `WinnerEngine` silent result attach/recompute.

SimulationLoop also lacks controlled per-game recovery registration, but current safe D2 must not resume active motion, so that capability is not required for the initially recoverable phase set.

### 14.3 APIs D2 should add

Architectural recommendation only:

```js
ConfigurationEngine.attachConfiguration(...)
GameStateEngine.attachState(...)
GameClockEngine.attachClock(..., { arm: false })
GameClockEngine.armRecoveredClock(gameId)
PhysicsEngine.attachSimulation(..., { emitEvents: false })
InputAuthority.attachRegistry(...)
WinnerEngine.attachResult(...) // or silent restoreResult(...)
```

All must be additive, owner-local, silent, duplicate-safe, and fail closed.

### 14.4 Exact recovery ordering

```text
Validate persisted candidate
  -> attach Room
  -> attach Player aggregates with attachPlayer(player)
  -> validate external playerIndex/order
  -> attach Game
  -> attach Configuration
  -> attach GameState
  -> attach Clock unarmed
  -> attach InputAuthority where eligible
  -> attach Physics
  -> attach/recompute Winner for terminal RESULT only
  -> validate complete candidate
  -> arm eligible non-expired Clock
  -> no SimulationLoop registration under current active-state limitations
```

### 14.5 Blockers before implementation/use

#### Blockers to safe active-game restoration

- SELF_TEST/SPEED/BRAKE physics state is not persisted.
- SPEED/BRAKE input state is not persisted.
- deterministic replay inputs are unavailable.

These phases must remain unrecoverable.

#### Data blockers for exact special cases

- exact paused-clock state lacks `pauseStartedAt` or explicit remaining/elapsed equivalent;
- exact historical winner object lacks `resolvedAt`/full result;
- exact ConfigurationEngine economy object is not persisted.

#### Blocker to end-to-end restart recovery

- `RecoveryDataPersistence` has no production write/update wiring and no production records currently exist.
- Recovery orchestration is intentionally outside D2 and not implemented.

### 14.6 Overall verdict

**D2 is feasible as a controlled engine-API stage, but not as end-to-end recovery.**

The safe initial restoration set is limited to:

- exact immutable configuration;
- silent GameState;
- non-expired, exactly reconstructable clock state;
- pre-motion CREATED physics/default input for `PRE_GAME_READY` or `READY`;
- terminal STOPPED physics and silently reconstructed winner for eligible `RESULT` candidates.

`SELF_TEST`, `SPEED`, and `BRAKE` must fail closed with the current recovery data contract. No normal gameplay event may be replayed during D2 attachment. D1 remains compatible and unchanged, with `PlayerManager.attachPlayer(player)` authoritative and `playerIndex` outside PlayerManager ownership.
