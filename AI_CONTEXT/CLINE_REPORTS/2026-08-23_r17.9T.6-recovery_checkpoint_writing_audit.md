## 3. Architecture Findings

### 3.1 Current Recovery Data Contract (source-verified)

Record type: `RECOVERY_DATA` ("recovery_data"), storage category `active` → `server/data/ton-financial/active/recovery_data/`. Record ID resolution: `metadata.recoveryRecordId ?? payload.recoveryRecordId ?? metadata.gameId ?? payload.gameId` — i.e., **the record ID is conventionally the gameId**, so one record per game.

**Allowed payload fields** (validated by `RecoveryDataPersistence._validateRecoveryPayload` / `validateRecoveryRecord`):

| Group | Fields | Required |
|---|---|---|
| Versioning | `recoveryContractVersion` (=1), `schemaVersion` (=1) | always |
| Identity | `recoveryRecordId`, `roomId`, `gameId`, `contractId`, `paymentSessionId`, `tonNetwork` (+ optional `correlationId`) | always |
| Configuration | `configuration` (full frozen object), `configurationHash` (SHA-256 over stableStringify), `configurationVersion`, `traceSeed`, `snapshotHash` | always |
| Gameplay state | `gameState`, `gameStatus`, `serverTimestampAtCheckpoint` | always |
| Players | `players[]`: `playerId`, `playerIndex`, `wallet`, `nickname`, `baseStake`, `sectorCount`, `color`, `colorSector2`, `icon`, `sectorArrangement`, `age` | always |
| Clock state | `phaseStartedAt`, `clockStartedAt`, `clockPaused`, `clockTotalPausedMs`, `awaitingResultActivation`, `resultPhaseStarted` | non-terminal records only |
| Terminal physics | `physicsFinalAngle`, `physicsFinalTriangleAngle`, `physicsSimulationState` | terminal-status records only |

Forbidden (structural rejection): `paymentStatus`, `paidAmount`, `confirmationStatus`, `refundTxHash`, `settlementTransactionHash`, `prizeAmount`, `organizerAmount`, `totalPot`, `requiredGram`.

Unknown compatible fields are preserved (forward compatibility).

**Immutable fields:** identity block, configuration block, configurationHash, traceSeed, snapshotHash, players[] content, recoveryContractVersion/schemaVersion. These are set once at creation and never legitimately change during a game's life.

**Mutable fields:** `gameState`, `gameStatus`, `serverTimestampAtCheckpoint`, clock-state fields, terminal-physics fields (set once when the game reaches STOPPED), envelope `status` (ACTIVE → TERMINAL/SETTLED/FAILED_CLOSED via metadata override).

**Create semantics:** full validation first; delegates to `TonFinancialPersistence.create()` which throws `DuplicateRecordError` if the record key already exists. No upsert exists.

**Update semantics:** re-validates payload; loads existing; throws `ImmutableRecordError` if existing envelope status ∈ {TERMINAL, SETTLED, FAILED_CLOSED}; supports optimistic concurrency via `metadata.expectedVersion` (throws `VersionMismatchError`); replaces payload wholesale, recomputes checksum, bumps version, updates `updatedAt`; single atomic file rewrite.

**Duplicate behavior:** create-on-existing → error (no silent overwrite). Update-on-terminal → error. There is no "newer-phase-wins" guard inside persistence — ordering discipline is the caller's responsibility (see §16).

**Validation:** checksum (SHA-256 of stableStringify(payload)) verified on load/list; configurationHash recomputed and compared; version compatibility enforced both directions (write-time throw, load-time CorruptedRecordError); invalid records skipped-and-logged by `listRecoveryRecords()` (per-record fail-closed, not server-wide).

**Atomicity:** `_writeJsonAtomic(filePath, value)` = `writeFileSync(tempPath)` + `renameSync(tempPath, filePath)`. Temp name includes pid+timestamp. **No fsync of file or directory.** On POSIX rename is atomic within a filesystem; on Windows (dev environment) `renameSync` over an existing file can fail but Node maps it to an overwrite-rename where supported. Crash between writeFileSync completion and rename leaves an orphan `.tmp` file and the previous record intact — partial writes cannot corrupt the target JSON. Crash mid-writeFileSync leaves only the temp file damaged. **Conclusion: record-level atomicity is sufficient for checkpoint use; durability (fsync) is not guaranteed against OS-level power loss — same guarantee level as all existing financial records, so no regression.**

**Synchronous:** all writes are synchronous (`writeFileSync`/`renameSync`). A checkpoint call blocks its calling stack for local-disk latency (milliseconds-scale). No async queue, no batching.

**Deletion:** `RECOVERY_DATA` is NOT in `DELETABLE_RECORD_TYPES` → `deleteRecord` throws. Recovery records persist until they reach a terminal status; they are never removed by the persistence layer.

**Manifest/checkpoint behavior:** every create/update/delete triggers `_maybeCheckpoint` → rewrites `manifest.json` atomically (record counts/index sizes/timestamp only — not record data). `shutdown({ checkpoint: true })` writes one final manifest. Manifest writes do not affect record integrity.

## 5. Authoritative Checkpoint Moments (lifecycle evidence)

Verified lifecycle chain:

```
entry payment completed
  → GameManager bootstrap: buildConfiguration(...) [frozen] → freezeEconomy(gameId)
  → GameManager._emit(GAME_INITIALIZED)            ← configuration committed BEFORE this emission
  → GameClockEngine.startClock → PRE_GAME_READY phase-started event
  → GameplayPhaseLifecycle._handlePhaseStarted → gameStateEngine.transition(PRE_GAME_READY)
      (mutates _states FIRST, then emits GAME_STATE_CHANGED)
  → ... READY ... SELF_TEST ... SPEED ... BRAKE (same pattern)
  → physics reaches STOPPED → PHYSICS_STOPPED
  → WinnerActivation: winnerEngine.resolveResult(gameId) (retry-bounded) → WINNER_DETERMINED
  → RESULT phase-started → gameStateEngine.transition(RESULT) → GAME_STATE_CHANGED(RESULT)
  → RESULT_COMPLETED → GameplayPhaseLifecycle emits GAME_RESULT_READY
  → settlement (financial domain, separate records)
```

Evaluation of candidate moments:

| Moment | Checkpoint? | Evidence-based reason |
|---|---|---|
| room/game initialization (pre-GAME_INITIALIZED) | NO | no financial obligation yet; synthesis classifies as discard-safe; contract requires contractId/paymentSessionId which may not exist |
| GAME_INITIALIZED | NO as separate checkpoint | configuration just committed but `gameState` is still pre-PRE_GAME_READY; the PRE_GAME_READY checkpoint moments later captures everything including configuration |
| transition into PRE_GAME_READY | **YES — CREATE** | first moment where all required contract groups exist simultaneously: identity (contract/payment session created earlier), frozen configuration, gameState=PRE_GAME_READY, clock running unpaused, CREATED physics, default input registry |
| transition into READY | **YES — UPDATE** | last recoverable active phase boundary; still CREATED physics, no motion; cheap update of mutable group only |
| transition into SELF_TEST | NO | self-test motion makes physics RUNNING → unrecoverable under contract; checkpointing it would create a record that RecoveryOrchestrator must fail closed anyway |
| SPEED / BRAKE | NO | active physics/input absent by design; fail-closed domain (synthesis §14, D2 §11) |
| winner resolution (WINNER_DETERMINED) | NO as trigger | RESULT state not yet entered; premature |
| transition into RESULT | **YES — UPDATE to terminal** | at this point physics is STOPPED with final angles, winner resolvable; this is the last gameplay-domain moment before settlement |
| settlement | NO gameplay checkpoint | financial domain owns SETTLEMENT records; gameplay record should already be terminal |
| terminal game completion / OPEN_PAGE6 | covered by RESULT update | nothing new to persist |
| graceful shutdown | see §20 | recommendation: not required |

**Minimal checkpoint policy: CREATE once at PRE_GAME_READY entry; UPDATE at READY entry; UPDATE once more at RESULT entry (optionally marking the record terminal). Three writes per game maximum. No periodic checkpointing, no per-tick writes, no checkpoints in SELF_TEST/SPEED/BRAKE.**

Timing direction: checkpoint AFTER the safe transition completes (post-transition), never before a dangerous transition. Rationale: a checkpoint written before a transition describes a state the server may never reach (crash between write and transition would resurrect a stale phase); writing after a completed transition means the record always describes a state the server actually attained. The unavoidable residual window (crash between transition and checkpoint) is analyzed in §18.

## 6. Checkpoint State Consistency

Question: can a checkpoint assembled from the nine components be guaranteed internally consistent?

Source-derived facts:

1. All mutations are synchronous on the single Node thread. No concurrent writers within one process.
2. `GameStateEngine.transition` mutates `_states` (currentState, enteredAt, history) **before** emitting `GAME_STATE_CHANGED`. A listener on `GAME_STATE_CHANGED` therefore observes post-transition GameStateEngine state — good.
3. However, the transition is triggered by a *phase-started* event from GameClockEngine (already mutated), while other components mutate in *other* handlers of the *same* event fan-out: e.g., SelfTestPhaseController/SpeedActivation drive physics commands; subscription order determines whether a checkpoint listener attached to `GAME_STATE_CHANGED` sees physics already started (SELF_TEST/SPEED) or not yet. EventBus handler order is subscription order — fragile coupling.
4. For the APPROVED phases this hazard does not materialize:
   - PRE_GAME_READY / READY: physics remains CREATED (zero motion) throughout; no controller mutates physics at these boundaries in a way that affects the persisted shape (CREATED shape is constant defaults). Clock is already mutated (phase-started preceded the transition). Input registry is default-empty. Therefore a snapshot taken in a `GAME_STATE_CHANGED(PRE_GAME_READY|READY)` handler is coherent regardless of subscription order.
   - RESULT: physics reached STOPPED earlier (PHYSICS_STOPPED → WinnerActivation → WINNER_DETERMINED precede the RESULT transition, since BRAKE must complete before RESULT phase starts). At `GAME_STATE_CHANGED(RESULT)` the winner result exists (or is being retried by WinnerActivation — see caveat below), physics is terminal, clock is irrelevant for terminal records. Coherent.
   - Caveat (RESULT): WinnerActivation uses bounded retries; if resolution is deferred, `winnerId` may be unavailable at the instant of the RESULT transition. Mitigation without schema change: read `WinnerEngine.getResult(gameId)` at checkpoint time; if null, persist `winnerId: null` (the orchestrator already treats null winnerId as "outcome stands unvalidated", D3 audit §9). Alternatively trigger the RESULT checkpoint on `WINNING_SECTOR_RESOLVED`/`GAME_RESULT_READY` instead of the state transition — see §7.
5. There IS an existing post-transition lifecycle boundary where all mutations are complete: the synchronous tail of the `GAME_STATE_CHANGED` emission for the three approved phases (and, for RESULT, `GAME_RESULT_READY` as an even-later alternative).

**Verdict: consistency is achievable at the proposed points WITHOUT locking or transactions, because the approved phases have no interleaved physics/input mutations. The general hazard exists only for SELF_TEST/SPEED/BRAKE — which are excluded from checkpointing by design.**

## 7. Event-Based vs Direct Checkpointing

| Option | Assessment |
|---|---|
| A. Direct calls inside lifecycle transition code (GameplayPhaseLifecycle / controllers) | Couples recovery persistence into gameplay orchestration; spreads recovery logic across controllers; hard to test in isolation; violates "no recovery logic leaking into gameplay engines". Rejected. |
| B. Checkpoint from an existing authoritative event (subscribe to GAME_STATE_CHANGED) | Zero gameplay-code changes; single subscriber; sees post-transition state (§6). Risk: receives ALL state changes incl. SELF_TEST/SPEED/BRAKE (filter internally); duplicate-event exposure if lifecycle ever re-emits. |
| C. Checkpoint from post-transition lifecycle events only (phase-started/completed) | Same as B but earlier in the chain — clock mutated, GameState possibly NOT yet transitioned (GameplayPhaseLifecycle handles phase-started asynchronously in subscription order). Inconsistent snapshot risk. Worse than B. |
| D. Centralized RecoveryCheckpointManager subscribing to authoritative lifecycle events | Same mechanism as B plus a named owner: one class owns assembly + validation + create/update policy + failure handling. Preserves server authority (reads authoritative registries), minimal coupling (event subscription only), testable in isolation, single place preventing duplicates, zero financial side effects, zero leakage into engines. |
| E. Explicit checkpoint call from the authoritative state owner (GameManager) | Makes GameManager depend on persistence; mixes lifecycle ownership with recovery I/O; larger blast radius; rejected. |

**Recommendation: Option D — a new `RecoveryCheckpointManager` (single file) that subscribes to `GAME_STATE_CHANGED` (and optionally `GAME_RESULT_READY` for the terminal write), filters to the approved phase set, assembles the payload from authoritative getters, and calls `RecoveryDataPersistence.create/update`.** This mirrors how GameplayPhaseLifecycle itself consumes lifecycle events without owning engine state, keeps RecoveryDataPersistence untouched, and adds no events, no hooks, no schema changes.

## 10. Clock Checkpoint Semantics

- `phaseStartedAt` + catalog/config timers ⇒ `phaseEndsAt = phaseStartedAt + durationMs(phase)`; remaining derived relative to `serverTimestampAtCheckpoint`. Sufficient for unpaused clocks — this is exactly what D2 `attachClock` validates and what the orchestrator's EXPIRED predicate uses.
- `serverTimestampAtCheckpoint` is writer-authoritative (Date.now() at assembly) and required.
- Remaining duration is DERIVED, never stored (no such field).
- Expiration calculation: `phaseStartedAt + durationMs <= serverTimestampAtCheckpoint` (classification) and wall-clock at arm time.
- `clockPaused`: persisted boolean. **Blocker (pre-existing, confirmed): the contract has NO `pauseStartedAt` and no pause history.** If a clock is paused at checkpoint time, exact resume timing cannot be reconstructed; D2 `armRecoveredClock` refuses paused clocks; orchestrator classifies paused candidates NOT_RECOVERABLE. Consequence for the writer: **if `clockPaused === true` at an approved checkpoint moment, the writer MUST NOT produce a record that pretends resumability** — options: (a) skip the checkpoint entirely (game becomes unrecoverable — acceptable, matches current ephemeral behavior), or (b) write it anyway knowing recovery will fail closed. Recommendation: (a) skip — avoids persisting misleading state; no invention of pause history. Note: in current production flow, do clocks pause during PRE_GAME_READY/READY? Pause APIs exist (CLOCK_PAUSED/RESUMED events) but the approved phases are short; the writer must handle the case defensively regardless.
- Armed timer recreation: deterministic via `armRecoveredClock` (exactly one setTimeout) — already implemented and tested; no writer involvement.

## 11. Physics Checkpoint Semantics

- PRE_GAME_READY / READY: simulation state CREATED, all angles/velocities/acceleration zero. Fully derivable constants — the writer can assemble the CREATED runtime shape from `DEFAULT_PHYSICS_PARAMETERS` + zeroed fields, or read the live simulation (preferred: read live `PhysicsEngine` getter to assert state === CREATED and capture actual zeros). Either way the persisted shape is exactly what D2 `attachSimulation` accepts.
- RESULT: state STOPPED, finite `angle`/`triangleAngle`, terminal velocities/acceleration zero. These are the authoritative inputs to `restoreResult`. Writer must read them from the live simulation at RESULT time and assert STOPPED.
- Velocity/angular velocity/active motion: NOT persisted for approved phases (CREATED zeros are implicit; STOPPED zeros validated by attach). Derived/transient.
- D2 restrictions (CREATED|STOPPED only) are sufficient and must not be expanded. No recovery into active SPEED/BRAKE.

## 12. Input Checkpoint Semantics

For the approved set, InputAuthority needs NO persisted input state:
- PRE_GAME_READY/READY: registry is the default shape (empty queue, empty history, sequenceNumber 0, default per-player states) — fully reconstructable via `attachRegistry` with `commandQueue: [], acceptedCommands: [], sequenceNumber: 0`. The writer persists nothing input-specific because the contract has no input fields — correctly so.
- RESULT: no input registry attached at all (orchestrator skips steps 12–13 for terminal candidates).
- Command replay: not needed and not possible (queues empty at these boundaries anyway; no command history invented).
- Verification duty of the writer: assert the live registry is in default shape (or simply rely on the fact that no input can have been processed before SELF_TEST). Defensive assertion recommended, not mandatory.

## 13. Winner / Result Checkpoint

WinnerEngine state becomes authoritative at `WinnerActivation`'s successful `resolveResult` (emits WINNER_DETERMINED), which occurs after PHYSICS_STOPPED and before/at the RESULT transition window.

For the RESULT checkpoint:
- winnerId: from `WinnerEngine.getResult(gameId)` — may be null if activation retry is still pending at the transition instant.
- final angles: from STOPPED physics (authoritative source of truth; winner is recomputable from them).
- terminal physics: asserted STOPPED.
- result status: implied by gameState=RESULT + gameStatus.
- resolvedAt: not in contract; not invented.

Checkpoint timing choice:
- After WinnerEngine resolution AND after all terminal state is stable = at/after `GAME_RESULT_READY` (GameplayPhaseLifecycle, emitted on RESULT_COMPLETED) — strictly safest: winner definitely resolved, physics stopped, state RESULT.
- After ResultActivation concerns: ResultActivation consumes GAME_RESULT_READY for client delivery; checkpointing on the same event is read-only and causes no settlement (settlement is a separate financial flow consuming winner/settlement events, not recovery-record writes).

**The checkpoint must never cause settlement — guaranteed structurally: RecoveryDataPersistence writes JSON files only; no financial code reads RECOVERY_DATA.** Recommended trigger: subscribe to BOTH `GAME_STATE_CHANGED` (for PRE_GAME_READY/READY create/update) and `GAME_RESULT_READY` (for the terminal RESULT update), filtering by phase. Using GAME_RESULT_READY for RESULT eliminates the WinnerActivation-retry race identified in §6.

## 14. Financial References

Population sources at gameplay time:
- `contractId`, `snapshotHash`, `contractAddress`: GameContractManager contract for the room/game (created during payment phase, restored by financial recovery).
- `paymentSessionId`: PaymentSessionManager session for the room.
- `tonNetwork`: contract/session envelope.
- `winnerId`: WinnerEngine (gameplay-side, used as validation reference only).

These are available from in-memory financial managers during live gameplay (they were created before GAME_INITIALIZED). The checkpoint writer reads them as references. It MUST NOT and (by structural validation) CANNOT persist: computed settlement amounts, payout truth, organizer amount, winner payment amount, payment confirmation truth, blockchain-derived status — all are in FORBIDDEN_FINANCIAL_AUTHORITY_FIELDS and rejected at write time. The writer never becomes financial authority: it performs zero TonFinancialPersistence financial-type writes; its only persistence interaction is the RECOVERY_DATA record.

## 15. Write Atomicity (summary)

See §3.1. Record writes: temp-file + renameSync, synchronous, no fsync. Partial-write protection: effective (target file never partially visible). Update atomicity: whole-envelope rewrite. Crash behavior: worst case orphan `.tmp` + previous version intact. Concurrent writers: single-process synchronous design; no cross-process locking — only one server instance may own the data directory (existing assumption for financial records, unchanged). Atomicity is SUFFICIENT for authoritative checkpoints; durability against power loss is equivalent to the existing financial records (accepted project-wide baseline). Insufficient-for-purpose issues: none.

## 16. Duplicate / Idempotency

| Scenario | Behavior with existing create/update semantics |
|---|---|
| same game, same phase, second event | create → DuplicateRecordError; correct handling = catch and convert to update (or track created-state in manager memory). Manager must implement create-or-update idempotency locally. |
| same game, newer phase | update succeeds (ACTIVE record); monotonic phase order enforced by writer (only advance forward through PRE_GAME_READY→READY→RESULT; reject/regress-ignore older phases) |
| same game, older phase | writer-side guard: ignore (never regress gameState). Persistence alone would accept it — caller discipline required. Optional extra safety: compare candidate phase rank vs persisted gameState before update. |
| same timestamp | harmless; update rewrites with new checksum/version |
| crash immediately after write | record reflects last completed transition; see §18 |
| duplicate lifecycle event | create-or-update idempotency + forward-only guard make repeats harmless |
| repeated RESULT checkpoint | second update attempt on a terminal-marked record → ImmutableRecordError; writer must treat "already terminal with same content" as success (idempotent) — check-before-write using loadRecoveryRecord |

Existing semantics are SUFFICIENT provided the writer implements: (1) create-or-update, (2) forward-only phase guard, (3) terminal-idempotency. No new persistence statuses, no persistence modification.

## 17. Failure Policy

Derived from WheelWin architecture (fail-closed recovery, financial truth precedence, gameplay continuity priority):

| Case | Correct behavior |
|---|---|
| A. checkpoint creation failure (PRE_GAME_READY) | log error, continue gameplay. The game is simply not recoverable after restart — identical to today's universal condition. NEVER block or roll back live gameplay for a recovery-writing problem: gameplay correctness serves 3 live paying players now; the record only serves a hypothetical restart. |
| B. checkpoint update failure (READY/RESULT) | same: log and continue. Previous checkpoint (if any) remains valid and describes an earlier attainable state — RecoveryOrchestrator handles stale-but-valid records (expired-deadline detection etc.). |
| C. filesystem unavailable | persistence layer throws StorageUnavailableError-family; writer logs and continues. NOTE: if the filesystem is down, financial persistence is equally affected — that is an existing operational concern outside this stage's scope. |
| D. malformed state encountered during assembly | abort THIS checkpoint (log), continue gameplay. Never persist a partially assembled payload — validation would reject it anyway; failing before the write is cleaner. |
| E. validation failure (payload rejected) | same as D — log the validation errors; this indicates a writer bug, not a gameplay fault. |
| F. duplicate conflict | handled per §16 (idempotent success paths); unexpected conflicts logged. |
| G. crash after transition, before checkpoint | record shows previous phase (or none). Recovery outcome: PRE_GAME_READY record + server restarted during READY ⇒ orchestrator sees EXPIRED or phase-mismatch and fails closed for that candidate; financial recovery proceeds. Unavoidable window — see §18. |
| H. crash immediately after checkpoint | record exactly matches last transition; best case. |

**Policy: LOG AND CONTINUE, always. Never block gameplay, never roll back gameplay, never fail the server, never mark games degraded (no such mechanism exists and adding one is out of scope). Reliability comes from the small number of well-chosen checkpoints, not from write-criticality.** This mirrors the R17.9T.6-B rollback/fail-closed statement: "If persistence fails, the game continues in-memory; lack of a record means not recoverable — acceptable, it is the current behavior."

## 18. Crash Consistency Analysis

| Case | Timeline | RecoveryOrchestrator reconstruction after restart |
|---|---|---|
| A | transition → checkpoint OK → crash | Record matches reality. PRE_GAME_READY/READY: recovered if unexpired/unpaused; RESULT: terminal recovery. Best case. |
| B | transition → checkpoint FAILS → crash | Record shows previous phase (READY record while game actually entered... e.g., crashed during SELF_TEST). Orchestrator classifies from RECORD: READY ⇒ attempts recovery of a game whose true state was SELF_TEST. Is this safe? The reconstructed READY game resumes its READY clock; on expiry it advances normally into SELF_TEST — a legitimate forward path, NOT invented state (the game genuinely was past READY). Residual risk: input/press history between READY-checkpoint and crash is lost — but no input is processed before SELF_TEST ends, so for READY→SELF_TEST the loss is nil. For a RESULT-checkpoint failure the record stays READY ⇒ expiry-driven forward replay would re-run SELF_TEST/SPEED/BRAKE with lost input history ⇒ WRONG outcome possible. Mitigation without schema change: the READY checkpoint is only safe while the game can still be considered "at READY" — i.e., the dangerous case is precisely the missing RESULT checkpoint. Acceptance: this is the unavoidable recovery window; the alternative (blocking gameplay on checkpoint success) violates §17. Document explicitly. |
| C | transition → crash BEFORE checkpoint | No record (PRE_GAME_READY case) ⇒ not recoverable, financial-only. Or stale record as in B. Same window. |
| D | RESULT → checkpoint OK → settlement later → crash | Terminal record present; settlement record present/absent per financial recovery; orchestrator recovers RESULT terminally; financial reconciliation (later stage) cross-checks SETTLEMENT.winnerId. Sound. |
| E | RESULT → settlement begins → checkpoint ABSENT | No gameplay record ⇒ gameplay side unrecoverable; SETTLEMENT record carries winnerId/traceSeed for financial continuation; escrow resolution proceeds financially. Game outcome preserved financially even though gameplay runtime is lost. Acceptable degradation consistent with hybrid architecture. |

**Unavoidable recovery window: the gap between a gameplay transition and its checkpoint write (synchronous, sub-millisecond, but nonzero), plus the RESULT-checkpoint-failure case in B.** Minimized by checkpointing immediately in the event-handler tail (§6/§7). Cannot be eliminated without transactional gameplay-persistence coupling, which the architecture forbids. No state invention to paper over it.

## 19. Retention / Cleanup

Current lifecycle facts: RECOVERY_DATA records are never deletable (not in DELETABLE_RECORD_TYPES); terminal statuses (TERMINAL/SETTLED/FAILED_CLOSED) make records immutable; `listActiveRecoveryDataRecords` excludes terminal envelopes from discovery; orchestrator additionally skips ALREADY_TERMINAL (gameStatus FINISHED/DESTROYED) and FINANCIAL_ONLY classes.

Recommended retention policy (no changes now):
- ACTIVE from PRE_GAME_READY creation until game terminal.
- UPDATE at READY, UPDATE(+optional terminal status mark) at RESULT.
- Settled games: marking the record SETTLED (via update metadata.status) is clean — freezes it immutably and removes it from active discovery; leaving it ACTIVE is also safe (skipped by classification). Prefer marking terminal at RESULT-checkpoint time OR at settlement-completion observation; simplest: mark TERMINAL at the RESULT checkpoint (status override in metadata) — the record's purpose (terminal reconstruction) is fulfilled and immutability protects it. Note: marking TERMINAL at RESULT means the REQUIRED_TERMINAL_PHYSICS_FIELDS become mandatory — which the RESULT checkpoint satisfies by definition. Consistent.
- Cancelled/expired: remain as-is; financial recovery and orchestrator classification handle them; no deletion path exists or is needed.

## 20. Shutdown Checkpointing

Facts: `financialPersistence.shutdown({ checkpoint: true })` writes only the manifest. All nine components destroy state on SERVER_SHUTDOWN without persisting. The startup audit (§16) stated the sequencing rule: any future checkpoint writing must complete before financial persistence shutdown.

Analysis:
- Necessary? NO. Every approved-phase game already has a current checkpoint from its last transition (written synchronously at the transition). A shutdown-time write would only re-persist identical data. The only incremental value would be capturing transitions that occurred without checkpoints — but by design there are none in the approved set (SELF_TEST/SPEED/BRAKE are deliberately not checkpointed, and a shutdown checkpoint must not sneak them in).
- Redundant? YES for the approved policy.
- Dangerous? Potentially: shutdown handlers run during teardown; assembling state mid-teardown risks reading half-destroyed registries; a slow/hanging disk write would delay shutdown; and a shutdown checkpoint of a game sitting in SPEED/BRAKE would either be skipped (correct) or tempt scope creep into persisting active state (forbidden).
- Dependent on future checkpoint writer? Only in sequencing (writer must flush before financial shutdown — trivially satisfied since all writes are synchronous and happen at transition time, long before shutdown).
- Required before financial persistence shutdown? Nothing to flush; no.

**Recommendation: do NOT implement shutdown checkpointing. Transition-time synchronous checkpointing fully covers graceful shutdown.** The startup-audit sequencing rule is satisfied vacuously.

## 21. Proposed Future Architecture

**Recommendation: ONE new file — `server/recovery/RecoveryCheckpointManager.js` (Option D).**

Responsibilities:
1. Subscribe to `EVENT_TYPES.GAME_STATE_CHANGED` and `EVENT_TYPES.GAME_RESULT_READY` (existing events; no new events).
2. Filter to approved phases: PRE_GAME_READY (create), READY (update), RESULT (update, via GAME_RESULT_READY preferred / GAME_STATE_CHANGED fallback).
3. Assemble the payload exclusively from authoritative getters (RoomManager, PlayerManager, GameManager, ConfigurationEngine, GameClockEngine, PhysicsEngine, WinnerEngine, GameContractManager/PaymentSessionManager references).
4. Enforce guards: forward-only phase progression, clock-not-paused (skip otherwise), physics-shape assertions (CREATED for pre-game, STOPPED for RESULT), create-or-update idempotency, terminal-idempotency.
5. Call `RecoveryDataPersistence.createRecoveryRecord` / `updateRecoveryRecord` (metadata.status TERMINAL for RESULT).
6. Failure policy: catch-all → structured error log → continue (never throw into the EventBus).

Why this preserves the architecture:
- Server authority: reads only authoritative owners; persists their state verbatim.
- Determinism: no random service, no regeneration; configuration persisted frozen.
- Minimal coupling: one subscriber; zero changes to gameplay engines/lifecycle/persistence.
- Testability: pure-ish class with injected deps; deterministic event injection in tests.
- No duplicate checkpoints: single owner, forward-only guard, idempotent create/update.
- No financial side effects: references only; forbidden-field rejection enforced underneath.
- No recovery logic in gameplay engines: engines unchanged.
- No startup coupling: independent instantiation; startup integration remains a separate approved stage.

Rejected alternatives recap: direct calls in transition code (A) leak recovery into gameplay; phase-started events (C) observe inconsistent mid-transition state; GameManager-owned calls (E) bloat lifecycle ownership; bare subscriptions without a manager (B) scatter policy.

## 24. Final Architecture Verdict

### Checkpoint Architecture Feasibility

**FEASIBLE WITH BLOCKERS** — feasible overall; two genuine blockers concern operational prerequisites rather than the writer itself (below). No schema, ownership, or architectural obstacle exists.

### Authoritative Checkpoint Trigger

Subscribe (in a new RecoveryCheckpointManager) to the existing post-transition events:
- `GAME_STATE_CHANGED` with `currentState === PRE_GAME_READY` → CREATE (immediately after the transition completes; handler-tail synchronous).
- `GAME_STATE_CHANGED` with `currentState === READY` → UPDATE.
- `GAME_RESULT_READY` (fallback: `GAME_STATE_CHANGED` RESULT) → UPDATE + mark TERMINAL, only when physics is STOPPED.

Never checkpoint before a transition; always after; never in SELF_TEST/SPEED/BRAKE; never at shutdown.

### Minimum Checkpoint Set

Exactly three writes per game: CREATE at PRE_GAME_READY entry; UPDATE at READY entry; UPDATE(terminal) at RESULT. Nothing else.

### TRUE BLOCKERS

1. **No production consumer chain yet end-to-end**: RecoveryDataPersistence is instantiated nowhere in production and RecoveryOrchestrator is not startup-integrated. The checkpoint writer can be built and tested fully, but ships zero protective value until the startup-integration stage lands. Sequencing decision required (writer first, or combined stage) — per the startup audit's recommendation, checkpoint writing first or together.
2. **Paused-clock gap (pre-existing)**: if `clockPaused === true` at a checkpoint moment, the writer must SKIP (no record) because exact resume timing is not representable in the current contract. This is a policy blocker requiring approval (skip-vs-write-anyway), not a schema change.

### NON-BLOCKING LIMITATIONS

- Historical economy object not persisted (`_economies` gap, D2-known) — recovered games have empty economies; unchanged.
- Winner `resolvedAt` not persisted — restored results carry `resolvedAt: null`.
- WinnerActivation retry race at RESULT transition — eliminated by triggering the terminal write on `GAME_RESULT_READY`; if the fallback trigger is used, `winnerId: null` is honest and orchestrator-compatible.
- No fsync — durability baseline equals existing financial records; accepted.
- Stale-record windows (§18 cases B/C) — inherent, documented, mitigated only by immediate post-transition writes.
- Catalog-version not persisted — frozenTimers carried inside the persisted configuration mitigate; unchanged from prior audits.

### EXACT IMPLEMENTATION SCOPE

Next coding stage: create `server/recovery/RecoveryCheckpointManager.js` + focused tests + additive construction/subscription wiring in `server/app.js`. Nothing else. No persistence/schema/engine/manager/lifecycle modifications. Approval additionally required for: (a) the skip-on-paused policy, (b) marking RESULT records TERMINAL at checkpoint time, (c) stage sequencing relative to startup integration.

### FAILURE POLICY

Log and continue, unconditionally. Checkpoint persistence failure never blocks, rolls back, degrades, or crashes live gameplay. A missing/stale record means the game is not recoverable after restart — which is today's universal behavior and therefore never a regression.

### SHUTDOWN POLICY

Shutdown checkpointing is NOT required and should NOT be implemented. Transition-time synchronous writes already cover graceful shutdown; a shutdown write would be redundant, teardown-risky, and sequencing-irrelevant (nothing to flush before `financialPersistence.shutdown({checkpoint:true})`).

### STARTUP DEPENDENCY

Checkpoint writing does not technically depend on startup integration and should be implemented FIRST (or as one combined stage). Implementing startup integration first yields permanently-empty recovery storage with zero benefit (startup audit §19/§22 High risk). The writer is independently testable against synthetic flows and becomes operationally meaningful the moment startup integration lands.
