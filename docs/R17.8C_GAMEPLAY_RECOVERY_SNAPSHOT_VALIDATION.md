# R17.8C — Gameplay Recovery Snapshot Availability Validation

**Mode:** Audit only (no code changes)  
**Date:** 2026-08-14  
**Depends on:** R17.8A (gap analysis), R17.8B (pre-game routing)  
**Main question:** Can a player recover successfully **immediately after** `GAME_INITIALIZED`?

---

## 1. Gameplay recovery lifecycle diagram

```text
SETUP_SESSION_COMPLETED
  │
  ├─ createGame
  ├─ InputAuthority.registerPlayers          ← input available
  ├─ PhysicsEngine.createSimulation          ← physics available (state CREATED)
  ├─ GameClockEngine.createClock             ← clock record exists (not started)
  └─ wait profiles + ENTRY_PAYMENT_COMPLETED
        │
        │  (configuration must be committed — activation fails closed otherwise)
        ▼
ENTRY_PAYMENT_COMPLETED → GameManager._activateGameplaySession
  │
  ├─ (1) GameStateEngine.initializeGameState → PRE_GAME_READY
  ├─ (2) GameClockEngine.startClock          ← clock running for PRE_GAME_READY
  ├─ (3) GameManager.initializeGame          → emits GAME_INITIALIZED
  └─ Physics remains CREATED until READY
        │
        │  ★ FIRST RECOVERY-SAFE POINT (same synchronous activation)
        ▼
PRE_GAME_READY → READY → SELF_TEST → SPEED → BRAKE → RESULT
  │                                              │
  │ on-demand RecoveryEngine.buildRecoverySnapshot
  │ (no RecoverySnapshotCache yet)
  │                                              ▼
  │                                    RecoverySnapshotCache._capture
  │                                    (RESULT only; Page6 stamp later)
```

### R17.8B routing (SocketGateway)

```text
SESSION_RECOVERY_REQUEST
  → reclaim / bind
  → peek live gameState
  → resolveRecoveryRoute:
       setupActive / no gameState+no cache → PRE_GAME_SUCCESS (skip engine)
       live gameState OR RESULT cache     → GAMEPLAY_SNAPSHOT
       no gameId                          → FAIL
  → GAMEPLAY_SNAPSHOT → RecoveryEngine.recoverPlayer → SESSION_SNAPSHOT
```

Immediately after `GAME_INITIALIZED`, `getState(gameId) === PRE_GAME_READY` → route is **GAMEPLAY_SNAPSHOT**.

## 2. First safe recovery point

```text
First recovery-safe timestamp:
  End of GameManager._activateGameplaySession’s successful try-block
  (after initializeGameState + startClock + initializeGame),
  i.e. the same moment GAME_INITIALIZED is emitted / logged.

Lifecycle phase:
  PRE_GAME_READY (GameStateEngine)
  Game status past CREATED (GameManager.hasInitializedGameplay === true)
  Physics simulation present but typically still CREATED (not yet STARTED)

Required components (all present under normal bootstrap):
  ✓ ConfigurationEngine.getConfiguration(gameId)
  ✓ GameStateEngine.getState(gameId) → PRE_GAME_READY
  ✓ PhysicsEngine.getSimulation(gameId) → non-null (CREATED OK)
  ✓ GameClockEngine.getClock(gameId) → non-null (started)
  ✓ InputAuthority.hasGame(gameId) + per-player input states
```

**SimulationLoop / PHYSICS_STARTED is not required** for `buildRecoverySnapshot()`.  
Recovery needs a physics **record** via `getSimulation`, not an active ticking simulation.

---

## 3. RecoveryEngine requirements

`RecoveryEngine.buildRecoverySnapshot(gameId)` / `recoverPlayer(gameId, playerId)`:

### Required objects / managers

| Source | Accessor | Validation failure |
|--------|----------|--------------------|
| Configuration | `ConfigurationEngine.getConfiguration` | `"Configuration is missing"` |
| Game state | `GameStateEngine.getState` (+ history/debug) | `"Game state is missing"` |
| Physics | `PhysicsEngine.getSimulation` | `"Physics snapshot is missing"` |
| Clock | `GameClockEngine.getClock` | `"Game clock is missing"` |
| Input | `InputAuthority.hasGame` + all seat states | `"Input authority state is missing"` |
| Winner | `WinnerEngine.getResult` | Optional (may be null) |
| Payment | `PaymentEngine.getPayment` | Optional (may be null) |
| PreGameReady | `preGameReadyActivation.getSnapshot` | Optional |
| Page6 / result session | `ResultActivation` / `ResultSessionLifecycle` | Optional enrichment |

### Lifecycle conditions

- RecoveryEngine must be `initialize()`d.
- For `recoverPlayer`, the claimed `playerId` must appear in `snapshot.input.players`.
- **No** requirement that state be SPEED/BRAKE/RESULT.
- **No** requirement that SimulationLoop be running.
- **No** dependency on `RecoverySnapshotCache` for live gameplay (cache is RESULT fallback only).

### Missing relative to full product recovery (out of scope here)

- Entry-payment / wallet-connection lobby sessions are **not** part of this snapshot (handled by RoomLobbyBridge reclaim on pre-game path).
- Socket binding is reclaim-side, not snapshot fields.

## 4. Immediate disconnect after GAME_INITIALIZED

Scenario:

```text
GAME_INITIALIZED
  → PLAYER SOCKET DISCONNECT (soft-offline; seat retained)
  → SESSION_RECOVERY_REQUEST
```

### Can RecoveryEngine succeed?

**Yes — under normal post-activation state.**

Why:

1. R17.8B sees non-null `gameState` (`PRE_GAME_READY`) → routes to `GAMEPLAY_SNAPSHOT`.
2. Bootstrap already created physics + input + configuration before payment activation.
3. Activation just initialized game state and started the clock.
4. `buildRecoverySnapshot` validation should pass; `SESSION_SNAPSHOT` is emitted.

### Exact failure conditions (if it fails)

| Condition | Likely reason string |
|-----------|----------------------|
| Activation never completed / rolled back | gameState missing → may route as `RECOVERY_SKIPPED` (pre-game) instead |
| Configuration lost / never committed | `"Configuration is missing"` |
| Physics simulation removed early | `"Physics snapshot is missing"` |
| Clock removed | `"Game clock is missing"` |
| Input seats incomplete / game forgotten | `"Input authority state is missing"` / player input missing |
| Credential / reclaim failure | Different failure strings (not snapshot) |

There is **no designed intentional gap** between `GAME_INITIALIZED` and first valid on-demand snapshot for the happy path.

## 5. RecoverySnapshotCache

| Question | Answer |
|----------|--------|
| When created? | `GAME_STATE_CHANGED` when `currentState === RESULT` only |
| Exists before RESULT? | **No** |
| Gameplay mid-session uses? | **On-demand** `RecoveryEngine.buildRecoverySnapshot` / `recoverPlayer` |
| Cache role | Survives teardown for Page6 reconnect; payment/audit refresh; `OPEN_PAGE6` stamp |
| Lifetime | In-memory until `forget` / shutdown |

Conclusion: immediate post-`GAME_INITIALIZED` recovery does **not** depend on cache.

## 7. Current limitations

1. **No RESULT cache before RESULT** — expected; live engines must remain intact for mid-game recovery.
2. **Physics may be CREATED (static)** during early PRE_GAME_READY — recoverable, but client restores a non-spinning pose until READY/SPEED.
3. **No explicit `RECOVERY_SUCCESS` log token** — harder to grep than SKIPPED/FAILED.
4. **No dedicated integration test** in-repo for “disconnect in the same tick as GAME_INITIALIZED” (routing unit tests cover phase gates; RecoveryEngine unit tests cover build with full stack).
5. **Process restart** still loses in-memory engines/cache (unchanged durability limitation).

## 9. R17.8D — Integration validation results

**Status:** Implemented and validated (2026-08-14)

### Observability

`SocketGateway` now emits:

| Event | When |
|-------|------|
| `RECOVERY_SKIPPED` | Pre-game path (retained) |
| `RECOVERY_SUCCESS` | Pre-game sync **and** gameplay snapshot success |
| `RECOVERY_FAILED` | Snapshot build failure (real reason) |
| `Snapshot sent` | Gameplay path (R12.5D detail line) |

`RECOVERY_SUCCESS` fields: `route`, `phase`, `roomId`, `playerId`, `gameId`.

- Pre-game: `route=PRE_GAME_SYNC`, `phase=ENTRY_PAYMENT|SETUP`
- Gameplay: `route=GAMEPLAY_SNAPSHOT`, `phase=<live state e.g. SPEED|PRE_GAME_READY|RESULT>`

### Tested scenarios (`server/tests/recoveryIntegration.r178d.test.js`)

| Test | Result |
|------|--------|
| A — Payment / pre-`GAME_INITIALIZED` reclaim | PASS — RecoveryEngine not called; `RECOVERY_SUCCESS` / `PRE_GAME_SYNC` |
| B — Immediate post-`GAME_INITIALIZED` (`PRE_GAME_READY`) | PASS — RecoveryEngine called; `SESSION_SNAPSHOT`; success log |
| C — Mid-game `SPEED` | PASS — snapshot restore; physics angle unchanged by path; success log |
| D — RESULT cache | PASS — cache fallback after live build fail; final state restored |
| Invalid (no gameId) | PASS — clear `SESSION_RECOVERY_FAILED` |

### Final Recovery lifecycle diagram

```text
SESSION_RECOVERY_REQUEST
        │
        ▼
   session reclaim / bind
        │
        ▼
 resolveRecoveryRoute(setupActive, gameId, gameState, cache)
        │
        ├─ PRE_GAME_SUCCESS ──► lobby/payment sync already done
        │                         RECOVERY_SUCCESS route=PRE_GAME_SYNC
        │                         (RecoveryEngine NOT called)
        │
        ├─ FAIL ──────────────► SESSION_RECOVERY_FAILED
        │
        └─ GAMEPLAY_SNAPSHOT ─► RecoveryEngine.recoverPlayer
                                  │
                                  ├─ live sources OK ──► SESSION_SNAPSHOT
                                  │                      RECOVERY_SUCCESS
                                  │                      route=GAMEPLAY_SNAPSHOT
                                  │                      phase=<PRE_GAME_READY|SPEED|…>
                                  │
                                  └─ throw ──► RESULT cache?
                                                ├─ hit ──► SESSION_SNAPSHOT + SUCCESS
                                                └─ miss ──► RECOVERY_FAILED
```

### Remaining limitations

- No durable recovery across process restart.
- RESULT cache still begins only at RESULT.
- Pre-game success does not emit `SESSION_SNAPSHOT` (by design; lobby events carry authority).
- Tests stub gateway dependencies; they do not spin a full multiplayer TON payment room.
