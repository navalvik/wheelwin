# R17.9T.8 — Attack E Observability

Date: 2026-08-24

Task: Implement minimal passive observability for Attack E per the R17.9T.7 "OPTION B — Monitoring First" recommendation. No blocking/anti-abuse controls were introduced.

## 1. Objective

Make the residual Attack E risk observable in production: who creates rooms, how fast rooms are created, how full the global room pool is, and whether ROOM_CREATION_LIMIT saturation is occurring — using ONLY existing logging/metrics architecture.

## 2. Starting R17.9T.7 Findings

- Attack E is architecturally possible; risk MEDIUM (low end).
- Four observability gaps identified: (1) no safe Telegram identity marker in CREATE_ROOM success logs; (2) no periodic active-room-count signal beyond on-demand debug snapshot; (3) no creation-velocity/near-capacity signal; (4) no saturation alert signal.

## 3. Existing Observability Architecture (Phase 1, verified)

- `RoomLobbyBridge._handleCreateRoom()` logged successes (`Lobby room created | roomId | playerId`) without identity; rejection `decisionTrace` entries carried socketId only.
- `RoomManager`: `getActiveRoomCount()`, `isAtCapacity()`, `getDebugSnapshot()`; configured max was private (`_resolveMaxConcurrentRooms`).
- Existing metrics stack (`server/monitoring/`): `MonitoringManager` singleton → `MetricsScheduler` → collectors (`GameplayMetricsCollector` already emitted `gameplay.active_rooms` from `roomManager.getRooms().length`) → `MetricsRegistry` → `MetricsSnapshot` → Prometheus `/metrics` exporter + JSON exporter + console `buildMetricsOverview` projection.
- `MetricsService` (`server/services/MetricsService.js`): monotonic counters (`increment`, e.g. existing `games.started`) and timing records; no-ops unless enabled+initialized.
- `LogSanitizer` redacts secret-shaped keys; Telegram numeric user ID is not secret-classified anywhere in project conventions (it already lives in trusted `socket.data`).

Conclusion: all four gaps could be closed by extending existing mechanisms; NO new logging subsystem was created.

## 4. Design Decision (Phases 2–3)

1. Files: `server/socket/RoomLobbyBridge.js`, `server/managers/RoomManager.js`, `server/monitoring/GameplayMetricsCollector.js`, `server/app.js`, new test `server/tests/attackEObservability.r179t8.test.js`.
2. Data emitted:
   - Safe numeric identity marker `tgId=<telegramUserId>` appended to the success log line; `telegramUserId` field added to the user-quota rejection `decisionTrace`.
   - New `CREATE_ROOM_SATURATION` decisionTrace (with `activeRooms` / `maxRooms`) on ROOM_CREATION_LIMIT rejections.
   - Monotonic counters via MetricsService: `rooms.created`, `rooms.create_rejected_user_limit`, `rooms.create_rejected_room_limit`.
   - Collector gauges: `gameplay.room_pool_max`, `gameplay.room_pool_utilization` (active/max, 0..1), `gameplay.room_pool_near_capacity` (1 when utilization ≥ 0.75), velocity gauges `gameplay.rooms_created_per_min` and `gameplay.rooms_creation_limit_rejected_per_min` (counter deltas over elapsed wall time inside the collector), cumulative `gameplay.rooms_created_total` / `gameplay.rooms_creation_limit_total`.
3. Events: successful create; user-limit reject; room-limit reject.
4. Frequency: counters at event time; collector gauges at the existing scheduler interval (default 1000 ms). Velocity is derived, not sampled.
5./6. Visibility: registry → snapshot → Prometheus `/metrics` + JSON export + developer console metrics overview; traces/logs through the existing structured logger.
7. Log volume: no new per-request log lines beyond one extended line and one trace on saturation; counter increments are silent.
8. Secrets: only the server-authenticated numeric telegramUserId is logged — never initData, tokens, HMAC values, or client payloads (test-enforced).
9. Single source of truth: pool numbers read live from RoomManager getters; no second registry.
10. Behavior unchanged: all additions are after the authorization decision; `metricsService?.increment` cannot gate anything (no-ops when absent/disabled).

## 5. Exact Implementation Changes

- `RoomLobbyBridge.js`: optional constructor dep `metricsService`; `tgId=` in success log; `telegramUserId` in quota-rejection trace; new `CREATE_ROOM_SATURATION` trace + `rooms.create_rejected_room_limit` increment on capacity rejection; `rooms.create_rejected_user_limit` on quota rejection; `rooms.created` on success.
- `RoomManager.js`: read-only `getMaxConcurrentRooms()` returning `_resolveMaxConcurrentRooms()`.
- `GameplayMetricsCollector.js`: constructor velocity-baseline state; collect() emits pool/utilization/near-capacity gauges, velocity gauges, cumulative counters.
- `app.js`: passes `this._metricsService` into the RoomLobbyBridge constructor.

## 6. Strategies

- Safe identity: numeric Telegram user ID from trusted `socket.data` (via the existing resolver), logged as `tgId=`; chosen because it is the project's canonical server-side identity, non-secret per conventions, and aggregation-friendly. No hashing introduced (documented decision: ID is already treated as safe server-side runtime data).
- Pool visibility: utilization = `getActiveRoomCount() / getMaxConcurrentRooms()`, near-capacity flag at ≥75%.
- Velocity: per-minute rates computed by the collector from monotonic counter deltas (first collect seeds baseline).
- Saturation: `CREATE_ROOM_SATURATION` trace + cumulative limit-rejection counter + near-capacity gauge together answer "is saturation happening".

## 7. /debug Integration

New gauges/counters appear automatically in: Prometheus `/metrics` (existing exporter), JSON metrics export, and the developer console metrics overview projection. Traces/logs flow through the existing structured logger. No new export path, no external telemetry platform, no database persistence added.
