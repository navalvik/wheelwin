## 3. Architecture Findings

The orchestrator already attached recovered PRE_GAME_READY/READY clocks with
dormant semantics (`attachClock(..., { arm: false })`) and armed them as the
final pipeline step regardless of player connectivity. PLAYER_CONNECTED is an
existing manager-level EventBus event emitted by PlayerManager with payload
`{ playerId, connectionState, runtime }`. The orchestrator receives the
PlayerManager (and optionally an EventBus) via constructor DI.

## 4. Lifecycle Flow (new)

1. Candidate recovery proceeds exactly as before through step 16.
2. Step 17 (PRE_GAME_READY/READY only): instead of arming immediately, the
   game is registered in a runtime-only pending map and the current connection
   state of all 3 registered players is evaluated:
   - all CONNECTED → `armRecoveredClock(gameId)` called once, pending entry removed;
   - otherwise → clock remains UNARMED-ATTACHED, entry stays pending;
   - if all players report CONNECTED but the engine refuses arming
     (e.g. deadline elapsed between validation and arming), the pre-existing
     fail-closed FAILED_EXPIRED rollback path applies unchanged.
3. On each manager-level PLAYER_CONNECTED event, affected pending games are
   re-evaluated against the CURRENT authoritative connection state of all 3
   registered players; arming happens exactly once when the predicate holds.
4. RESULT / unsupported-phase / failed candidates never enter pending state.

## 5. Ownership Boundaries

Policy owner: RecoveryOrchestrator (recovery domain only). No gameplay module,
manager, engine, socket layer, or financial module was modified. The pending
map is internal runtime memory owned by the orchestrator instance.

## 6. Risks

- Critical: none found.
- High: none found.
- Medium: none found.
- Low: If a production deployment constructs multiple RecoveryOrchestrator
  instances over the same PlayerManager bus, each instance would track its own
  pending set (arming is still guarded by the engine's own idempotency).
  Current production constructs exactly one instance during startup.

## 7. Recommendations

## 8. Changes Made

### Production (single file)

`server/recovery/RecoveryOrchestrator.js`:

- Added `_pendingRecoveredClocks` Map (runtime-only, keyed by gameId, storing
  `{ roomId, playerIds }`). NOT persisted; NOT part of the Recovery Data
  Contract; NOT a gameplay state.
- Added idempotent one-time subscription to the existing manager-level
  `PLAYER_CONNECTED` event (bus resolved from injected EventBus or the
  PlayerManager's own bus; no socket awareness). Subscription is created once
  per orchestrator instance, lazily at first recoverCandidate/recoverAll call.
- Step 17 replaced immediate arming with: register pending → evaluate current
  connectivity → arm immediately if all 3 CONNECTED, else remain dormant.
- New helpers: `_resolveEventBus()`, `_ensurePlayerConnectedSubscription()`,
  `_handlePlayerConnected(event)`, `_areAllRegisteredPlayersConnected(ids)`,
  `_tryArmPendingRecoveredClock(gameId)`.
- Pending entries removed on: successful arming, refused (fail-closed) arming,
  rollback/failure (rollback path never registers before full success —
  registration occurs only after consistency validation passes).
- Success reason strings now distinguish
  `pre_game_candidate_recovered_clock_armed` vs
  `pre_game_candidate_recovered_clock_pending_connectivity`.
- No changes to classification, duplicate detection, validation, aggregate
  construction, consistency validation, rollback mechanics, or result building
  beyond the reason strings.

## 9. Deadline Preservation & Expiry

`phaseStartedAt`, `clockStartedAt`, durations, deadlines and remaining-time
semantics are untouched. Late arming uses existing `armRecoveredClock()`
remaining-time computation; if the original deadline has already elapsed, the
engine refuses and the orchestrator logs and drops the pending entry
(fail-closed). Test G covers this end-to-end with a real timer.

## 10. Disconnect After Arming

No PLAYER_DISCONNECTED listener exists in the orchestrator. Once armed, the
recovered clock behaves as normal running gameplay. Test H verifies handle and
deadline immutability across a post-arming disconnect.

## 11. Idempotency

Duplicate PLAYER_CONNECTED events, repeated handler invocations, second
recoverAll() passes, and post-arming connection churn are safe no-ops. The
engine's own armRecoveredClock safeguards remain authoritative. Tests D/F/L.

## 12. Normal-Game Isolation

PLAYER_CONNECTED handling only consults the pending recovered-clock map.
Normal GameManager→startClock() behavior is untouched. Test M verifies a
normal running clock's timeout handle and deadline are unaffected.

## 16. Remaining Limitations

- Pending recovered-clock state is per-orchestrator-instance memory; a
  process restart between reconstruction and full reconnection simply
  re-runs recovery from persistence (by design).
- If the original deadline elapses while pending, the game fails closed on
  the late arming attempt (deliberate; financial continuation belongs to the
  existing financial recovery architecture).

## 17. Final Verdict

IMPLEMENTED AND VALIDATED. INVARIANT R-CLOCK-1 holds: a recovered
PRE_GAME_READY/READY game exists in exactly one of UNARMED-ATTACHED or ARMED;
the transition occurs only inside the recovery domain and only when all 3
registered players report CONNECTED.
