# R17.8H — TON Payment Confirmation Flow Audit

**Mode:** Investigation only (no code changes)  
**Date:** 2026-08-14  
**Depends on:** R17.8A–G (recovery / RoomLobby reconnect validated)  
**Symptom:** After successful wallet connection on mobile browsers (Opera / Mi Browser), games fail with `ROOM_DESTROYED`, `finalStage: PAYMENT`, `payment.status: PAYMENT_FAILED`. Telegram WebApp recovery was OK in earlier tests; this failure is in the **payment confirmation** lifecycle, not RoomLobby reconnect.

---

## 1. Current payment lifecycle diagram

```text
VERIFY / PAYMENT_STAGE_READY
  │
  ├─ WalletConnectionSession created
  │     timer: WALLET_CONNECTION_DURATION_MS (default 5 min)
  │     clears when paymentConnectionReady
  │
  ├─ TonConnect connect (client Page4Payment)
  │     → WALLET_CONNECT_REPORT
  │     → seat CONNECTED
  │
  └─ all seats CONNECTED
        │
        ▼
  PAYMENT_CONNECTION_READY          ← observed as "PAYMENT_READY" in handshake logs
        │
        ▼
  PaymentSessionManager.createPaymentSession
        status → WAITING_FOR_PAYMENTS
        paymentDeadline = now + PAYMENT_SESSION_DURATION_MS (default 5 min)
        _scheduleExpiry → failSession("payment_timeout") on deadline
        │
        ├─ emit PAYMENT_SESSION_CREATED
        └─ if no contractAddress yet → PAYMENT_SESSION_UPDATED
              │
              ▼
        GameContractManager deploy (timeout default 2 min)
              │
              ├─ success → GAME_CONTRACT_READY / activate PAYMENT_REQUEST
              │     seats → AWAITING_PLAYER_CONFIRMATION
              │     BlockchainMonitor.watchPayment per seat
              │
              └─ failure → GAME_CONTRACT_DEPLOY_FAILED
                    → PaymentSessionManager.failSession(reason)
                    → session.status = PAYMENT_FAILED
                    → PAYMENT_SESSION_FAILED
                    → RoomLobbyBridge._closeRoom
                    → ROOM_DESTROYED
        │
        ▼  (only if deploy + requests succeeded)
  Player taps Confirm (Page4Payment.handleConfirmPayment)
        │
        ├─ tonConnectUI.sendTransaction(STAKE)
        │     ★ awaits wallet UI / external wallet app
        │
        └─ on success only → socket.emit(PAYMENT_CONFIRM_INTENT)
              → submitPlayerConfirmation
              → seat PAYMENT_SUBMITTED → BLOCKCHAIN_PENDING
        │
        ▼
  BlockchainMonitor observes STAKE / deposit
        → PAYMENT_TRANSACTION_CONFIRMED
        and/or GAME_ESCROW_STAKE_CONFIRMED
        → PaymentSessionManager confirms seat PAYMENT_CONFIRMED
        │
        ▼
  allConfirmed → PAYMENT_SESSION_COMPLETED (FULLY_PAID)
        → GameStartAuthorization → GAME_START_BOOTSTRAP_READY
        → ENTRY_PAYMENT_COMPLETED → OPEN_PAGE5 / gameplay
```

**Naming note:** Client/server handshake logs use stage label `PAYMENT_READY` for the transition into `PAYMENT_CONNECTION_READY`. That is **wallet barrier clear**, not on-chain payment completion. Entry-payment completion is `PAYMENT_SESSION_COMPLETED` / `ENTRY_PAYMENT_COMPLETED` (settlement `PAYMENT_COMPLETED` is a different PaymentEngine path).

## 3. Exact `PAYMENT_FAILED` trigger

### Primary terminal path (matches archive shape)

```text
PaymentSessionManager.failSession(roomId, reason)
  ├─ reason === "payment_timeout" → markTimedOut() → status PAYMENT_TIMEOUT
  └─ else → markFailed() → status PAYMENT_FAILED
       → emit PAYMENT_SESSION_FAILED { …snapshot, reason }
            → RoomLobbyBridge._handlePaymentSessionFailed
                 → _closeRoom(reason)
                 → ROOM_DESTROYED
```

| Field | Value |
|--------|--------|
| **File** | `server/gameplay/PaymentSessionManager.js` |
| **Function** | `failSession` |
| **Condition** | Session exists and is non-terminal |
| **Required state** | In-progress PaymentSession |
| **Actual state (symptom)** | `payment.status: PAYMENT_FAILED` ⇒ **`markFailed` path** (not `payment_timeout`) |
| **Room close** | `RoomLobbyBridge._handlePaymentSessionFailed` |
| **Archive** | `PAYMENT_SESSION_FAILED` sets `paymentFailed`; `finalStage: PAYMENT` if `paymentEntered` (set at `PAYMENT_CONNECTION_READY`) |

### Call sites that reach `markFailed` (non-timeout)

| Reason source | Trigger |
|---------------|---------|
| `GAME_CONTRACT_DEPLOY_FAILED` | Deploy / init / openPayments failure → `failSession(roomId, reason)` |
| Default / explicit | `failSession(roomId, "payment_failed")` or other non-timeout reasons |
| Create failure | `createAndRequest` catch emits `PAYMENT_SESSION_FAILED` **without** necessarily setting session.status (edge) |

### Timeout path (related but different status)

| Field | Value |
|--------|--------|
| **Timer source** | `PaymentSessionManager._scheduleExpiry` |
| **Duration** | `PAYMENT_SESSION_DURATION_MS` (default **5 minutes** from session create) |
| **Start event** | `createPaymentSession` |
| **Stop event** | `_clearExpiry` on FULLY_PAID / fail / destroy |
| **Failure action** | `failSession(roomId, "payment_timeout")` → status **`PAYMENT_TIMEOUT`** |

If production JSON truly shows session `status: PAYMENT_FAILED` (not `PAYMENT_TIMEOUT`), prefer **deploy/create failure** over wall-clock payment timeout. Participant seats are marked `PAYMENT_FAILED` on **both** timeout and fail, which can confuse UI summaries.

### Is failure caused by…?

| Candidate | Fit |
|-----------|-----|
| Timeout (payment session) | Possible for incomplete STAKE; status would usually be `PAYMENT_TIMEOUT` |
| Missing client callback | **Strong on mobile browsers** — `PAYMENT_CONFIRM_INTENT` only after `await sendTransaction`; external wallet return can drop/hang the promise |
| Invalid transaction | Possible (build/reject); usually local error, not immediate room destroy unless deadline later |
| Missing wallet event | Unlikely after observed `PAYMENT_CONNECTION_READY` / `PAYMENT_READY` |
| Client disconnect | Soft-disconnect protected; players remained connected per report |
| Server validation / deploy | **Strong** — next step after wallet barrier is contract deploy; failure → `PAYMENT_FAILED` immediately |

## 4. Telegram WebApp vs mobile browser

| Aspect | Telegram WebApp | Mobile browser (Opera / Mi) |
|--------|-----------------|-----------------------------|
| TonConnect bridge | In-app Telegram bridge; wallet often in same host | Universal / deep link to **external** wallet app |
| `sendTransaction` return | Usually resolves in-place | Browser may **background / freeze / reload**; promise may never resolve |
| `PAYMENT_CONFIRM_INTENT` | Emitted after await success | May never emit if await hangs or page dies |
| Visibility recovery (R17.8) | Gameplay pages only — **not Page4** | Same — resume does not auto-retry STAKE |
| Wallet connection validity | Can remain CONNECTED | Can remain CONNECTED while confirm path is stuck |
| Advertising / socket | Independent; can stay healthy | Same — matches “players remained connected” |

### Can mobile browser lose confirmation while wallet stays connected?

**Yes.**

1. Connection report already succeeded → seats stay `CONNECTED` / barrier already cleared.  
2. Confirm depends on a **second** TonConnect round-trip (`sendTransaction`).  
3. If that round-trip never completes client-side, intent is never emitted.  
4. On-chain confirmation can still succeed **if** the wallet actually broadcast STAKE and `BlockchainMonitor` matches it (watches are registered at `PAYMENT_REQUEST` time, and confirm accepts several seat statuses).  
5. If the wallet never signed, or the page died before submit, or monitoring never matches before a **deploy fail** / **deadline**, the room terminates with payment failure while wallets still look “connected”.

## 5. Payment timeout / cleanup logic

| Timer | Source | Duration (default) | Start | Stop / clear | Failure |
|-------|--------|--------------------|-------|--------------|---------|
| Setup Timer | `SetupSessionLifecycle` | 5 min from setup start | Setup session start | Expiry / gameplay release | `SETUP_SESSION_EXPIRED` → `_closeRoom("setup_expired")` — **still runs during ARCHIVED payment** (R7.70C23) |
| Wallet barrier | `RoomLobbyBridge._scheduleWalletConnectionTimeout` | 5 min | Wallet session create | Cleared when `paymentConnectionReady` | `_closeRoom("wallet_connection_timeout")` — **N/A after observed PAYMENT_READY** |
| Contract deploy | `GameContractManager` / room config | 2 min | Deploy begin | Deploy success/fail | `GAME_CONTRACT_DEPLOY_FAILED` → `failSession` → **PAYMENT_FAILED** |
| Payment session | `PaymentSessionManager._scheduleExpiry` | 5 min from create | `createPaymentSession` | FULLY_PAID / fail | `failSession("payment_timeout")` → **PAYMENT_TIMEOUT** |

```text
PAYMENT_CONNECTION_READY / "PAYMENT_READY"
  → waiting for deploy + STAKE confirmations
  → can hit deploy fail (PAYMENT_FAILED) before any confirm callback
  → or payment_timeout if STAKE never confirmed in time
```

**Yes:** the system can fail while waiting for confirmation **before** a late wallet callback arrives — especially deploy failure (fast) or payment deadline (slow), and Setup Timer if prep burned most of the 5 minutes.

## 6. Logging coverage

| Desired diagnostic | Present? | Actual signal |
|--------------------|----------|---------------|
| `PAYMENT_REQUEST_CREATED` | **Missing** as named event | `PAYMENT_SESSION_CREATED`, `PAYMENT_REQUEST` |
| `PAYMENT_TRANSACTION_SENT` | **Missing** server-side | Client console `[Page4Payment] TonConnect sendTransaction` only |
| `PAYMENT_TRANSACTION_CONFIRMED` | **Yes** | EventBus + history timeline |
| `PAYMENT_CONFIRMATION_RECEIVED` | **Missing** | Closest: `PAYMENT_CONFIRM_INTENT` / seat → `BLOCKCHAIN_PENDING` |
| `PAYMENT_COMPLETED` | **Misleading name** | Settlement `PaymentEngine`; entry uses `PAYMENT_SESSION_COMPLETED` / `ENTRY_PAYMENT_COMPLETED` |
| `PAYMENT_FAILED` | Partial | Settlement `PAYMENT_FAILED`; entry terminal is **`PAYMENT_SESSION_FAILED`** + session `PAYMENT_FAILED` / `PAYMENT_TIMEOUT` |

**Gaps for this bug:** no authoritative server log that a client **broadcast** a STAKE; no first-class “intent received” / “sendTransaction succeeded” correlation id; easy to confuse handshake `PAYMENT_READY` with payment completion.

## 8. Exact failure path (hypothesis for observed games)

```text
… → all wallets CONNECTED → PAYMENT_CONNECTION_READY ("PAYMENT_READY")
        → PaymentSession created (WAITING_FOR_PAYMENTS)
        → ★ missing ENTRY / SESSION completed
        → PAYMENT_SESSION_FAILED
        → ROOM_DESTROYED
        → archive: finalStage=PAYMENT, payment.status=PAYMENT_FAILED
```

Most likely forks after `PAYMENT_CONNECTION_READY`:

1. **Contract deploy / init / openPayments fails** → `failSession(deploy_*)` → `PAYMENT_FAILED` (fits “immediately after wallet connection”).  
2. **Mobile browser never completes STAKE** (TonConnect return loss) → seats never confirm → later `payment_timeout` (status `PAYMENT_TIMEOUT`) **or** concurrent deploy/setup issues misread as immediate fail.  
3. **Setup Timer expiry** during payment → `setup_expired` (lifecycle usually `SETUP_EXPIRED`, not `PAYMENT_FAILED`) — weaker match to reported `payment.status`.

## 9. Root cause candidates (ranked)

| Rank | Candidate | Why |
|------|-----------|-----|
| **1** | **Mobile TonConnect `sendTransaction` return-path fragility** (Opera / Mi) | Wallet can stay connected; confirm awaits external app; intent only after await; Telegram bridge more reliable |
| **2** | **Post-ready contract deploy failure** | Immediate `PAYMENT_FAILED` right after wallet barrier; players still connected |
| **3** | **Payment session deadline while STAKE pending / unobserved** | Fits missing completion; status often `PAYMENT_TIMEOUT` — verify exact JSON |
| **4** | **Setup Timer still enforcing wall clock into payment** | Can destroy room mid-payment; usually different lifecycle label |
| **5** | R17.8 reconnect cancel | **Unlikely** — recovery rehydrates payment; not cancel |

**Primary hypothesis:** On mobile browsers, the **payment confirmation** step (TonConnect STAKE +/or deploy readiness) fails after the **wallet connection** barrier succeeds. The server then terminates via `PAYMENT_SESSION_FAILED` → room destroy. This is a **payment / TonConnect confirmation** issue, not RoomLobby reconnect.

## 10. Recommended minimal fix direction (do not implement here)

1. **Correlate production archives** for the two failed games: `PAYMENT_SESSION_FAILED.reason`, deploy logs, whether any `PAYMENT_REQUEST` / `PAYMENT_TRANSACTION_CONFIRMED` / `PAYMENT_CONFIRM_INTENT` existed.  
2. **Client:** treat return-from-wallet / `visibilitychange` on Page4 as a chance to re-sync escrow (`syncFromGameEscrow` path) and re-offer confirm without wiping wallet session; do not require destroying recovery.  
3. **Client:** emit a non-authoritative “tx submitted” diagnostic when `sendTransaction` resolves; optionally allow server to mark `PAYMENT_SUBMITTED` from a safer ack — **without** trusting client for money.  
4. **Server:** ensure deploy failures are clearly distinguished in player-facing / history reason from timeout.  
5. **Do not** change Gameplay / Physics / R17.8 recovery protocol in the first fix; keep scope to Page4 TonConnect confirm + deploy diagnostics.

**Suggested next stage:** **R17.8I** — forensic pull of the two failed session history JSON + deploy traces; then minimal Page4 return-from-wallet confirm resilience if reason shows missing STAKE/intent, or deploy hardening if reason is `deploy_*`.
