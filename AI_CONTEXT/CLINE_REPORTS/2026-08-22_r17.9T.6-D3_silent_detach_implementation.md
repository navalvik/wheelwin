# R17.9T.6-D3 — Silent Detach Primitives Implementation

Date: 2026-08-22

Task: R17.9T.6-D3 prerequisite — remove the rollback blocker identified by the D3 pre-implementation audit by adding minimal silent detach helpers (approved Option A). RecoveryOrchestrator itself is NOT implemented.

## 1. Scope

Additive silent rollback detach APIs on RoomManager, GameManager, PlayerManager, ConfigurationEngine, and WinnerEngine, mirroring the D1/D2 silent attach pattern. Each helper removes exactly one runtime entry with zero events and zero cross-subsystem effects.

## 5. RoomManager Behavior

`detachRoom(roomId)`:
- Deletes the room from `_rooms`.
- Deletes `_playerRoomIndex` entries ONLY where the mapping points to the detached room (`get(playerId) === roomId`); mappings belonging to other rooms are never removed.
- Unsubscribes and deletes the room's own `_roomListeners` subscriptions (unsubscribe only — no listener callbacks triggered).
- Does NOT emit ROOM_DESTROYED, does NOT call destroyRoom(), does NOT call setupSessionLifecycle.abortForRoom, does NOT mutate room.status, does NOT print forensics, does NOT touch GameManager/PlayerManager/socket/session systems.
- Unknown/null roomId or duplicate detach → returns false, modifies nothing.

## 6. GameManager Behavior

`detachGame(gameId)`:
- Deletes the game from `_games`.
- Cleans GameManager-owned bookkeeping directly associated with the gameId:
  - `_pendingGameplayActivation` entries whose value === gameId;
  - `_pendingConfigurationByRoom` entries whose value === gameId;
  - `_entryPaymentActivatedGames.delete(gameId)`;
  - unsubscribes/deletes the game's own `_gameListeners` subscriptions.
- Does NOT emit GAME_DESTROYED, does NOT call destroyGame()/finishGame(), does NOT mutate game.status, does NOT trigger winner/settlement logic, does NOT touch PaymentSessionManager/RoomManager/PlayerManager/sockets.
- Unknown gameId or duplicate detach → false, no-op.

## 7. PlayerManager Behavior

`detachPlayer(playerId)`:
- Deletes the player's entry from `_identities` and `_runtimes`.
- Does NOT derive or alter playerIndex ownership (playerIndex is not owned by PlayerManager).
- Does NOT emit PLAYER_REMOVED, does NOT call removePlayer(), does NOT touch RoomManager/GameManager/sockets/reconnect.
- Unknown/null playerId or duplicate detach → false, no-op.

## 8. ConfigurationEngine Behavior

`detachConfiguration(gameId)`:
- Source inspection confirmed the D2 attach path (`attachConfiguration`) populates exactly ONE registry: `_configurations`. The `_economies` registry is per-game runtime state populated via `freezeEconomy` (also at GAME_INITIALIZED); both are keyed by gameId and both are cleaned by the existing `removeConfiguration`, so `detachConfiguration` deletes both entries for the requested gameId — matching removeConfiguration minus the event.
- Does NOT emit CONFIGURATION_REMOVED, does NOT call removeConfiguration(), does NOT generate replacement configuration, does NOT modify catalog/version data or persisted configuration, does NOT modify GameManager/GameStateEngine.
- Unknown gameId or duplicate detach → false, no-op.

## 9. WinnerEngine Behavior

`detachResult(gameId)`:
- Deletes the game's entry from `_results` (the single runtime registry populated by `attachResult()`/`restoreResult()`).
- Does NOT emit GAME_RESULT_REMOVED, does NOT call removeResult()/resolveResult(), does NOT recalculate a winner, does NOT trigger ResultActivation/settlement/financial actions, does NOT touch configuration/physics/game state.
- Unknown gameId or duplicate detach → false, no-op.

## 10. Event Isolation

Verified by tests with global event counters on: ROOM_DESTROYED, GAME_DESTROYED, PLAYER_REMOVED, CONFIGURATION_REMOVED, GAME_RESULT_REMOVED, plus ROOM_CREATED, GAME_CREATED, PLAYER_CREATED, CONFIGURATION_READY, GAME_RESULT_READY, WINNING_SECTOR_RESOLVED, PHYSICS_STOPPED, CLOCK_STOPPED. All counts remain zero across every detach operation — proving no indirect emission through normal destruction paths.

## 11. Atomicity / Isolation

Each detach is deliberately local: removes only its own component's runtime state. No multi-component rollback coordination, no transaction abstraction, no RecoveryOrchestrator. RecoveryOrchestrator will later coordinate Room/Players/Game/Configuration/GameState/Clock/Input/Physics/Winner using these primitives plus the already-silent removals (`removeState`, unarmed `removeClock`, `removeSimulation` for CREATED/STOPPED, InputAuthority `removeGame`).
