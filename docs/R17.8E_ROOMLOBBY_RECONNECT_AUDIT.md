# R17.8E — RoomLobby Reconnect State Audit

**Mode:** Audit only (no code changes)  
**Date:** 2026-08-14  
**Depends on:** R17.8A–D (recovery routing context; this issue is **not** Recovery Snapshot)  
**Symptom:** RoomLobby UI stuck on **"Reconnecting…"** before a game room / Setup Session is fully active; ads keep rotating in sync across devices.

**Observed (production / unstable mobile):**

- 3 Android clients (Telegram WebApp, Opera, one other).
- Two clients showed Reconnecting; one did not.
- Advertising banners continued switching **synchronously** on all devices.
- Game Engine room was **not** created yet (RoomLobby stage only).

**Key implication:** Synced ads prove the **shared Socket.IO transport can be connected and receiving** while RecoveryOverlay still shows Reconnecting. The overlay is a **client recovery UI state machine**, not a direct mirror of `socket.connected`.

## 2. RoomLobby reconnect lifecycle

```text
User opens app
  → main.jsx: socket.connect()
  → App page = LOBBY (2)  [isSetupRecoveryPage = true]

[Optional] Create/Join room
  → roomCreated / roomJoined → PlayerIdentity { roomId, playerId, … }
  → OR still on create/join UI with empty identity

Temporary network loss
  → Socket.IO disconnect
  → RecoveryExperience.onDisconnect
       if LOBBY|prep|gameplay:
         hadDisconnect = true
         status = RECONNECTING   ← overlay shows "Reconnecting…"
  → (no hard timeout on RECONNECTING)

Reconnect success (Manager reconnect → "connect")
  → RecoveryExperience.onConnect
       if hadDisconnect && (LOBBY|prep|gameplay):
         requestSessionRecovery()
         hadDisconnect = false

requestSessionRecovery()
  → if !hasGameplayIdentity(roomId+playerId) OR recoveryInFlight:
         return          ← ★ does NOT clear RECONNECTING
  → else:
         recoveryInFlight = true
         status = RECONNECTING
         emit SESSION_RECOVERY_REQUEST

Server (SocketGateway + RoomLobbyBridge.reconnectSession)
  → reclaim seat / rebound socket
  → maybe SETUP_SESSION_SYNC (only if Setup Session payload exists)
  → resolveRecoveryRoute:
       setupActive     → PRE_GAME_SUCCESS (return; no SESSION_SNAPSHOT)
       !gameId         → FAIL "No active gameplay session for recovery"
       gameState/cache → GAMEPLAY_SNAPSHOT
       else            → PRE_GAME_SUCCESS (ENTRY_PAYMENT / not initialized)

Client clear paths for Reconnecting
  → SETUP_SESSION_SYNC + isSetupRecoveryPage → COMPLETE → soft hide → IDLE
  → SESSION_SNAPSHOT (gameplay pages) → RESTORING → COMPLETE → hide
  → SESSION_RECOVERY_FAILED → FAILED → soft hide → IDLE
  → ★ No path: connect + IDLE when recovery is unnecessary
  → ★ No timeout while status === RECONNECTING
```

## 3. Finding 1 — Reconnecting state owner

| Field | Value |
|--------|--------|
| **File** | `client/src/context/RecoveryExperienceContext.jsx` |
| **Component/Context** | `RecoveryExperienceProvider` / `useRecoveryExperience` |
| **UI** | `client/src/components/RecoveryOverlay.jsx` |
| **Message** | `mapRecoveryStatusMessage` → `"Reconnecting…"` (`client/src/game/sessionRecovery/recoveryFlow.js`, `RECOVERY_UI_STATUS.RECONNECTING`) |
| **State variable** | `status` (`useState`) |
| **Setter** | `setStatus(RECOVERY_UI_STATUS.RECONNECTING)` |
| **Trigger events** | (1) `socket` `disconnect` while `isSetupRecoveryPage(currentPage)` **includes LOBBY** or gameplay page; (2) `requestSessionRecovery()` when identity exists; (3) welcome boot recovery when restoring setup page |
| **Clear conditions** | `SETUP_SESSION_SYNC` → `handleSetupRecoveryComplete` → COMPLETE → hide; gameplay `SESSION_SNAPSHOT` path → COMPLETE; `SESSION_RECOVERY_FAILED` → FAILED → hide; `hideOverlay` / soft-hide timer → IDLE. **Hard max overlay timer applies only to COMPLETE / RESTORING — not RECONNECTING.** |

**Note:** `SocketSyncLayer` also has a `RECONNECTING` connection status on `reconnect_attempt`. That does **not** render the RoomLobby overlay string.

## 4. Finding 2 — Socket lifecycle before room creation

| Step | What happens |
|------|----------------|
| Sets reconnecting | `disconnect` on LOBBY (page 2) always sets overlay RECONNECTING (identity optional). |
| Clears reconnecting | Only recovery completion / failure / hide — **not** bare `connect`. |
| Reconnect can succeed while UI stuck | **Yes.** Ads + `socket.connected` can be true while `status === RECONNECTING`. |

### Primary stuck path (matches “room not created yet”)

1. User on RoomLobby **before** `roomCreated` / `roomJoined` → **no** `roomId`+`playerId`.
2. Brief disconnect → overlay **RECONNECTING**.
3. Socket reconnects → `onConnect` calls `requestSessionRecovery()`.
4. Early return: `!hasGameplayIdentity(identity)` → **no emit, no clear**.
5. `hadDisconnectRef` still set `false` → later connects won’t retry clear.
6. Overlay stays **RECONNECTING** indefinitely (no RECONNECTING timeout).

### Secondary stuck path (room joined, waiting for players / startGame)

1. Identity exists; Setup Session usually **not** started → no `SETUP_SESSION_SYNC`.
2. `requestSessionRecovery` → inFlight true → RECONNECTING.
3. Server reclaim OK → `setupActive=false`, `gameId=null` → `FAIL` → client should show FAILED then hide (**not** permanent Reconnecting), *if* `SESSION_RECOVERY_FAILED` is received.
4. **Race on flaky mobile:** inFlight true → second disconnect/connect → `requestSessionRecovery` no-ops while status stays RECONNECTING; response for the first request may be lost with the old socket → **stuck RECONNECTING**.

### Tertiary path (R17.8B gap)

If server returns `PRE_GAME_SUCCESS` **without** emitting `SETUP_SESSION_SYNC` / `SESSION_SNAPSHOT` / `SESSION_RECOVERY_FAILED`, client leaves `recoveryInFlight=true` and status **RECONNECTING** forever (no timeout).

- `setupActive=true` normally emits sync when `buildSyncPayload` exists.
- `ENTRY_PAYMENT` / `GAME_NOT_INITIALIZED` PRE_GAME_SUCCESS is later than pure lobby waiting, but same client gap applies.

## 6. Finding 4 — Advertising vs RoomLobby transport

```text
Advertising transport:  Same Socket.IO client (`socket` singleton)
                        Channels: advertisement:message / ADVERTISEMENT_CHANGED / SYNC_RESPONSE
RoomLobby transport:    Same Socket.IO client
                        Lobby events (roomCreated, roomJoined, startGame, …)
                        Recovery: game:message + SETUP_SESSION_SYNC
Shared or separate:     SHARED socket; SEPARATE application channels / UI state machines
```

Ads ignore `RecoveryExperience` status. As soon as the socket is connected again, rotation broadcasts keep all devices in sync — including devices stuck on the overlay.

## 8. Answers to audit questions

1. **Can Socket.IO be connected while RoomLobby displays "Reconnecting"?**  
   **Yes.** Overlay is independent of `socket.connected`; ads prove the transport can be live.

2. **Can reconnect happen without clearing the UI state?**  
   **Yes.** Successful `connect` does not set IDLE. Clear requires recovery protocol messages or FAILED/COMPLETE hide paths. Missing identity or `recoveryInFlight` short-circuit leaves RECONNECTING set.

3. **Why do advertising events continue during the problem?**  
   Same reconnected socket; ad channel does not consult recovery overlay status.

4. **Frontend state machine or server issue?**  
   **Primarily client-side recovery UI state machine.** Server may contribute (silent PRE_GAME_SUCCESS / lost recovery response), but observed “ads sync + Reconnecting” is explained without a dead server connection.

## 9. Root cause candidates (ranked)

| Rank | Candidate | Why it fits |
|------|-----------|-------------|
| **1** | LOBBY disconnect → RECONNECTING; reconnect with **no identity** → `requestSessionRecovery` no-op → never IDLE | Matches “before room created”; socket can be healthy; ads sync. |
| **2** | `recoveryInFlight` blocks re-request after flaky multi-disconnect; first response lost | Fits unstable mobile; identity present after join. |
| **3** | Silent `PRE_GAME_SUCCESS` (R17.8B) with no client-clearing event | Stuck RECONNECTING + inFlight; more likely after setup/payment than empty lobby. |
| **4** | Lobby+identity → FAIL path works but user mis-labels FAILED toast | Less likely if text is specifically “Reconnecting…”. |

**Hypothesis (best fit for this report):**  
RoomLobby treats transient Socket.IO disconnect as a recovery session that **must** complete via reclaim/sync, but before room join (and in several reclaim edge cases) **nothing clears** `RECOVERY_UI_STATUS.RECONNECTING`. Advertising continues because it only needs the shared socket.

---

## 10. Recommended fix direction (do not implement in this stage)

1. **On connect after disconnect on LOBBY:** if `!hasGameplayIdentity`, set status **IDLE** immediately (no recovery request).
2. **On connect:** if recovery is unnecessary or identity missing, never leave RECONNECTING sticky when `socket.connected`.
3. **Always clear or re-arm on connect:** if `recoveryInFlight` and socket reconnected, either reset inFlight and re-emit, or treat connect as cancel of stale inFlight for pre-game lobby.
4. **Add a RECONNECTING max timeout** (or “connected ⇒ IDLE if no in-flight request”) so overlay cannot block forever.
5. **Server pairing (optional):** for lobby reclaim with no Setup Session, emit an explicit success/ack the client maps to IDLE (or keep FAIL but ensure client never stays on RECONNECTING). Prefer client fix #1–4 first.
6. **Do not** change Recovery Snapshot / Game Engine for this symptom.

## 13. R17.8F — Implemented fix

**Date:** 2026-08-14  
**Scope:** Frontend state machine only (no server / gameplay / payment / TON changes).

### Before / after

```text
BEFORE
  disconnect → RECONNECTING
  connect    → requestSessionRecovery()
                 └─ no identity → return (status stays RECONNECTING forever)
                 └─ stale recoveryInFlight → return (blocked forever)
  RECONNECTING → no timeout

AFTER (R17.8F)
  disconnect → RECONNECTING (+ 15s cap timer)
  connect    → resolvePostReconnectAction()
                 ├─ CLEAR_TRANSPORT_ONLY (no identity)
                 │     → IDLE, reset inFlight, no SESSION_RECOVERY_REQUEST
                 └─ REQUEST_SESSION_RECOVERY (identity present)
                       → reset stale inFlight, then existing reclaim flow
  RECONNECTING timeout → IDLE + clear inFlight (identity untouched)
```
