## 4. Recovery Data Discovery

### RecoveryDataPersistence current API (source-verified)

| Method | Behavior |
|---|---|
| `createRecoveryRecord(payload, metadata)` | Validates payload (`_validateRecoveryPayload`: throws on missing identity/configuration/gameplay-state fields, bad versions, configurationHash mismatch, forbidden financial-authority duplication), builds envelope metadata, delegates to `TonFinancialPersistence.createRecoveryDataRecord`. |
| `loadRecoveryRecord(recordId)` | Loads by record ID (JSDoc: "typically the gameId"); re-validates via `validateRecoveryRecord`; returns `null` on `RecordNotFoundError`; **throws `CorruptedRecordError`** on checksum/version/structure failure. |
| `listRecoveryRecords()` | Delegates to `listActiveRecoveryDataRecords()` (ACTIVE envelopes only — terminal `TERMINAL`/`SETTLED`/`FAILED_CLOSED` records are excluded by storage semantics) and **filters out invalid records with an error log** (skip, not throw). |
| `updateRecoveryRecord(recordId, …)` | Validates, rejects immutable (terminal-status) records with `ImmutableRecordError`. |
| `validateRecoveryRecord(record)` | Pure validation: envelope checksum, schema version, recoveryContractVersion ≤ 1, required identity fields (`recoveryRecordId, roomId, gameId, contractId, paymentSessionId, tonNetwork`), required configuration fields (`configuration, configurationHash, configurationVersion, traceSeed, snapshotHash`) + configurationHash recomputation, gameplay-state fields (`gameState, gameStatus, serverTimestampAtCheckpoint`), players array with per-player required fields (incl. `playerIndex`), clock-state fields for non-terminal records (`phaseStartedAt, clockStartedAt, clockPaused, clockTotalPausedMs, awaitingResultActivation, resultPhaseStarted`), terminal-physics fields for terminal records (`physicsFinalAngle, physicsFinalTriangleAngle, physicsSimulationState`), and rejection of any duplicated financial-authority field. |

### Get-by-room / get-by-game behavior

- **Not present.** Lookup is by `recordId` only. Because the record ID is conventionally the `gameId`, get-by-game is achievable via `loadRecoveryRecord(gameId)`; get-by-room requires scanning `listRecoveryRecords()` and matching `payload.roomId`. D3 does not need new persistence methods.

### Can discovery be performed entirely through RecoveryDataPersistence?

**Yes.** `listRecoveryRecords()` returns every valid ACTIVE recovery record with its full payload. Corrupted records are skipped-and-logged by design (they cannot be classified safely → they are effectively `INVALID`/invisible; if explicit `INVALID` accounting is desired, D3 may additionally call `loadRecoveryRecord(id)` per known id, catching `CorruptedRecordError`). No direct filesystem access is required or permitted.

### Must D3 interact with TonFinancialPersistence?

- **For reconstruction: no.** Every field D3 needs is inside the recovery payload, including financial *references* (`contractId`, `paymentSessionId`, `snapshotHash`, `winnerId`).
- **Winner validation:** the payload carries `winnerId`. Comparing the silently restored winner against `payload.winnerId` is a **payload-local, read-only** check D3 may perform. Cross-checking against the live `SETTLEMENT` record would require `TonFinancialPersistence` reads — this belongs to a **later financial reconciliation stage**, not D3.
- **Boundary preserved:** financial authority fields (`paymentStatus`, `paidAmount`, `confirmationStatus`, `refundTxHash`, `settlementTransactionHash`, `prizeAmount`, `organizerAmount`, `totalPot`, `requiredGram`) are structurally forbidden in recovery payloads (enforced by persistence) and must remain invisible to D3 decision-making. D3 never reads, writes, or derives financial truth.

## 5. Recovery Candidate Classification

Using **only fields that currently exist** in the payload/envelope:

| Class | Exact criteria (source-derived) |
|---|---|
| `INVALID` | Fails `validateRecoveryRecord` (checksum, versions, missing fields, configurationHash mismatch, forbidden financial duplication), or `loadRecoveryRecord` throws `CorruptedRecordError`, or unsupported future `recoveryContractVersion`. |
| `ALREADY_RECOVERED` | Runtime check, not persistence: `GameManager.hasGame(gameId)` true (or `RoomManager.hasRoom(roomId)`), i.e., a previous successful/partial reconstruction exists. |
| `ALREADY_TERMINAL` | `gameStatus === "FINISHED"` or `"DESTROYED"` — gameplay lifecycle already concluded; nothing to reconstruct. |
| `FINANCIAL_ONLY` | Envelope `record.status ∈ {"SETTLED","FAILED_CLOSED","TERMINAL"}` where gameplay runtime is unnecessary (settled/refund-closed games). Note: `listRecoveryRecords()` already excludes terminal-status envelopes from ACTIVE listing, so this class mostly arises from explicit `loadRecoveryRecord` probes or future listing changes. |
| `EXPIRED` | Non-terminal record, `clockPaused === false`, and `phaseStartedAt + durationMs(phase) <= serverTimestampAtCheckpoint` (authoritative deadline already passed at checkpoint) — or, equivalently at recovery time, `<= Date.now()`. Duration comes from the persisted `configuration.timers[gameState].durationMs` (never the live catalog when versions differ). |
| `PRE_GAME_RECOVERABLE` | `gameState ∈ {"PRE_GAME_READY","READY"}`; `clockPaused === false`; not `EXPIRED`; exactly 3 players with unique in-range `playerIndex` values `{0,1,2}`; configuration validates; no terminal physics expected. |
| `TERMINAL_RESULT_RECOVERABLE` | `gameState === "RESULT"`; `physicsSimulationState === "STOPPED"`; `physicsFinalAngle` and `physicsFinalTriangleAngle` finite numbers; configuration validates; winner restorable and (if present) matching payload `winnerId`. |
| `NOT_RECOVERABLE` | Everything else under the current contract, specifically: `gameState ∈ {"SELF_TEST","SPEED","BRAKE"}` (active physics/input state absent by design); `clockPaused === true` (exact pause timing not persisted — `pauseStartedAt`/remaining-time gap proven in the D2 audit); missing active physics/command state; identity conflicts (roomId/gameId/player-set inconsistencies across payload fields); invalid configuration. |

Classification uses no new gameplay states, no new GameState values, and no persistence changes. `gameStatus` participates only via `ALREADY_TERMINAL` (FINISHED/DESTROYED); `RUNNING`/`INITIALIZED`/`CREATED`/`READY` gameStatus values are consistent with active gameplay records and do not by themselves block classification (the authoritative phase signal is `gameState`).

## 6. Safe Recovery Set (verified against D1+D2 implementations)

SAFE (eligible for full reconstruction):
- `PRE_GAME_READY` — config attach + state attach + unarmed clock + default input registry + CREATED physics; arm clock after validation if non-expired.
- `READY` — same as above (input registry included; still no active motion).
- `RESULT` with terminal STOPPED physics — config + state(RESULT) + STOPPED physics with exact final angles + silent winner restore; **no clock attach required** (terminal records carry no clock-state requirement) and **no arming** (RESULT is terminal-invalid for arming per D2).

FAIL CLOSED (evidence-backed):
- `SELF_TEST`, `SPEED`, `BRAKE` — active physics/input/tick history not persisted (D2 audit §3.4/§3.5 feasibility tables); D2 `attachSimulation` rejects RUNNING/BRAKING; D2 `attachRegistry` rejects non-empty queues.
- Paused clock without exact recoverable timing — `pauseStartedAt`/persisted remaining absent (D2 audit §4.3 gaps); D2 `armRecoveredClock` refuses paused clocks.
- Expired unpaused phase — D2 refuses at attach (checkpoint-relative) and at arm (wall-clock-relative).
- Missing active physics state / command state — structural consequence of the contract.
- Conflicting identity — D1/D2 duplicate-conflict detection fails closed.
- Invalid configuration — hash/structure validation fails closed.
- Corrupted recovery record — persistence validation fails closed.

This set is identical to the D2 audit verdict; no expansion is proposed.

## 8. Construction of Aggregates

### Room
- Constructor: `new Room({ roomId, createdAt, status, maxPlayers, players })`.
- From payload: `roomId` (required identity field); `players` = playerIds ordered by `playerIndex` (ascending); `maxPlayers = 3` (= players.length; WheelWin is exactly-3-player); `status = ROOM_STATUS.FULL` (derivable: players.length === maxPlayers — derivation, not invention).
- `createdAt`: **not persisted anywhere in the contract.** Safe value: `null` (the field is nullable). Setting `Date.now()` or the checkpoint time would fabricate history — rejected.
- Never generated: `roomId`.

### Player
- Authoritative D1 API preserved: `PlayerManager.attachPlayer(player)` where `player = { playerId, playerIndex, identity, runtime }` (correction-report shape; the legacy `attachPlayer(identity, runtime)` is superseded and must NOT be used).
- `identity = new PlayerIdentity({ playerId, nickname, wallet, icon, age, color, colorSector2, sectorCount, sectorArrangement, baseStake, createdAt })` — every field except `createdAt` is in `REQUIRED_PLAYER_FIELDS` and comes verbatim from the payload. `createdAt` is not persisted → `null` (nullable; honest absence).

### Game
- Constructor: `new Game({ gameId, roomId, createdAt, status, players, metadata })`.

## 10. Atomicity / Rollback (CRITICAL)

D1/D2 provide **local** atomicity only (each attach validates fully before mutating; failures leave that engine clean). There is **no multi-component transaction**. D3 must therefore define rollback for failures after step 5.

### Existing removal APIs — event behavior (source-verified)

| Component | Removal API | Silent? | Evidence |
|---|---|---|---|
| RoomManager | `destroyRoom(roomId)` | **NO** | Emits `ROOM_DESTROYED`; prints forensics block; calls `setupSessionLifecycle.abortForRoom`; clears `_playerRoomIndex` and listeners. No silent remove exists. |
| GameManager | `destroyGame(gameId)` | **NO** | Emits `GAME_DESTROYED`; clears pending maps; removes listeners. No silent remove exists. |
| PlayerManager | `removePlayer(playerId)` | **NO** | Emits `PLAYER_REMOVED`. No silent remove exists. |
| ConfigurationEngine | `removeConfiguration(gameId)` | **NO** | Emits `CONFIGURATION_REMOVED`. |
| GameStateEngine | `removeState(gameId)` | **YES** | Logs only; deletes from `_states`. |
| GameClockEngine | `removeClock(gameId)` | **Conditional** | Calls `stopClock` only `if (record.running)`; an unarmed attached clock (`running=false`) is deleted **silently**. An armed clock emits `CLOCK_STOPPED`. |
| PhysicsEngine | `removeSimulation(gameId)` | **YES for D2 shapes** | Calls `stopSimulation` only for RUNNING/BRAKING; D2-attached simulations are CREATED/STOPPED ⇒ deletion is silent. |
| InputAuthority | `removeGame(gameId)` | **YES** | Deletes registry + speed-closed flag; no events. |
| WinnerEngine | `removeResult(gameId)` | **NO** | Emits `GAME_RESULT_REMOVED`. However, `restoreResult` failure paths already leave `_results` empty, so rollback is usually unnecessary. |

### Danger analysis of rollback emissions

None of the rollback-emitted events (`ROOM_DESTROYED`, `GAME_DESTROYED`, `PLAYER_REMOVED`, `CONFIGURATION_REMOVED`, `CLOCK_STOPPED`, `GAME_RESULT_REMOVED`) directly starts WinnerActivation, ResultActivation, settlement, or financial actions (those consume `PHYSICS_STOPPED`, winner/result-ready events, and `GAME_STATE_CHANGED(RESULT)` — none of which rollback emits, provided D3 never calls `stopSimulation`/`resolveResult` during rollback). **However**, these events are consumed by operational/session consumers (session lifecycle, cleanup, diagnostics, reconnect-adjacent listeners), so rollback emissions can cause observable side effects (forensics noise, listener churn, potential session bookkeeping). This is a real, bounded exposure — not a financial hazard.

### Blocker statement

**Safe fully-silent multi-component rollback is NOT currently possible** with existing public APIs for Room, Game, Player, Configuration, and Winner. Two architecturally clean resolutions exist for the D3 implementation stage (decision required before implementation):

- **Option A (recommended):** add minimal **silent detach helpers** alongside the existing attach APIs — e.g., `RoomManager.detachRoom(roomId)`, `GameManager.detachGame(gameId)`, `PlayerManager.detachPlayer(playerId)`, `ConfigurationEngine.detachConfiguration(gameId)` (delete without `CONFIGURATION_REMOVED`), `WinnerEngine.detachResult(gameId)` — mirroring the silent D1/D2 attach pattern. This touches the three managers + two engines additively (same pattern D1/D2 established) and keeps rollback event-free.
- **Option B:** accept rollback via existing removal APIs, documenting that a failed candidate's rollback emits removal-class events (never gameplay-transition events). Simpler, zero new APIs, but operationally noisy and dependent on consumer tolerance.

Under **no circumstances** may rollback invoke: `PhysicsEngine.stopSimulation` (emits `PHYSICS_STOPPED` → WinnerActivation), `WinnerEngine.resolveResult`, `GameClockEngine.stopClock` on unrelated clocks, `GameManager.finishGame`, or any settlement/payment path.

### Failure-point matrix (summary)

Failure after… → rollback scope:
- Room attach → detach room.
- Player attach(s) → detach players + room.
- Game attach → detach game + players + room.
- Configuration attach → + detach configuration.
- GameState attach → + `removeState` (silent).
- Clock attach → + `removeClock` (silent while unarmed).
- Input attach → + `removeGame` (silent).
- Physics attach → + `removeSimulation` (silent for D2 shapes).
- Winner restore failure → nothing to roll back (registry untouched by design).
- Final validation failure → full rollback of everything attached for the candidate.
- Arming failure → clock remains attached-unarmed; either report FAILED_EXPIRED and roll back fully, or (policy decision) keep the validated dormant candidate. Default recommendation: full rollback for consistency; dormancy is a separate approved policy.

Rollback itself must be best-effort-complete: if a rollback step fails, the candidate is reported `FAILED_ROLLBACK` and the residual state is logged for operator attention (no silent partial-liveness: nothing was armed/registered, so residue is inert).

## 11. Idempotency / Retry

Definitions (no persistent status values invented; idempotency derives from runtime registry state + envelope status):

- **Called twice for the same recoveryRecordId / gameId:**
  - Prior full success → second call detects `GameManager.hasGame(gameId)` ⇒ result `ALREADY_RECOVERED` (skip). Optional deep check: engine registries contain equivalent state (D2 idempotent-equivalent semantics confirm equivalence cheaply).
  - Prior partial failure with residue → per-step re-run: D2 attach APIs return idempotent success for **equivalent** existing state, so a retry can proceed through the same sequence; any **conflicting** existing state ⇒ fail closed (`FAILED_*` of the offending step) — never overwrite.
- **Already reconstructed room/game exists but identities differ** (different payload for same ids) ⇒ `FAILED_IDENTITY` (conflict), fail closed.
- **Cleanup-and-retry policy:** recommended default is rollback-then-report (candidate not retried automatically within the same run); a subsequent `recoverAll()` may retry the record from scratch because rollback removed all residue. Automatic in-process retry loops are discouraged (mask systemic faults).
- **Skip because already recovered** is the correct treatment of `ALREADY_RECOVERED`; it is a success-class outcome, not an error.
- Equivalent-engine-state short-circuit: for repeat calls, D2 idempotency means steps 10–15 can be re-invoked harmlessly; steps 5/6/9 (manager attaches) are NOT idempotent (duplicates return null) — hence the `hasRoom`/`hasPlayer`/`hasGame` pre-checks must map "already present + identity-consistent" to idempotent-success rather than failure.

## 12. Recovery Result / Activation Boundary

After successful reconstruction:

- **Recovered-flag:** no `isRecovered` (or similar) field exists on `Room`/`Game`/`PlayerIdentity`/`PlayerRuntime` (constructors verified). D3 must NOT add one. Recovered state is implicit: components are present in the existing registries. If marking is ever required, `Game.metadata` (existing free-form field) is the only schema-compatible carrier — but even that is deferred: D3 should return the outcome in its **result object** only.
- **Clock arming:** yes — exactly per D2: only eligible, non-expired, unpaused PRE_GAME_READY/READY clocks, only after full cross-engine validation, creating exactly one timeout. RESULT candidates: never armed (no clock attached; terminal-invalid).
- **SimulationLoop:** untouched. Zero registration. (Membership normally arises only from `PHYSICS_STARTED`, which D3 never emits.)
- **Sockets:** not opened, not touched.
- **Events:** D3 should emit **nothing** during reconstruction. If a distinct recovery-completion signal is later desired, the existing `RECOVERY_STARTED`/`SESSION_RECOVERED` types exist in `EventTypes` — adopting them is a separate, explicitly-approved decision (they currently have reconnect-domain semantics via RecoveryEngine). Default: silent + structured logger summary per candidate.
- **Playable?** A recovered PRE_GAME_READY/READY candidate is *visible* through standard getters but is **not fully playable**: sockets/sessions are not bound, players are `IDLE`/`DISCONNECTED` in PlayerRuntime, and no client has been notified. Treat as **dormant until a later reconnect-integration stage** activates it. A recovered RESULT candidate is terminal: its purpose is audit/financial-continuation correctness, not playability.

## 13. Startup Boundary

- **D3 can be implemented fully independently of startup integration.** The orchestrator is a plain class with injected dependencies; unit/integration tests construct the full graph manually (as existing engine tests do).
- **Where `recoverAll()` belongs (future, not implemented):** in `app.js` after (a) all managers/engines are constructed and initialized, (b) `RecoveryDataPersistence` is instantiated over the shared `TonFinancialPersistence`, and (c) `TonFinancialRecovery.recover()` has completed (financial state first, gameplay second — mirrors the D2-audit ordering rationale). Concretely: between the current `TonFinancialRecovery` startup line and `SocketGateway` connection-acceptance.
- **Must startup wait for recovery before…**
  - Socket.IO accepts connections: **yes** — otherwise clients may join/reference rooms mid-reconstruction. The existing `RoomManager.attachLifecycleGate` drain mechanism (`isAcceptingNewWork`) is a ready-made gate pattern for "hold new work until recovery completes."
  - SessionManager starts: **yes** (sessions bind to rooms/games).
  - Normal game creation becomes available: **yes** (same gate).
- None of this is implemented or proposed-for-implementation in this audit beyond locating the seam.

## 14. Financial Boundary (verified)

D3 does **not** own, read, or derive: `paymentStatus`, `paidAmount`, `confirmationStatus`, refund state, settlement state, `prizeAmount`, `organizerAmount`, `totalPot`, `requiredGram`. These are structurally excluded from recovery payloads (`FORBIDDEN_FINANCIAL_AUTHORITY_FIELDS`) and financially owned by `TonFinancialPersistence`.

D3 merely **preserves** reference identifiers present in the payload: `contractId`, `paymentSessionId`, `snapshotHash`, `contractAddress` (if carried), `tonNetwork`, `correlationId`, and `winnerId` (used only for the payload-local winner cross-check in §9). It performs no writes to any financial record and issues no chain operations.

Read-only validation split:
- In D3: winner-vs-`payload.winnerId` (payload-local).
- Later financial reconciliation stage: live `SETTLEMENT`/`GAME_CONTRACT` cross-checks, escrow/status consistency, settlement continuation.

## 15. Reconnect Boundary (analysis only)

- **Lookup sufficiency:** the reconnect path resolves rooms via `RoomManager.getRoom/hasRoom` and games via `GameManager.getGameIdByRoomId(roomId)` / `hasInitializedGameplay(roomId)` (true when a non-CREATED/non-DESTROYED game exists for the room). A successfully reconstructed Room (status FULL) + Game (status from payload, e.g., RUNNING) **is sufficient for lookup visibility**.
- **What reconnect still expects beyond D3:** bound sockets/sessions (`SessionWalletStore` wallet sessions), PaymentSession domain data, `RecoverySnapshotCache` snapshots for state resync, players in `PLAYING` state for SPEED input validation (D2 `attachRegistry` deliberately does not mutate PlayerManager, so recovered players remain `IDLE` — acceptable because PRE_GAME_READY/READY accept no input, but a reconnect flow that resumes into SPEED would need a later-stage, explicitly-approved player-state policy), and client notification of the recovered session.
- These requirements belong to a **later reconnect-integration stage**; D3 neither implements nor blocks them.

## 18. Failure Model (transient orchestration result categories)

Per-candidate results returned by the orchestrator (in-memory only; no new persistence statuses):

- `SUCCESS` — fully reconstructed (+ armed when eligible).
- `ALREADY_RECOVERED` — runtime already contains an identity-consistent reconstruction.
- `SKIPPED_NOT_RECOVERABLE` — classified SELF_TEST/SPEED/BRAKE or other NOT_RECOVERABLE (structural, permanent under current contract).
- `SKIPPED_FINANCIAL_ONLY` — settled/failed-closed/already-terminal; gameplay reconstruction unnecessary.
- `FAILED_INVALID_RECORD` — corrupted/fails persistence validation/incompatible version.
- `FAILED_IDENTITY` — roomId/gameId/player-set/index conflicts.
- `FAILED_CONFIGURATION` — hash/structure/catalog incompatibility.
- `FAILED_STATE` — invalid state/timestamps/state-clock mismatch.
- `FAILED_CLOCK` — expired, paused-without-exact-timing, timer mismatch, arm refusal.
- `FAILED_PHYSICS` — shape violation (non-CREATED/STOPPED, non-zero motion, missing terminal angles).
- `FAILED_INPUT` — player-set/queue violations.
- `FAILED_WINNER` — resolution failure or payload-`winnerId` mismatch.
- `FAILED_CONSISTENCY` — cross-engine validation failure.
- `FAILED_ROLLBACK` — rollback itself incomplete (residue logged; inert).
- `FAILED_EXPIRED` — explicit expired-deadline outcome (clock left unarmed).

Each result carries `recoveryRecordId`, `gameId`, `roomId`, classification, failed step, and reason string. No persistence writes.

## 19. Validation Strategy (future D3 tests — NOT implemented now)

1. Successful `PRE_GAME_READY` recovery (full attach set + arming; zero events; zero loop registration).
2. Successful `READY` recovery (incl. input registry).
3. Successful `RESULT` recovery (STOPPED physics + deterministic winner == payload.winnerId; no clock; no arming).
4. `SELF_TEST` fail closed (`SKIPPED_NOT_RECOVERABLE`).
5. `SPEED` fail closed.
6. `BRAKE` fail closed.
7. Expired clock fail closed (`FAILED_EXPIRED`; clock unarmed or rolled back; no timeout alive).
8. Paused-clock fail closed (no pause-history invention).
9. Duplicate game detection (`ALREADY_RECOVERED`; second call makes no mutations).
10. Identity mismatch (roomId/gameId/player-set/playerIndex) → `FAILED_IDENTITY`, clean rollback.
11. Configuration mismatch (hash tampering) → `FAILED_CONFIGURATION`.
12. State/clock phase mismatch → `FAILED_STATE`/`FAILED_CONSISTENCY`.
13. Terminal physics mismatch (RUNNING payload, non-zero motion, missing angles) → `FAILED_PHYSICS`.
14. Winner mismatch vs payload `winnerId` → `FAILED_WINNER`.
15. Failure injection at every orchestration step (steps 5–17) → assert: no armed timeout survives, no SimulationLoop membership, no stale engine entries, unrelated pre-existing games untouched, retry cannot double-register.
16. Rollback cleanliness (with Option A: zero events during rollback; with Option B: only documented removal-class events).
17. Retry/idempotency (equivalent re-run succeeds idempotently; conflicting re-run fails closed).
18. Zero normal gameplay event replay across whole recovery run (counter harness as in D2 tests).
19. Zero SimulationLoop registration (loop spy / absence of `PHYSICS_STARTED`).
20. Zero financial side effects (no TonFinancialPersistence write-method invocations — spy/assert).

## 20. Final Verdict

### D3 Feasibility

**FEASIBLE WITH BLOCKERS**

### TRUE BLOCKERS

1. **No fully-silent multi-component rollback.** Existing removal APIs for Room (`destroyRoom` → `ROOM_DESTROYED` + forensics + setup-session abort), Game (`destroyGame` → `GAME_DESTROYED`), Player (`removePlayer` → `PLAYER_REMOVED`), Configuration (`removeConfiguration` → `CONFIGURATION_REMOVED`), and Winner (`removeResult` → `GAME_RESULT_REMOVED`) emit events; GameState/Clock(unarmed)/Physics(D2 shapes)/Input removals are silent. Rollback emissions never trigger gameplay/financial activations, but they are observable to session/operational consumers. Resolution required before implementation: approve Option A (additive silent `detach*` helpers on the three managers + Configuration/Winner engines, mirroring the D1/D2 pattern) or accept Option B (documented removal-event exposure). Neither option modifies schemas, ownership, or normal-path behavior.
2. **No production recovery records / no production `RecoveryDataPersistence` instantiation.** Identical to the D2 blocker: D3 can be built and fully tested against synthetic records, but end-to-end restart recovery remains impossible until a later stage wires checkpoint writing. This blocks *use*, not *implementation*.

### NON-BLOCKING LIMITATIONS (remain outside D3)

- Paused-clock exactness gap (`pauseStartedAt`/remaining not persisted) → paused candidates fail closed.
- Winner historical `resolvedAt`/full-result not persisted → outcome-only restoration (`resolvedAt: null`).
- Historical economy object not persisted → `_economies` stays empty for recovered games.
- Active SELF_TEST/SPEED/BRAKE state absent by design → permanently unrecoverable under this contract.
- Reconnect depth (sockets, sessions, PLAYING player states, client notification) → later stage.
- Startup gating mechanics → later stage (seam documented in §13).
- Live SETTLEMENT cross-validation → later financial reconciliation stage.

### EXACT D3 IMPLEMENTATION SCOPE (authoritative list)

Create `server/recovery/RecoveryOrchestrator.js` (new file) implementing: candidate discovery + classification + aggregate construction + ordered D1/D2 attach invocation + orchestrator-owned cross-validation + rollback + idempotency + result reporting (`recoverAll()`, `recoverCandidate(recordId)`). Plus, contingent on the §10 decision: additive silent `detach*` helpers in `RoomManager`, `GameManager`, `PlayerManager`, `ConfigurationEngine`, `WinnerEngine` (Option A). Plus focused tests under `server/tests/`. Nothing else. No changes to persistence schema, startup, financial, reconnect, socket, client, SimulationLoop, gameplay phase definitions, or the D1/D2 attach API semantics.

### EXPECTED RECOVERY BEHAVIOR (per state)

| State | Behavior |
|---|---|
| `PRE_GAME_READY` | **recover** — full attach set (config, state, unarmed clock, default input registry, CREATED physics); arm clock after validation if non-expired/unpaused; dormant until reconnect stage. |
| `READY` | **recover** — same as PRE_GAME_READY (input registry included; still no active motion). |
| `SELF_TEST` | **fail closed** — `SKIPPED_NOT_RECOVERABLE` (active physics not persisted). |
| `SPEED` | **fail closed** — `SKIPPED_NOT_RECOVERABLE` (active physics + input + tick history not persisted). |
| `BRAKE` | **fail closed** — `SKIPPED_NOT_RECOVERABLE` (brake elapsed/start-omega/angles not persisted). |
| `RESULT` | **recover, terminal-only** — config + state(RESULT) + STOPPED physics with exact final angles + silent winner restore validated against payload `winnerId` when present; no clock attach/arming; no input registry; dormant (audit/financial-continuation relevance). |
| `EXPIRED` (unpaused expired deadline) | **fail closed** — `FAILED_EXPIRED`; clock never armed; no clamping, no catch-up, no missed-event replay. |
| `INVALID` (corrupted/version/structure/hash failure) | **fail closed** — `FAILED_INVALID_RECORD`; zero runtime mutation. |
| `SETTLED` (envelope SETTLED/FAILED_CLOSED/TERMINAL, or gameStatus FINISHED/DESTROYED) | **skip as financial-only** — `SKIPPED_FINANCIAL_ONLY` / `ALREADY_TERMINAL`; gameplay reconstruction unnecessary; financial recovery owns continuation. |
