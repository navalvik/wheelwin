# R17.8A — Recovery Snapshot Availability Audit

**Mode:** Investigation only (no code changes)  
**Date:** 2026-08-14  
**Symptom:** `SESSION_RECOVERY_REQUEST` → `Recovery snapshot is unavailable`  
**Scope:** Server-side recovery / session persistence (RecoveryEngine, SocketGateway, RoomLobbyBridge, RecoverySnapshotCache)

---

## 2. Snapshot Lifecycle (by phase)

| Phase | Recovery state available? | Snapshot created? | Snapshot updated? |
|-------|---------------------------|-------------------|-------------------|
| **PLAYER_CONNECTED / ROOM_CREATED** | Seat/identity only | No | No |
| **ROOM_FULL** | Lobby maps | No | No |
| **SETUP_SESSION** (Page2–Matrix–Verify) | SetupSession + reclaim maps | No RecoveryEngine snapshot | Lobby `SETUP_SESSION_SYNC` only |
| **GAME_CREATED** (after Setup complete) | `gameId` mapped; input registered; physics sim created; clock **created** (not started); **gameState not initialized** | Cannot build (fails validation) | No |
| **Profiles / WHEEL_CONFIGURATION** | Configuration may appear | Still blocked if gameState missing | No |
| **TON_CONNECT / PAYMENT** (before `ENTRY_PAYMENT_COMPLETED`) | Lobby payment/wallet sessions + optional Setup reclaim | **RecoveryEngine cannot build** (`gameState` missing) | Cache empty |
| **ENTRY_PAYMENT_COMPLETED → GAME_INITIALIZED** | gameState + clock started | **Can build** if all sources present | Built on-demand on recover |
| **PRE_GAME_READY / READY / SELF_TEST / SPEED / BRAKE** | Full live engines | On-demand build OK | On-demand rebuild each recover |
| **RESULT** | Live + **cache capture** | Cache stores frozen snapshot | Payment/audit refresh on events |
| **OPEN_PAGE6** | Cache stamped `page6Opened` | No new engine build required | Cache metadata update |
| **SOCKET_DISCONNECT** | Soft-offline; ownership stash; seat kept | No automatic snapshot write | No |
| **SESSION_RECOVERY_REQUEST** | Reclaim → then build or cache | Attempt build; fallback cache | Writes `_snapshots` if build succeeds |
| **SESSION_RECLAIM** | Socket rebound + lobby re-delivery | Same as above | — |
| **Gameplay cleanup / teardown** | Live sources removed | Live build fails; **RESULT cache** may still serve Page6 | Engine `_snapshots` removed on cleanup paths |

### Critical bootstrap timing (`GameManager`)

After Setup completion:

1. `createGame` → activate room↔game mapping  
2. `inputAuthority.registerPlayers`  
3. `physicsEngine.createSimulation`  
4. `gameClockEngine.createClock` (**not** `startClock`)  
5. Wait for profiles + **`ENTRY_PAYMENT_COMPLETED`**  
6. Only then: `initializeGameState` + `startClock` + `initializeGame` → **`GAME_INITIALIZED`**

Therefore RecoveryEngine’s hard requirement for **`gameState`** means **no valid gameplay recovery snapshot exists during the entire payment / TON Connect window**, even though the player seat and `gameId` already exist.

## 3. Failure Path Analysis

### Exact emission site

```text
File:     server/socket/SocketGateway.js
Function: _handleRecoveryRequest
Condition:
  reclaim/context produced a gameId AND setupActive !== true
  AND RecoveryEngine.recoverPlayer threw
  AND RecoverySnapshotCache.get(gameId) has no snapshot
Expected state:
  Live RecoveryEngine sources (or RESULT cache) available
Actual state:
  buildRecoverySnapshot validation failed; cache empty (pre-RESULT)
Root cause hypothesis:
  Recovery requested in a phase where gameId exists but GameStateEngine
  has not been initialized yet (pre–ENTRY_PAYMENT_COMPLETED / pre–GAME_INITIALIZED),
  OR another required source (configuration / physics / clock / input) is missing,
  while setupActive gating is false so the request is not treated as Setup-only.
```

Relevant code path:

1. `recoverPlayer` → `buildRecoverySnapshot`  
2. `_validateRecoverySources` throws `RecoveryValidationError` if any of:  
   - Configuration missing  
   - **Game state missing**  
   - Physics missing  
   - Clock missing  
   - Input missing  
3. `SocketGateway` catch is **empty** (error reason not logged)  
4. Cache fallback only helps post-RESULT  
5. Client receives `SESSION_RECOVERY_FAILED` with `"Recovery snapshot is unavailable"`  
6. Client treats this as **non-terminal** (`recoveryFlow.js`) — overlay fails, session not wiped, but player cannot restore

### Setup vs gameplay gate

```text
setupActive = SetupSession.isRecoverable(roomId)
              && !entryPaymentCompletedByRoom.has(roomId)
```

- If `setupActive === true`: gateway returns after lobby sync; **does not** emit this exact failure string.  
- If `setupActive === false` with `gameId` present: RecoveryEngine path runs → **this failure is reachable**.

So the production string implies reclaim reached **gameplay recovery**, not Setup-only sync.

## 4. TON Connect Interaction

**Yes — the reported sequence can happen.**

```text
TON modal opens
  → browser / WebView visibility / focus change (esp. mobile browser)
  → socket disconnect (transport drop; player remains registered / soft-offline)
  → socket reconnect
  → SESSION_RECOVERY_REQUEST
  → reclaim succeeds (credential + room/player still live)
  → setupActive false  OR  RecoveryEngine path taken with gameId
  → buildRecoverySnapshot fails (typically gameState missing during payment)
  → cache miss (RESULT not reached)
  → "Recovery snapshot is unavailable"
```

Notes:

- Disconnect itself does **not** destroy the seat (by design).  
- Lobby reclaim **does** re-deliver payment/wallet/session events when `paymentStageReady`.  
- Gap: after reclaim, gateway still attempts **RecoveryEngine** whenever `setupActive` is false — and that engine is **gameplay-phase only**, not payment-phase.  
- Empty `catch` hides the precise validation reason in production logs next to the failure string.

## 5. Required Recovery State (minimum; not implemented)

### What RecoveryEngine snapshot covers today (gameplay)

| Field | Present? | Notes |
|-------|----------|-------|
| roomId | Partial | Via configuration metadata, not always top-level |
| gameId | Yes | |
| playerId | Via input players | Must exist in input snapshot |
| nickname / profile | Partial | Through configuration/players if committed |
| wallet information | **No** (not in RecoveryEngine) | Lobby wallet/payment sessions separate |
| payment state (entry/escrow) | Partial | `paymentEngine.getPayment(gameId)` — settlement-oriented; **not** Page4 wallet connect session |

| server timestamps | Yes | `recoveredAt`, clock fields |

### Missing for payment / TON-gap recovery

Minimum authoritative data needed to restore the **observed failure phase** (post-wallet confirm, pre-gameplay):

- `roomId`, `playerId`, `gameId` (if mapped)  
- Setup Session recoverability / expiresAt  
- Verify barrier + wallet address binding  
- Wallet connection session snapshot  
- Entry payment / PaymentSession / GameContract client snapshots  
- `ENTRY_PAYMENT_COMPLETED` / `OPEN_PAGE5` flags  
- GameStartAuthorization reconnect snapshot  

Much of this **already exists** in `RoomLobbyBridge.reconnectSession` re-delivery — but the client recovery UX still depends on `SESSION_SNAPSHOT` / fails on RecoveryEngine miss.

## 6. Root Cause Candidates (ranked)

1. **Primary — Phase mismatch (payment / pre–GAME_INITIALIZED)**  
   `gameId` exists and reclaim succeeds, but `GameStateEngine` not initialized until `ENTRY_PAYMENT_COMPLETED`. RecoveryEngine hard-requires `gameState` → build fails → cache empty → unavailable.

2. **Setup gate false during payment**  
   `setupActive` becomes false (Setup `expiresAt` passed, or session not recoverable) while entry payment still incomplete → forces RecoveryEngine path into candidate (1).

3. **Configuration not yet committed**  
   Profiles incomplete → configuration missing → same validation failure.

4. **RESULT-only cache**  
   Cache cannot cover payment or mid-gameplay disconnects before RESULT; mid-gameplay should still live-build unless engines torn down.

5. **Diagnostic opacity**  
   Empty `catch` in `_handleRecoveryRequest` drops `RecoveryValidationError.reason`, making production triage harder.

6. **Less likely for this symptom**  
   Full gameplay teardown with stale `gameId` mapping; credential failure uses a **different** reason string.

## 7. Recommended Minimal Fix Direction (do not implement here)

**Do not expand RecoveryEngine into payment.** Keep it gameplay-authoritative.

Minimal direction:

1. **Split recovery outcomes in SocketGateway** after successful reclaim:  
   - **Setup / payment room recovery:** if `!GAME_INITIALIZED` (or `!gameState` / pending activation), treat reclaim + existing lobby re-delivery as **success**; emit an explicit non-failure signal (or suppress `SESSION_RECOVERY_FAILED` for this case).  
   - **Gameplay recovery:** only call `RecoveryEngine.recoverPlayer` when live game state is initialized (or RESULT cache exists).

2. **Log validation reason** when build fails (replace empty catch).

3. **Optional:** client should treat payment-page reconnect as complete when lobby sync events arrive, without requiring `SESSION_SNAPSHOT`.

4. **Do not** invent a second physics snapshot for payment; **do not** change Gameplay / Physics / Payment / TON engines for this gap.

Suggested next stage: **R17.8B — Payment-phase recovery success path** (gateway gating + logging), audit-proven, no engine redesign.

## 9. R17.8B — Implemented Solution

**Status:** Implemented (2026-08-14)

### Changed recovery routing

`resolveRecoveryRoute()` in `server/socket/gameplayRecoveryProtocol.js` +
`SocketGateway._handleRecoveryRequest`:

| Condition | Route | Behavior |
|-----------|-------|----------|
| `setupActive` | `PRE_GAME_SUCCESS` / phase `SETUP` | Log `RECOVERY_SKIPPED`; lobby sync already sent; **no** RecoveryEngine |
| `gameId` + no live `gameState` + no RESULT cache | `PRE_GAME_SUCCESS` / phase `ENTRY_PAYMENT` | Log `RECOVERY_SKIPPED reason=GAME_NOT_INITIALIZED`; **no** RecoveryEngine |
| live `gameState` or RESULT cache | `GAMEPLAY_SNAPSHOT` | Existing `recoverPlayer` + `SESSION_SNAPSHOT` |
| no `gameId` and not setup | `FAIL` | `SESSION_RECOVERY_FAILED` with clear reason |

### Pre-game vs gameplay

- **Pre-game (ROOM / VERIFY / PAYMENT / TON / ENTRY_PAYMENT):** reclaim + `RoomLobbyBridge.reconnectSession` lobby/payment re-delivery is the success path. Client must not receive `"Recovery snapshot is unavailable"` for this phase.
- **Gameplay (after GAME_INITIALIZED):** unchanged RecoveryEngine snapshot restore.
- **Failures:** empty `catch` replaced; logs `RECOVERY_FAILED | reason=<real validation error> | phase=...`.
