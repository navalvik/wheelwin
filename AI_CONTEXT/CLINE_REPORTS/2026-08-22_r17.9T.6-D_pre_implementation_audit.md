## 3. Current Room Lifecycle

### How Rooms Are Currently Created

Rooms are created via `RoomManager.createRoom()` (or equivalent factory method). The flow is:

1. A client sends a room creation request via socket event.
2. `socketHandler.js` receives the request and calls `RoomManager.createRoom()`.
3. `RoomManager` generates a new `roomId` using `crypto.randomUUID()`.
4. A new `Room` instance is constructed with the generated `roomId`.
5. The room is stored in `RoomManager.rooms` (a `Map<string, Room>`).
6. The room status is set to its initial lifecycle state (e.g., `WAITING` or `LOBBY`).

### Where roomId Is Generated

`roomId` is generated inside `RoomManager` using `crypto.randomUUID()`. The ID is generated at creation time and is never accepted from external input. There is no code path that allows a caller to provide a pre-existing `roomId`.

### Whether RoomManager Has an API Capable of Attaching/Reconstructing an Existing roomId

**No.** `RoomManager` has no `attachRoom()`, `restoreRoom()`, `reconstructRoom()`, or any similar API. The only way to add a room to `RoomManager.rooms` is through `createRoom()`, which always generates a new `roomId`.

No such API exists under another name either. The `RoomManager` API surface consists of:
- `createRoom()` — generates new roomId
- `getRoom(roomId)` — retrieves by ID
- `removeRoom(roomId)` / `closeRoom(roomId)` — removes by ID
- `hasRoom(roomId)` — checks existence

### What Runtime State a Room Object Requires

A `Room` object contains:

| Field | Type | Durable | Runtime-only |
|---|---|---|---|
| `roomId` | string (UUID) | ✅ | |
| `createdAt` | timestamp | ✅ | |
| `status` | enum | ✅ | |
| `players` | Map/array | ✅ (playerIds) | (socket refs) |
| `game` | Game reference | ✅ (gameId) | (object ref) |
| `sockets` | Map | | ✅ |
| `eventListeners` | Map | | ✅ |
| `metadata` | object | ✅ | |

### Whether an Existing Room Can Safely Be Reconstructed Without Generating a New roomId

**Not with the current API.** The `Room` constructor accepts a `roomId` parameter, so a `Room` object can theoretically be constructed with a pre-existing ID. However, `RoomManager` has no method to insert a pre-constructed `Room` into its internal `rooms` Map without going through `createRoom()`.

**Proposed approach (not implemented):** A new `RoomManager.attachRoom(room)` method that accepts a pre-constructed `Room` object with an existing `roomId` and registers it in the `rooms` Map, with duplicate detection.

### What Dependencies Must Exist Before a Room Can Be Attached

Before a room can be attached/reconstructed:
1. `RoomManager` must be initialized.
2. The `Room` object must be constructed with the persisted `roomId`.
3. The room's `status` must be set from persisted state.
4. Player references must be resolved after players are reconstructed.
5. The game reference must be resolved after the game is reconstructed.

## 4. Current Game Lifecycle

### How Games Are Currently Created

Games are created via `GameManager.createGame()` or through `GameInitializer.initializeGame()`. The flow is:

1. When a room reaches the required player count (3 players), `GameInitializer` is called.
2. `GameInitializer` creates a new `Game` instance with a freshly generated `gameId`.
3. The `Game` is associated with its parent `Room` via `room.game = game` or equivalent.
4. `ConfigurationEngine` creates a committed configuration for the game.
5. `GameStateEngine` initializes the game state.
6. `GameClockEngine`, `PhysicsEngine`, `InputAuthority`, `WinnerEngine` are initialized.
7. `SimulationLoop` is started.

### Where gameId Is Generated

`gameId` is generated using `crypto.randomUUID()` inside `GameManager` or `GameInitializer` at game creation time. Like `roomId`, it is never accepted from external input.

## 5. Current Player Lifecycle

### How PlayerManager Creates Players

Players are created via `PlayerManager.createPlayer()` or `registerPlayer()`. The flow is:

1. When a client joins a room, `socketHandler` calls `PlayerManager.createPlayer()`.
2. `PlayerManager` generates a new `playerId` using `crypto.randomUUID()`.
3. A `playerIndex` is assigned sequentially (0, 1, 2 for the 3-player game).
4. A new `Player` instance is constructed.
5. The player is added to `PlayerManager.players` (a `Map`).
6. The player is associated with the room.

### Where playerId Is Generated

`playerId` is generated using `crypto.randomUUID()` inside `PlayerManager` at player registration time. It is never accepted from external input.

### Whether PlayerManager Can Restore/Register an Existing playerId

**No.** `PlayerManager` has no `restorePlayer()`, `attachPlayer()`, or similar API. The only way to add a player is through `createPlayer()`, which always generates a new `playerId`.

### Whether playerIndex Is Authoritative and Reusable

`playerIndex` is assigned sequentially by `PlayerManager` (0, 1, 2). It is authoritative within the context of a specific game. The index is reusable in the sense that it can be reassigned during reconstruction, but it must match the persisted value to maintain deterministic game state.

### How Wallet Identity Is Associated with a Player

Wallet identity is associated via:
- `player.walletAddress` — the TON wallet address
- `player.walletId` — may be used as an alias

The wallet address is the primary identity link to the financial system (PaymentSessionManager, TonFinancialPersistence).

## 6. Configuration Reconstruction Boundary

### How Committed Configuration Is Currently Created

Configuration is created via `ConfigurationEngine.createConfiguration()` or `commitConfiguration()`. The process involves:
1. Selecting wheel segments from `WheelCatalog`.
2. Computing multipliers and payout structure.
3. Generating a deterministic seed.
4. Computing `configurationHash` from the configuration content.
5. Assigning a `configurationVersion` (monotonic counter).
6. Marking the configuration as committed (immutable).

### Whether Configuration Is Immutable After Commitment

**Yes.** Once a configuration is committed, it is frozen. The `ConfigurationEngine` does not provide any API to modify a committed configuration. The `configurationHash` serves as a tamper-detection mechanism.

### Whether the Existing Configuration Can Be Restored Directly

**Theoretically yes, but no API exists.** The persisted Recovery Data Contract contains the full `configuration` object. Since configuration is immutable, the persisted object is still valid. However, `ConfigurationEngine` has no `restoreConfiguration()`, `importConfiguration()`, or `attachConfiguration()` API.

### Whether ConfigurationEngine Has a Restore/Import/Attach API

**No.** `ConfigurationEngine` has no restore/import/attach API. The only way to create a configuration is through `createConfiguration()`, which generates a new configuration with a new hash and version.

### Whether Configuration Must Be Regenerated or Can Be Restored from the Persisted `configuration` Object

**It can be restored from the persisted object.** Since the configuration is immutable, the persisted `configuration` object is still valid. The `configurationHash` can be recomputed and compared to verify integrity. However, a new API is needed to accept the persisted configuration without regeneration.

### How `configurationHash` Is Currently Used

`configurationHash` is:
- Computed from the configuration content (segments, multipliers, seed, etc.).
- Stored alongside the configuration.
- Used for integrity verification.
- Included in the Recovery Data Contract.

During reconstruction, the hash can be recomputed from the persisted configuration and compared to the persisted hash to verify integrity.

### Whether `configurationVersion` Is Sufficient to Validate the Persisted Configuration

`configurationVersion` is a monotonic counter that identifies the configuration version. It is **not sufficient alone** to validate the configuration. The `configurationHash` must also be recomputed and compared to ensure the configuration content has not been tampered with.

### Whether Catalog Version Information Is Currently Available and Where It Lives

Catalog version information is **not explicitly tracked** in the current codebase. The `WheelCatalog` provides wheel segments but does not expose a version number. The `gameConfig.js` file contains static configuration parameters but does not include a catalog version.

### Whether the Absence of Persisted Catalog Version Creates a Real Reconstruction Blocker

**It is a non-blocking gap.** The full `configuration` object is persisted in the Recovery Data Contract, including all segment definitions. Since the configuration is self-contained and immutable, the catalog version is not strictly needed for reconstruction. The `configurationHash` provides sufficient integrity verification.

However, for long-term maintainability, adding a catalog version to the persisted contract would help detect incompatible catalog changes between server versions. This is a **non-blocking gap** that can be addressed in a later stage.

## 7. GameState Reconstruction Boundary

### How GameStateEngine Represents State

`GameStateEngine` tracks the following state:

| Field | Type | Description | Persisted |
|---|---|---|---|
| `currentPhase` | enum | Current game phase (WAITING, BETTING, SPINNING, RESULT, SETTLEMENT, COMPLETE) | ✅ |
| `lifecycleStatus` | enum | Lifecycle status (ACTIVE, PAUSED, TERMINATED) | ✅ |
| `phaseStartedAt` | timestamp | When the current phase started | ✅ |
| `awaitingResultActivation` | boolean | Whether result activation is pending | ✅ |
| `resultPhaseStarted` | timestamp | When the result phase started | ✅ |
| `terminalState` | boolean | Whether the game has reached terminal state | ✅ |
| `serverTimestampAtCheckpoint` | timestamp | Server time when the checkpoint was taken | ✅ |

### Mapping Against Recovery Data Contract Fields

| Recovery Data Contract Field | GameStateEngine Field | Restore API Exists? |
|---|---|---|
| `gameState` | `currentPhase` | ❌ No |
| `gameStatus` | `lifecycleStatus` | ❌ No |
| `phaseStartedAt` | `phaseStartedAt` | ❌ No |
| `awaitingResultActivation` | `awaitingResultActivation` | ❌ No |
| `resultPhaseStarted` | `resultPhaseStarted` | ❌ No |
| `serverTimestampAtCheckpoint` | (checkpoint timestamp) | ❌ No |

### Which Existing APIs Can Restore These Values and Which Do Not Exist

**No restore APIs exist.** `GameStateEngine` only provides:
- `initState()` — initializes to default state
- `transitionTo(newPhase)` — transitions to a new phase
- `getCurrentState()` — returns current state

There is no `restoreState()`, `setState()`, or `importState()` API. All state changes go through `transitionTo()`, which enforces the state machine's transition rules. This means reconstruction cannot simply set the state directly; it must either:
1. Add a new `restoreState()` API that bypasses transition validation, or
2. Replay transitions from the initial state to the persisted state (not recommended for terminal or mid-spin states).

## 10. Startup / Shutdown Boundary

### Current Startup Sequence

```
SERVER_START
  ↓
1. Process starts (index.js)
   ↓
2. Load environment variables (dotenv)
   ↓
3. Initialize PostgreSQL connection pool
   ↓
4. Initialize persistence layer (RecoveryDataPersistence, TonFinancialPersistence)
   ↓
5. Initialize managers (RoomManager, GameManager, PlayerManager, PaymentSessionManager, PaymentEngine)
   ↓
6. Initialize engines (ConfigurationEngine, GameStateEngine, etc.)
   ↓

   ↓
8. Initialize session manager (SessionManager.js)
   ↓
9. Start Express HTTP server
   ↓
10. Start Socket.IO server
    ↓
11. Register socket event handlers
    ↓
12. Normal gameplay begins (rooms/games created on demand)
```

### Current Shutdown Sequence

```
SERVER_SHUTDOWN
  ↓
1. Process receives SIGTERM/SIGINT (or is killed)
   ↓
2. [NO GRACEFUL SHUTDOWN HANDLER EXISTS]
   ↓
3. Process terminates
   ↓
4. All in-memory state is lost
```

**Critical finding:** There is **no SIGTERM/SIGINT handler** and **no graceful shutdown logic**. The server does not checkpoint active games before termination. This means the Recovery Data Contract must be written **during gameplay** (periodic checkpointing), not at shutdown time.

### Where a Future Recovery Orchestration Stage Could Safely Execute

A future recovery orchestration stage should execute:

```
SERVER_START
  ↓
1. Process starts
   ↓
2. Load environment variables
   ↓
3. Initialize PostgreSQL connection pool
   ↓
4. Initialize persistence layer
   ↓
5. Initialize managers (empty, no rooms/games yet)
   ↓
6. Initialize engines
   ↓
7. ★ RECOVERY ORCHESTRATION STAGE ★
   │  a. Load all persisted Recovery Data Contracts
   │  b. For each contract:
   │     - Reconstruct Room (attach existing roomId)
   │     - Reconstruct Players (attach existing playerIds)
   │     - Reconstruct Game (attach existing gameId)
   │     - Restore Configuration (from persisted object)
   │     - Restore GameState (from persisted fields)
   │     - Reinitialize GameClockEngine
   │     - Reinitialize PhysicsEngine
   │     - Reinitialize InputAuthority
   │     - Reinitialize WinnerEngine
   │     - Validate internal consistency
   │  c. Register reconstructed rooms/games in managers
   │  d. Mark reconstructed games as "recovered" (not "active gameplay")
   ↓
8. Initialize socket handler
   ↓
9. Initialize session manager
   ↓
10. Start servers
    ↓
11. Clients reconnect and resume
```

The recovery stage must execute **after** managers are initialized but **before** the socket handler starts accepting connections.

## 11. Identity Preservation Rules

### roomId

- **Must be restored exactly as persisted.**
- The `roomId` is the primary key for room reconstruction.
- Generating a new `roomId` during recovery would break all references from games, players, and financial records.
- **Current code path that would accidentally generate a replacement:** `RoomManager.createRoom()` always generates a new `roomId`. This must NOT be called during recovery.

### gameId

- **Must be restored exactly as persisted.**
- The `gameId` is the primary key for game reconstruction.
- Generating a new `gameId` would break references from financial records and recovery data.
- **Current code path that would accidentally generate a replacement:** `GameManager.createGame()` or `GameInitializer.initializeGame()` always generates a new `gameId`. These must NOT be called during recovery.

### playerId

- **Must be restored exactly as persisted.**
- The `playerId` is the primary key for player reconstruction.
- Generating a new `playerId` would break wallet associations and financial records.
- **Current code path that would accidentally generate a replacement:** `PlayerManager.createPlayer()` always generates a new `playerId`. This must NOT be called during recovery.

### playerIndex

- **Must be restored exactly as persisted.**
- The `playerIndex` (0, 1, 2) is authoritative and determines the player's position in the game.
- Reassigning indices would break deterministic game state.
- **Current code path that would accidentally generate a replacement:** `PlayerManager.createPlayer()` assigns the next available index. This must NOT be called during recovery.

### contractId

- **Must be restored exactly as persisted.**
- The `contractId` references the blockchain escrow contract.
- Regenerating it would break the link to the on-chain escrow.
- **Current code path that would accidentally generate a replacement:** `PaymentSessionManager.createSession()` may generate a new `contractId`. This must NOT be called during recovery.

### paymentSessionId

- **Must be restored exactly as persisted.**
- The `paymentSessionId` references the payment session.
- Regenerating it would break payment tracking.
- **Current code path that would accidentally generate a replacement:** `PaymentSessionManager.createSession()` generates a new `paymentSessionId`. This must NOT be called during recovery.

## 12. Financial Boundary

### Verification: R17.9T.6-D Must NOT Become the Owner of Financial Truth

**Confirmed.** R17.9T.6-D is a gameplay reconstruction task. It must NOT:
- Create new financial records
- Modify existing financial records
- Override payment status
- Bypass blockchain verification
- Assume wallet state

### How Reconstructed Gameplay Objects Should Reference Financial Identity

Reconstructed gameplay objects should store **references only** (not duplicates) to financial identity:

## 13. Reconnect Boundary

### What Happens When a Client Reconnects After SERVER_RESTART

Currently, when a client reconnects:

1. The client establishes a new Socket.IO connection.
2. `socketHandler.js` receives the `connection` event.
3. The client sends a `rejoin` or `reconnect` event with their `roomId`/`gameId`.
4. `SessionManager` looks up the session by socket ID or wallet address.
5. `RoomManager.getRoom(roomId)` is called to find the room.
6. If the room exists, the player is re-associated with the room and game.

### What the Client Currently Expects

The client expects:
- The server has the room and game in memory.
- The player's seat (playerIndex) is still reserved.
- The game state is preserved (phase, timer, etc.).
- The player can resume from where they left off.

### How Room/Game Identity Is Resolved

Room/game identity is resolved by the `roomId` sent by the client during reconnect. The server looks up `RoomManager.getRoom(roomId)` to find the room.

### Whether an Existing Reconstructed Game Can Be Exposed Through the Existing Reconnect Path

**Yes, if the reconstructed game is properly registered in `RoomManager` and `GameManager`.** The reconnect path simply calls `RoomManager.getRoom(roomId)`. If the reconstructed room is in the `rooms` Map, the reconnect path will find it.

**However**, the reconstructed game must be in a state that the reconnect path can handle. If the game was in `SPINNING` phase when the server crashed, the reconstructed game should either:
1. Resume the spin (if physics state is available), or
2. Transition to a `RECOVERY` state that allows players to rejoin and then resume/resolve.

### Whether Reconnect Currently Assumes an In-Memory Object Created During the Current Process

**Yes.** The current reconnect path assumes the room and game were created during the current process lifetime. There is no fallback to persistence. If the room is not in `RoomManager.rooms`, the reconnect fails.

### What Missing Runtime State Would Prevent Reconnect

The following missing runtime state would prevent reconnect:
1. **Socket references** — `Player.socket` must be updated when the client reconnects.
2. **Session mapping** — `SessionManager` must map the new socket ID to the player.
3. **Room socket membership** — The player must re-join the Socket.IO room.
4. **Game timer** — If the game was in a timed phase, the timer must be recreated.
5. **Simulation loop** — If the game was spinning, the simulation loop must be restarted.

## 14. Recovery Safety Rules

### Operations That Must NEVER Happen During Recovery

1. **Generating a new roomId for an existing room** — `RoomManager.createRoom()` must NOT be called.
2. **Generating a new gameId for an existing game** — `GameManager.createGame()` must NOT be called.
3. **Generating replacement playerIds** — `PlayerManager.createPlayer()` must NOT be called.
4. **Regenerating committed configuration** — `ConfigurationEngine.createConfiguration()` must NOT be called for existing games.
5. **Trusting client-provided recovery state** — All recovery data must come from `RecoveryDataPersistence`, never from client input.
6. **Overwriting financial authority** — Financial fields must NOT be modified during recovery.
7. **Silently accepting corrupted recovery records** — Recovery data must be validated (hash check, field completeness) before use.
8. **Creating duplicate active games for the same roomId/gameId** — Before reconstruction, check if a game with the same ID already exists.
9. **Starting active gameplay before the reconstructed state is internally consistent** — The simulation loop must NOT start until all engines are initialized and state is validated.

## 17. BLOCKERS

### Issues That Genuinely Prevent Safe Implementation of R17.9T.6-D

1. **No attach/restore APIs on any manager or engine.**
   - `RoomManager`, `GameManager`, `PlayerManager`, `ConfigurationEngine`, `GameStateEngine`, `GameClockEngine`, `PhysicsEngine`, `InputAuthority`, `WinnerEngine` — none have APIs to accept pre-existing identities or persisted state.
   - **Impact:** Cannot reconstruct any runtime object without generating new IDs.
   - **Resolution:** Must implement new attach/restore APIs (listed in Section 15).

2. **No recovery orchestration logic.**
   - `RecoveryOrchestrator` exists but is a stub/placeholder with no reconstruction logic.
   - **Impact:** No code path to coordinate the full reconstruction sequence.
   - **Resolution:** Must implement `RecoveryOrchestrator.reconstructFromContract()`.

3. **No duplicate detection guard.**
   - No mechanism to prevent double reconstruction of the same game.
   - **Impact:** If recovery runs twice (e.g., due to retry), duplicate games could be created.
   - **Resolution:** Must add duplicate detection before reconstruction.

## 18. NON-BLOCKING GAPS

### Issues That Can Be Handled During Implementation Without Architectural Redesign

1. **No catalog version in persistence** — The full configuration object is persisted, so catalog version is not strictly needed. Can be added in a later stage.

2. **No graceful shutdown handler** — Recovery relies on periodic checkpoints, not shutdown-time checkpoints. Graceful shutdown can be added later.

3. **No periodic checkpointing** — This is a separate concern from reconstruction. R17.9T.6-D only reads existing checkpoints; it does not create them.

4. **No reconnect integration** — The existing reconnect path will work if rooms/games are properly registered in managers. Full reconnect integration (handling recovered game states) can be done in a later stage.

5. **No simulation loop resumption** — Resuming active spinning is complex and can be deferred. Recovered games can be placed in a `RECOVERY` state that waits for manual resolution.

6. **No stale input handling** — Inputs submitted before the crash are lost. This is acceptable; players can resubmit after reconnect.

7. **Physics state recomputation** — If physics state (angle, velocity) is not persisted, it can be recomputed from the seed and elapsed time. This is a deterministic computation.

8. **Game timer recreation** — Timers can be recreated from `phaseStartedAt` and phase duration. This is a straightforward computation.

## 21. Final Verdict

### Summary

The WheelWin runtime **cannot currently reconstruct** room/game/player identity from persisted Recovery Data after SERVER_RESTART. The fundamental blocker is that **all manager and engine APIs are creation-only** — they always generate new IDs and initialize to default state. No attach, restore, or reconstruct APIs exist.

### What Needs to Happen

R17.9T.6-D must implement:

1. **Attach APIs** on `RoomManager`, `GameManager`, `PlayerManager` to register pre-constructed objects with existing IDs.
2. **Restore APIs** on `ConfigurationEngine`, `GameStateEngine`, `GameClockEngine`, `PhysicsEngine`, `InputAuthority`, `WinnerEngine` to accept persisted state.
3. **Recovery orchestration** in `RecoveryOrchestrator` to coordinate the full reconstruction sequence.
4. **Duplicate detection** to prevent double reconstruction.
5. **Consistency validation** to ensure reconstructed state is internally consistent.

### What Must NOT Happen

R17.9T.6-D must NOT:
- Modify financial logic or financial persistence
- Modify persistence schemas
- Modify reconnect logic
- Create new checkpoints
- Start active gameplay for recovered games
- Trust client-provided recovery state

### Risk Assessment

- **Critical risk:** Accidentally calling `createRoom()`/`createGame()`/`createPlayer()` during recovery, which would generate new IDs and break all references.
- **High risk:** Incomplete state restoration leading to inconsistent game state.
- **Medium risk:** Double reconstruction if recovery runs multiple times.
- **Low risk:** Missing catalog version (can be handled by full configuration persistence).

### Feasibility

**Feasible with controlled changes.** The existing `Room`, `Game`, and `Player` constructors already accept IDs as parameters. The existing `RecoveryDataPersistence` already loads persisted data. The missing piece is the attach/restore APIs on managers/engines and the orchestration logic. These are additive changes that do not require architectural redesign.

**No source code was modified in this audit.**
