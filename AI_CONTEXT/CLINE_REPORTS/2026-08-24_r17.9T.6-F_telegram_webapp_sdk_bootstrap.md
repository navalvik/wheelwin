# R17.9T.6-F — Telegram WebApp SDK Bootstrap

Date: 2026-08-24

Task: Load the official Telegram WebApp SDK synchronously in the client HTML entry so that `window.Telegram.WebApp.initData` is available before `socket.js` executes, enabling real Telegram Mini App authentication (Telegram Web and Telegram Android).

## 1. Scope

- Client HTML entry inspection.
- Addition of the official Telegram WebApp bootstrap script.
- Focused client tests for bootstrap wiring and socket auth behavior.
- Production build validation.

## 2. Files Inspected

- `client/index.html` — Vite application HTML entry
- `client/src/socket/socket.js` — socket factory, `resolveTelegramInitData()`
- `client/src/socket/socket.telegramAuth.test.js` — existing focused socket auth test
- `client/scripts/run-tests.js` — client test runner convention
- `client/package.json` — build/test scripts

## 3. Architecture Findings

- The Vite HTML entry is `client/index.html`. It previously contained no Telegram SDK of any kind — neither the official `telegram-web-app.js` nor any vendored copy. This confirmed the root cause: in a real Mini App launch, `window.Telegram.WebApp` did not exist at module evaluation time, so `resolveTelegramInitData()` returned `""`, and the server correctly rejected `CREATE_ROOM`.
- `client/src/socket/socket.js` already reads `globalThis.window?.Telegram?.WebApp?.initData` at socket creation time and forwards it verbatim as `auth.telegramInitData`. No changes were needed there.
- The existing test suite is plain Node scripts (`*.test.js`) executed by `client/scripts/run-tests.js`; no browser automation exists or was added.

## 4. Lifecycle Flow

Resulting boot order:

```
Telegram Mini App launch
→ <head>: telegram-web-app.js?63 (synchronous)
→ window.Telegram.WebApp populated with initData
→ <body>: /src/main.jsx (application module)
→ socket.js evaluated → resolveTelegramInitData()
→ io(SOCKET_URL, { auth: { telegramInitData: <raw string> }, autoConnect: false })
→ Socket.IO handshake → server Telegram validator (unchanged)
```

## 5. Ownership Boundaries

- Server remains the sole authority for initData validation (`server/auth/` validator untouched).
- Client only forwards the raw initData string; it never parses, stores, logs, or transforms it.
- Room authorization, SocketGateway, RoomLobbyBridge, recovery, gameplay, and financial modules were not touched.

## 6. Risks

- **Low**: If the CDN `telegram.org/js/telegram-web-app.js` is unreachable, standard Web behavior degrades gracefully to empty `telegramInitData` (existing socket.js fallback). Telegram clients load the Mini App inside Telegram's own webview where the script is reliably reachable.
- **Low**: No new runtime dependencies; no vendored code; no CSP/vercel.json header changes required (script loads from public CDN like any external resource).

No Critical or High risks identified.

## 7. Recommendations

1. Perform manual validation on real devices (checklists below). Unit tests alone do NOT validate real Telegram authentication.
2. After validation, confirm via server logs that `CREATE_ROOM` succeeds inside Telegram and remains rejected on standard Web.
3. Do not add `WebApp.ready()` / `WebApp.expand()` unless a future task explicitly requires Telegram UI integration.

## 14. Remaining Risks
