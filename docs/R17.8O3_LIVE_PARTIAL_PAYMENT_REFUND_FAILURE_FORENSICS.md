**Classification:** **Lifecycle bypass — uncovered teardown path** (not an O.1 cancel/refund implementation defect; O.1 scope gap).

**On-chain evidence (post-session):** Escrow contract remains **active** with balance **~2.145 TON** (TonAPI, 2026-08-14) — funds not returned.

## 9. Room destruction path analysis

### Path taken (confirmed by timestamps + code)

1. `SetupSessionLifecycle.archiveForPayment()` — archives setup but **reschedules** expiry at original Setup Timer `expiresAt` (R7.70C23).
2. Payment proceeds; two stakes confirm; session becomes `PARTIALLY_PAID`.
3. At `expiresAt` (`13:16:20`), `SetupSessionLifecycle._onExpiry()` emits `SETUP_SESSION_EXPIRED`.
4. `RoomLobbyBridge._handleSetupSessionExpired()` → **`_closeRoom(roomId, "setup_expired")`** directly.
5. **Does not call** `PaymentSessionManager.failSession()`.

## 12. Recommended minimal fix stage (R17.8O.4)

**Do not redesign architecture.** Extend O.1 coverage to the bypass path:

### Option A (minimal, recommended)

In `RoomLobbyBridge._handleSetupSessionExpired` (before `_closeRoom`):

- If active payment session exists and `sessionNeedsEscrowUnwind(session)` → call `failSession(roomId, "setup_expired")` instead of `_closeRoom`.
- Defer room destroy until O.1 refund completion (same as `payment_timeout`).

### Option B (defense in depth)

Central guard in `_closeRoom`: when partial payment with confirmed on-chain stakes, route through `failSession` / unwind before destroy.

### Option C (product/timer — separate decision)

When payment stage starts, **extend or supersede** Setup Timer so payment window is independent (conflicts with R7.70C23 “honor original expiresAt” — needs explicit product sign-off).

**Suggested stage ID:** **R17.8O.4 — Setup-expiry escrow unwind bridge**
