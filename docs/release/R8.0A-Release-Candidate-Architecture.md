## 1. Release Lifecycle

```text
Development
    ↓
Internal Validation
    ↓
Release Candidate
    ↓
Closed Beta
    ↓
Open Beta
    ↓
Production Release
    ↓
Hotfix
    ↓
Maintenance
```

### Phase definitions, entry & exit criteria

| Phase | Purpose | Entry criteria | Exit criteria |
|-------|---------|----------------|---------------|
| **Development** | Feature / fix work on non-frozen surfaces (ops tooling, docs, client UX polish that does not alter authority) | Backlog item approved; branch from `main` | PR merged; unit/integration green; no authority regression |
| **Internal Validation** | Full ops + gameplay regression on staging-like config | Candidate commit tagged `internal-validation/*` or CI green on `main` | R7.0H suite PASS; smoke probes PASS; no Critical defects open |
| **Release Candidate** | Official RC build for beta / launch gates | See §2 | Signed RC checklist; artifacts published; git tag `vX.Y.Z-rcN` |
| **Closed Beta** | Invited users; controlled load; feedback loop | RC approved; beta cohort selected; incident channel live | Exit criteria in §7; no Critical; settlement success within SLO |
| **Open Beta** | Public invite / soft launch | Closed Beta exit met; capacity plan signed | Launch go/no-go (§8); monitoring SLOs held ≥72h |
| **Production Release** | First public `v1.0.0` (or agreed GA version) | Open Beta exit; legal docs published; mainnet readiness (§6) | Post-launch verification window complete; first patch window scheduled |
| **Hotfix** | Urgent patch for Critical / High production defects | Rollback avoided or post-rollback fix; severity ≥ High | Patch validated; promoted staging → production; notes published |
| **Maintenance** | Steady-state ops, scheduled patches, dependency updates | Production stable ≥ first patch window | Continuous; exits only on major version program |

### Lifecycle ownership (organizational)

| Role | Responsibility |
|------|----------------|
| Release Owner | Gate decisions, checklist sign-off, go/no-go |
| Engineering Lead | RC build integrity, freeze enforcement |
| Ops / SRE | Staging/prod promote, probes, rollback execution |
| Security | Secret / JWT / dependency review |
| Blockchain / Payments | Settlement & contract verification |
| Support / Community | Beta feedback triage |
| Legal / Product | ToS, Privacy, launch communications |

## 2. What Constitutes a Release Candidate

A **Release Candidate (RC)** is a versioned, immutable artifact set that satisfies all of the following:

### Hard requirements

| Requirement | Definition of done |
|-------------|-------------------|
| Gameplay frozen | No authority / simulation / settlement rule changes after RC cut |
| Server authoritative frozen | No redesign of SimulationLoop, EventBus contracts, RecoveryEngine, payment authority |
| Infrastructure validated | R7 subsystems present and configured for target profile |
| Production validation PASS | `npm run validate:production` (R7.0H) **PASS** on the RC commit |
| No critical defects | Zero open **Critical** issues (§10) |
| No known data-loss issues | No open bugs in settlement, audit ledger integrity, or durable payment state |
| No security blockers | Secrets review clear; JWT review clear; no unpatched Critical CVEs in runtime deps |
| Configuration finalized | Staging + production env schemas reviewed; `DEPLOYMENT_PROFILE` / TON network / auth secrets plan documented |
| Documentation complete | Checklist docs in §3 Documentation row exist or have tracked owners + due dates before GA |

### RC naming

```text
v{MAJOR}.{MINOR}.{PATCH}-rc{N}
```

Examples: `v1.0.0-rc1`, `v1.0.0-rc2`.

Each RC is **immutable**. Fixes create `rcN+1`, never mutate an existing RC tag.

### RC cut procedure (process)

1. Freeze commit on `main` (or release branch).  
2. Run Internal Validation (R7.0H + smoke).  
3. Complete Release Checklist (§3).  
4. Produce Release Artifacts (§5).  
5. Tag git + draft GitHub Release (pre-release flag).  
6. Release Owner signs RC approval.

## 3. Release Checklist

All items must be **Pass** or **N/A (justified)** before RC approval.

### Gameplay

- [ ] Deterministic simulation under fixed seed / authority rules  
- [ ] Client–server synchronization validated (no desync under reconnect)  
- [ ] Authoritative regression suite green (existing gameplay integration tests)  
- [ ] No pending authority-changing PRs  

### Infrastructure

- [ ] Structured logging active; rotation/retention configured  
- [ ] Monitoring collectors active; Prometheus path verified if enabled  
- [ ] Deployment profiles set (`development` / `staging` / `production`)  
- [ ] Health probes: `/health`, `/ready`, `/live`, `/startup` respond correctly  
- [ ] Failure recovery policies initialized; circuits configured for external deps  
- [ ] Graceful drain verified (`RUNNING` → `DRAINING` → `STOPPED`)  
- [ ] R7.0H Production Validation Suite **PASS**  

### Blockchain

- [ ] Target network selected (testnet for beta; mainnet for GA per §6)  
- [ ] Wallet verification procedure executed  
- [ ] Settlement verification (happy path + reject / expiry)  
- [ ] Contract addresses / deploy mode verified for environment  
- [ ] Network endpoint / API key configuration validated (secrets not in git)  

### Security

- [ ] Secret inventory reviewed (`DEVELOPER_AUTH_*`, `TON_*`, owner wallet)  
- [ ] JWT settings: TTL, secret strength, production auth enabled  
- [ ] Audit log channel writing; no secrets in audit payloads  
- [ ] Dependency review (known Critical CVEs addressed or waived)  
- [ ] Health / metrics / console expose no secrets, stacks, or absolute secret paths  
- [ ] Address R7.0H warning: expand sanitizer coverage for JWT/`authorization` field keys before GA if still open  

### Performance

- [ ] Memory growth within accepted bounds under soak (extend `VALIDATION_LONG_MS` for RC)  
- [ ] CPU utilization acceptable under expected concurrent rooms  
- [ ] Gameplay / probe latency within targets (§9)  
- [ ] Event loop delay healthy under load  

### Documentation

- [ ] README (repo / product overview)  
- [ ] Installation guide  
- [ ] Deployment guide (staging → production)  
- [ ] API / socket event overview (as needed for partners)  
- [ ] Game Rules (`client/public/docs/rules.md` or successor)  
- [ ] FAQ  
- [ ] Privacy Policy  
- [ ] Terms of Service  
- [ ] Changelog

## 4. Deployment Strategy

```text
Development  →  Staging  →  Production
```

### Environments

| Environment | Purpose | Typical profile | Blockchain |
|-------------|---------|-----------------|------------|
| Development | Local / CI | `development` | stub / testnet |
| Staging | Pre-prod validation, RC soak, beta backend | `staging` | testnet (preferred) |
| Production | Public / GA traffic | `production` | mainnet (GA) or testnet (open beta if declared) |

### Configuration promotion

1. Validate env schema via ConfigurationManager (fail-fast).  
2. Promote **non-secret** config as versioned examples / ops docs.  
3. Promote **secrets** via secret store / host env only—never git.  
4. Confirm `DEPLOYMENT_PROFILE`, monitoring, failure policy, and TON keys match the target phase.  
5. Record config fingerprint (safe summary only) in release notes.

### Versioning in deploy

- Container / process image or build ID must match **git tag**.  
- Client and server versions must be recorded as a pair in release notes.  
- Mismatched client/server majors are a **High** launch risk (block GA if incompatible).

### Smoke tests (post-promote)

| Check | Expect |
|-------|--------|
| `GET /startup` | 200, `startup: true` |
| `GET /live` | 200, `live: true` |
| `GET /ready` | 200, `ready: true` (not during drain) |
| `GET /health` | 200 when ready; includes lifecycle `RUNNING` |
| Developer Console login (staging) | Auth succeeds; Server Health populates |
| Create room / join (staging) | Lobby path healthy |
| Optional: `/metrics` | 200 if Prometheus enabled |

### Post-deployment verification

- Confirm monitoring freshness  
- Confirm logging writes (app + audit)  
- Confirm failure policy enabled  
- Confirm no unexpected readiness flaps  
- Confirm settlement path against target network (staging/testnet first)

### Rollback strategy

See §9 Rollback Criteria for *when*. Execution pattern:

1. Mark release **bad** in ops channel; page Release Owner.  
2. Stop new traffic (LB / DNS / feature flag) if needed.  
3. Begin graceful drain on bad instances (`DRAINING` → finish in-flight).  
4. Redeploy **previous known-good git tag** artifacts.  
5. Smoke test (§4).  
6. Post-incident: root cause, hotfix RC, or permanent revert notes.

Never “fix forward” Critical payment / settlement / security failures without an explicit Release Owner decision.

## 5. Semantic Versioning

Adopt **SemVer 2.0.0**:

| Component | Meaning for WheelWin |
|-----------|----------------------|
| **MAJOR** | Incompatible architecture or protocol / authority contract breaks (rare; requires unfreeze decision) |
| **MINOR** | Backward-compatible functionality (ops, UX, non-authority features) |
| **PATCH** | Backward-compatible bug fixes, hotfixes, dependency patches |

### Pre-release & GA examples

```text
1.0.0-rc1     First Release Candidate
1.0.0-rc2     RC with fixes from Closed Beta
1.0.0         Production / GA
1.0.1         Hotfix / patch
1.1.0         Minor feature train post-GA
2.0.0         Major (only with explicit architecture unfreeze)
```

### Tagging rules

- Every production deploy corresponds to an annotated git tag.  
- RC tags use GitHub **pre-release**.  
- GA tags use GitHub **latest** release (or explicit non-latest if supporting LTS later).  
- Changelog entry required for every tagged release.

Required for each RC and GA:

|----------|-------------|

## 7. Blockchain Readiness

```text
Testnet  →  Mainnet
```

| Gate | Network | Allowed phases |
|------|---------|----------------|
| Default for RC / Closed Beta | **Testnet** | Internal Validation, RC, Closed Beta |
| Open Beta | Testnet **or** Mainnet (explicit product decision) | Documented in release notes |
| Production GA | **Mainnet** (unless product declares testnet-only soft launch) | Production Release |

### Requirements before advancing network

- [ ] Wallet verification (deposit / identity rules)  
- [ ] Settlement verification (confirm + reject + expiry)  
- [ ] Contract verification (address, ABI/mode, deploy mode `live` vs `stub`)  
- [ ] Network verification (endpoint, chain id/network name, rate limits)  
- [ ] Rollback policy for chain misconfig (revert config + redeploy previous tag; freeze settlements if corruption suspected)

### Blockchain rollback policy

| Symptom | Action |
|---------|--------|
| Wrong network / contract | Immediate config rollback; halt new games; incident |
| Settlement corruption suspected | Halt settlements; preserve logs/audit; do not “repair” balances ad hoc |
| Transient RPC outage | Rely on failure policy retries/circuits; gameplay continues; do not rollback app solely for RPC blips |

## 8. Beta Strategy

### Closed Beta

| Topic | Policy |
|-------|--------|
| **Selection criteria** | Invite-only; mix of trusted testers + internal; wallet-capable users if payments on |
| **Scale** | Soft cap on concurrent rooms/games; staging or dedicated beta cluster |
| **Bug reporting** | Single intake (issue tracker template: repro, room id, trace id, severity) |
| **Crash reporting** | Client crash + server fatal logs correlated by `traceId` |
| **Feedback workflow** | Triage daily → Critical/High block exit; Medium/Low backlog |
| **Exit criteria** | ≥ agreed soak duration; zero Critical; settlement success rate within SLO; RC checklist still green; Release Owner approval for Open Beta |

### Open Beta

| Topic | Policy |
|-------|--------|
| **Availability** | Public signup or open client; rate limits as needed |
| **Monitoring** | Full R7 stack; on-call for probes + settlement failure rate |
| **Incident response** | Severity matrix (§10); drain + rollback if Critical |
| **Exit criteria** | Launch go/no-go (§8 Production Launch); SLOs held; docs/legal complete |

## 9. Production Launch Procedure

### Pre-launch

1. Final RC (or GA candidate) tagged; artifacts published.  
2. Mainnet readiness signed (§6) if GA on mainnet.  
3. Checklist §3 complete.  
4. On-call roster + escalation tree confirmed.  
5. Rollback package (previous tag) staged and tested on staging.  
6. Communications ready (changelog, status page if any).

### Launch

1. Promote configuration to production.  
2. Deploy GA artifacts.  
3. Run smoke tests (§4).  
4. Enable traffic.  
5. Announce release.

### Immediate verification (T+0 to T+1h)

- Probes green  
- Logging/monitoring fresh  
- Sample gameplay path  
- Sample settlement path  
- Error/settlement rates within baseline  

### 24-hour monitoring

- Uptime, crash-free sessions, settlement success, latency, support volume  
- Daily triage of High+  

### 72-hour monitoring

- Trend vs SLO (§9 Success Metrics)  
- Decide first patch window content  
- Post-launch review scheduled  

### First patch window

- Time-boxed (e.g. T+7d) for High/Medium fixes as `vX.Y.Z+1`  
- Critical issues may force out-of-window hotfix  

### Post-launch review

- What went well / poorly  
- Rollback drills learning  
- Update this architecture if process gaps found (doc-only unless later R8 stage implements tooling)

## 10. Success Metrics

Measurable goals for Open Beta and Production (targets to be finalized by Release Owner; defaults below):

| Metric | Default target (first release) | Source |
|--------|--------------------------------|--------|
| Server uptime | ≥ 99.5% monthly (exclude planned drain) | Probes / host |
| Crash-free sessions | ≥ 99% | Client + server fatals |
| Settlement success rate | ≥ 99% of valid payments | Payment / blockchain metrics |
| Average gameplay latency | Within established sim tick budget | Monitoring simulation gauges |
| Average HTTP probe latency | < 50 ms p95 on `/ready` `/live` | Monitoring / load tests |
| Support requests | Tracked; Critical tickets = 0 open | Support intake |
| Critical bugs in production | **0 open** | Issue tracker |
| R7.0H suite on release tag | **PASS** | CI / `validate:production` |

Tune targets upward after first stable month.

## 11. Rollback Criteria

**Must roll back** (or halt traffic and restore last good) when any of the following is confirmed in production/open beta:

| Trigger | Notes |
|---------|-------|
| Critical payment failure | Systematic inability to take or settle valid payments |
| Settlement corruption | Ledger / payout inconsistency or double-settlement risk |
| Gameplay desynchronization | Authority divergence affecting fairness |
| Security incident | Secret leak, auth bypass, dependency exploit in prod |
| Infrastructure failure | Persistent unreadiness / crash loops after remediation window |

**May roll back** (Release Owner judgment):

- Sustained SLO breach (uptime, settlement, latency) without near-term fix  
- Data-loss risk that is High but not yet proven Critical  

**Do not roll back solely for:**

- Cosmetic UX bugs  
- Single-user wallet misconfiguration  
- Transient external RPC throttling handled by failure policy

## 12. Known Release Blockers (Severity Model)

| Severity | Definition | Blocks RC / GA? |
|----------|------------|-----------------|
| **Critical** | Data loss, payment/settlement integrity, security breach, authority desync, unrecoverable outage | **Yes** |
| **High** | Major feature broken for many users; workaround poor; SLO at risk | Blocks GA by default; may allow Closed Beta with waiver |
| **Medium** | Limited impact; workaround exists | No — track for patch |
| **Low** | Cosmetic / polish | No |

Only **Critical** blockers **hard-stop** release. High items require explicit Release Owner waiver to ship.
