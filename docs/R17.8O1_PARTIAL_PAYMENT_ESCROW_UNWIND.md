# R17.8O.1 — Partial Payment Escrow Unwind

## 1. Previous unsafe lifecycle

When some players reached `PAYMENT_CONFIRMED` but the session could not complete (timeout, creator leave, deploy failure after partial pay), the server emitted `PAYMENT_SESSION_FAILED` and destroyed the room immediately. `GameContractManager.destroyContract()` only removed in-memory registry entries. No production caller invoked `TonGameContractAdapter.cancel()`, so confirmed stakes could remain locked in GameEscrow.

```
PARTIALLY_PAID → room failure → ROOM_DESTROYED → (no EMERGENCY_CANCEL) → funds locked
```

## 2. New lifecycle

Payment failure with confirmed-but-incomplete funds now unwinds escrow before room teardown:

```
detect payment failure
  ↓
PaymentSessionManager.failSession → REFUND_PENDING
  ↓
GameContractManager.requestPartialPaymentEscrowUnwind
  ↓
ESCROW_CANCEL_REQUESTED → adapter.cancel() → ESCROW_CANCEL_CONFIRMED
  ↓
BlockchainMonitor.watchGameEscrowRefunds → ESCROW_REFUND_PENDING
  ↓
GAME_ESCROW_REFUND_CONFIRMED (per player) → ESCROW_REFUND_CONFIRMED
  ↓
all confirmed players refunded → PAYMENT_SESSION_FAILED
  ↓
RoomLobbyBridge._closeRoom → ROOM_DESTROYED
```

Full payment (`3/3` confirmed) is unchanged — no cancel path.

## 3. Trigger conditions

Escrow unwind runs when **all** of the following hold:

- `PaymentSessionManager.failSession()` is invoked (timeout, creator leave, deploy failure, etc.).
- Session is not already terminal or `REFUND_PENDING`.
- `sessionNeedsEscrowUnwind(session)` — at least one confirmed payer and not fully paid.
- Deployed contract has `contractAddress`.
- `GameContractManager.requestPartialPaymentEscrowUnwind` is available.

`RoomLobbyBridge` routes creator leave during partial payment through `failSession("creator_left")` instead of immediate `_closeRoom`.

## 4. Cancel flow

Owned by `GameContractManager`:

1. Emit `ESCROW_CANCEL_REQUESTED` (`gameId`, `roomId`, `contractAddress`, `reason`, `confirmedPlayersCount`).
2. Call `TonGameContractAdapter.cancel({ contractAddress })`.
3. On success: emit `ESCROW_CANCEL_CONFIRMED` (`transactionHash`, `contractAddress`); store `cancelTxHash` on payment session recovery metadata.
4. On failure: emit `ESCROW_CANCEL_FAILED`; set unwind state to `failed`; **do not** destroy contract or emit `PAYMENT_SESSION_FAILED`.

## 5. Refund confirmation flow

1. After successful cancel, `BlockchainMonitor.watchGameEscrowRefunds()` starts observation (reuses R7.69C infra).
2. Emit `ESCROW_REFUND_PENDING`.
3. Each on-chain refund → existing `GAME_ESCROW_REFUND_CONFIRMED` → `PaymentSessionManager._handleGameEscrowRefundConfirmed` marks seat refunded and emits `ESCROW_REFUND_CONFIRMED`.
4. When all confirmed payers are refunded, `_finalizePartialPaymentUnwind` marks session `CANCELLED` and emits `PAYMENT_SESSION_FAILED` so room cleanup proceeds.

## 7. Remaining limitations

- **Stub deploy mode** — `GameContractDeployAdapter` has no `cancel()`; unwind emits `ESCROW_CANCEL_FAILED` and preserves contract reference for investigation.
- **Cancel failure** — Room is not destroyed automatically; manual recovery may be required using preserved contract/session metadata.
- **Creator leave during unwind** — Room stays open until refunds complete; creator disconnect does not force immediate lobby teardown.
- **No manual refund UI** — Operational recovery remains server-side / admin tooling only (per scope).
- **Smart contract unchanged** — Behavior relies on existing GameEscrow `EMERGENCY_CANCEL` and refund semantics.
