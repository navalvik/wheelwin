## R17.8V.2H — SETTLE Economic Audit

**Audit date:** 2026-08-15  
**Mode:** READ-ONLY (no chain txs; no production code changes)  
**Sources:** `contracts/game_escrow/GameEscrow.tact`, `TonGameContractAdapter.js`, `buildSettleMessagePlan.js`, `buildGameContractSnapshot.js`

### 1. SETTLE source path

Opcode: `0x53544c` (`"STL"`) — `message(0x53544c) Settle`  
Handler: `receive(msg: Settle)` in `GameEscrow.tact` (approx. lines 213–243)

```text
SETTLE received (+ oracle attach valueTon)
        ↓
require sender == oracle
require not settled
require msg.snapshotHash == self.snapshotHash
require status == STATUS_READY   // paidMask == 7 only
        ↓
required = winnerAmount + ownerAmount + SETTLE_GAS_RESERVE
require myBalance() >= required
        ↓
status = SETTLING
send(winner, winnerAmount, SendPayGasSeparately, bounce=false)
send(owner, ownerAmount, SendPayGasSeparately, bounce=false)
        ↓
store winner / amounts; status = SETTLED; settled = true
```

**No `context().value` check on SETTLE.**

### 2. Constants

| Constant | Value | Unit | Purpose | Source |
|----------|------:|------|---------|--------|
| `SETTLE_GAS_RESERVE` | **0.05** | TON | Cushion for **two** payout sends | `GameEscrow.tact` L18–19, used L220–221 |
| `CANCEL_GAS_RESERVE` | 0.08 | TON | CANCEL path only (comparison) | L21–22 |
| Payout `send` values | `msg.winnerAmount`, `msg.ownerAmount` | coins | Exact amounts from oracle message | L225–236 |
| Send mode | `SendPayGasSeparately` | — | Gas for forwards paid separately from send value | L228, L234 |

No additional settlement storage/action reserve constants beyond `SETTLE_GAS_RESERVE`.

### 3. Exact SETTLE formula

```text
myBalance() >= msg.winnerAmount + msg.ownerAmount + SETTLE_GAS_RESERVE
SETTLE_GAS_RESERVE = 0.05 TON
```

Oracle attach enters `myBalance()` with the incoming message (same pattern as CANCEL). There is **no** `context().value == …` or `>=` attach gate.

### 4. Winner payout (off-chain → on-chain)

On-chain GameEscrow **does not compute** the pot split. It pays whatever the oracle puts in `Settle`.

Server snapshot economics (`buildGameContractSnapshot.js`):

```text
totalPot       = Σ player.requiredGram
organizerFee   = totalPot × feeRate   // typically 5%
payoutAmount   = totalPot − organizerFee
```

These become `winnerAmount` / `organizerAmount` on the settle request.

Answers:

| Question | Answer |
|----------|--------|
| Full stake pool to winner? | No — winner gets `totalPot − organizerFee` |
| Retained amount? | Organizer fee paid to `owner` |
| Oracle fee? | Organizer fee (snapshot), not a separate oracle fee on-chain |
| All stakes included? | Yes, via `totalPot` / registered stakes |
| 1- vs 2-sector? | Affects `requiredGram` per seat off-chain; contract only sees stake coins + settle amounts |
| Depends on `paidMask`? | Indirectly: SETTLE requires `STATUS_READY` ⇒ **all three** seats paid (`paidMask == 7`) |
| Fewer than 3 paid? | **SETTLE impossible** (`not ready`) |

### 5. TON sources

| Source | Role |
|--------|------|
| Player STAKE attaches | Fund pot (`totalPaid`) |
| Lifecycle oracle attaches (DEPLOY/INIT/OPEN) | Residual gas cushion on escrow |
| SETTLE oracle attach (`resolveOracleValueTon("SETTLE")`) | Adds to `myBalance()`; production **0.05**; measurement harness may use uniform `V` |
| Existing escrow balance | Primary funding for payouts + reserve check |

Attached SETTLE value is **not** an exact-match requirement; it is balance top-up / gas. Payouts come from **contract balance**, not “only” the SETTLE message.

Adapter: `_broadcastSettle` → `_sendOracleMessage({ operation: "SETTLE", valueTon: resolveOracleValueTon("SETTLE"), bounce: false })`.

### 6. CANCEL vs SETTLE

| Property | CANCEL | SETTLE |
|----------|--------|--------|
| Required contract balance | `pendingRefund + 0.08` | `winnerAmount + ownerAmount + 0.05` |
| Reserve | `CANCEL_GAS_RESERVE = 0.08` | `SETTLE_GAS_RESERVE = 0.05` |
| Payout | Exact stakes to paid seats | Oracle-specified winner + owner |
| Attached value requirement | None (`myBalance` only) | None (`myBalance` only) |
| Uses escrow balance | Yes | Yes |
| Preconditions | PAYMENTS_OPEN or READY | **READY only** (3/3 paid) |
| Main economic risk | Reserve **0.08** vs thin lifecycle residual | Reserve **0.05**; pot must remain for payouts |

Why CANCEL hit `0.022 PASS / 0.021 FAIL`: uniform-`V` gate ≈ `4·V − G ≥ 0.08`.  
SETTLE under `winnerAmount + ownerAmount ≈ totalPaid` simplifies to ≈ `4·V − G ≥ 0.05` — **looser** than CANCEL. SETTLE does **not** set a higher independent lower bound than CANCEL for uniform lifecycle `V`.

### 7. Scenario C @ 0.022 before SETTLE (theoretical)

Assume equal stakes `S = 0.05`, `N = 3`, `totalPaid = 0.15`, fee 5%:

```text
winnerAmount = 0.1425
ownerAmount  = 0.0075
need myBalance >= 0.1425 + 0.0075 + 0.05 = 0.20
```

Uniform `V = 0.022`, `G ≈ 0.004` (from CANCEL-era inference):

```text
myBalance ≈ 3·V + totalPaid − G + V_settle
         ≈ 4·0.022 + 0.15 − 0.004
         ≈ 0.234

0.234 − 0.20 = +0.034 TON headroom
```

Remaining after successful sends (ignoring send gas beyond reserve design): design intent leaves ~`SETTLE_GAS_RESERVE` consumed as cushion, not returned as a fixed leftover formula on-chain.

### 8. Worst-case SETTLE

| Factor | Bound |
|--------|-------|
| Paid seats | Must be 3 (READY) |
| Payout sum | `winnerAmount + ownerAmount` should equal pot accounting (`≈ totalPaid`) |
| Reserve | **+0.05** hard-coded |
| Min balance at SETTLE | **`totalPaid + 0.05`** (when payouts exhaust the pot) |
| Uniform-`V` implication | `4·V − G ≥ 0.05` ⇒ `V ≳ (0.05+G)/4 ≈ 0.0135` for `G≈0.004` |

Worst case vs CANCEL: CANCEL’s **0.08** reserve dominates; SETTLE’s **0.05** does not raise the uniform-`V` floor above 0.022.

### 9. 0.022 vs 0.05

| Lifecycle `V` | CANCEL gate `4V−G ≥ 0.08` | SETTLE gate `4V−G ≥ 0.05` |
|--------------:|---------------------------:|---------------------------:|
| 0.05 | large margin | large margin |
| 0.022 | live PASS (thin) | math PASS (~+0.034 vs need) |
| 0.021 | live FAIL | math still likely PASS for SETTLE alone |

Reducing production from 0.05 → 0.022 does **not** introduce a hidden SETTLE-only shortfall **relative to CANCEL**; CANCEL remains the binding constraint. SETTLE still needs a **live** confirmation (never executed in V.2A–V.2G).

### 10. Audit conclusion

```text
A. SETTLE is mathematically safe at 0.022 TON.
   A single live 0.022 SETTLE test is recommended.
```

**Recommended live test (not executed in V.2H):**

```text
ValueTon = 0.022 (uniform DEPLOY/INIT/OPEN/SETTLE)
Scenario: full 3× STAKE → READY → SETTLE
Verify: status SETTLED; winner + owner receive expected amounts;
        myBalance gate satisfied; no bounce / insufficient balance
```

Do **not** change production `0.05` until that live SETTLE evidence exists.

## R17.8V.2E — CANCEL Value Formula Audit

**Audit date:** 2026-08-15  
**Mode:** READ-ONLY (no chain txs; no production code changes)  
**Sources:** `contracts/game_escrow/GameEscrow.tact`, `server/payment/TonGameContractAdapter.js`, `server/payment/ton/testValueTonOverride.js`, harness `runValueTonSweep.js`

### 1. CANCEL source path

Handler: `receive(msg: EmergencyCancel)` in `GameEscrow.tact` (opcode `0x43414e43` / `"CANC"`).

Flow:

```text
oracle EmergencyCancel (+ attach valueTon)
        ↓
require sender == oracle
require not settled
require status ∈ {PAYMENTS_OPEN, READY}
        ↓
pendingRefund = Σ stake_i for bits in paidMask \ refundMask
        ↓
require myBalance() >= pendingRefund + CANCEL_GAS_RESERVE
        ↓
send stake_i to each unpaid-refund seat (SendPayGasSeparately, bounce=false)
        ↓
refundMask |= bits; refundedAmount += …; status = CANCELLED
```

**There is no `context().value` check on CANCEL.** Only `myBalance()`.

### 2. Constants (CANCEL / refund economics)

| Name | File | Location | Value | Unit | Purpose |
|------|------|----------|------:|------|---------|
| `CANCEL_GAS_RESERVE` | `GameEscrow.tact` | lines 21–22, used 266–268 | **0.08** | TON (`ton("0.08")`) | Cushion so up to 3 refund `send`s can pay forward fees |
| `SETTLE_GAS_RESERVE` | `GameEscrow.tact` | lines 18–19, used 220–221 | **0.05** | TON | SETTLE path only (not CANCEL) |
| Refund send `value` | `GameEscrow.tact` | 276–304 | exact `stake0/1/2` | coins | Exact stake refunded; mode `SendPayGasSeparately` |
| STAKE exactness | `GameEscrow.tact` | 201 | `context().value == required` | coins | Player deposit must match registered stake exactly |
| Production oracle attach | `testValueTonOverride.js` | `PRODUCTION_ORACLE_VALUE_TON` | **0.05** | TON | Default when override off |

No separate “refund gas reserve” constant beyond `CANCEL_GAS_RESERVE`. No storage / action-phase reserve constants in this contract beyond those two.

### 3. Exact CANCEL formula

Contract gate (source):

```text
myBalance() >= pendingRefund + CANCEL_GAS_RESERVE
pendingRefund = Σ stake_i  for i where (paidMask & bit_i) != 0 and (refundMask & bit_i) == 0
CANCEL_GAS_RESERVE = 0.08 TON
```

Under the **current measurement architecture** (uniform oracle `valueTon = V` for DEPLOY + INIT_GAME + OPEN_PAYMENTS + CANCEL; player stakes `S` each):

```text
balance_pre_cancel ≈ 3·V′ + N·S − G
myBalance_at_require ≈ balance_pre_cancel + C′
                     ≈ 3·V′ + N·S − G + C′
```

where:

- `V′` / `C′` = effective TON credited to the escrow from each oracle message (≤ configured `V` / cancel attach; oracle wallet uses default `SendMode.NONE`, so forward fees may reduce credited value);
- `N` = number of paid seats;
- `G` = compute/storage TON burned from the escrow before CANCEL.

Gate simplifies (stakes cancel) to:

```text
3·V′ + C′ − G  >=  0.08
```

With uniform `C′ ≈ V′`:

```text
4·V′ − G  >=  0.08
V′        >=  (0.08 + G) / 4
```

**Important:** minimum CANCEL attach alone is **not** `0.08 + pendingRefund` unless prior residual is zero. The contract cares about **total contract balance**, not CANCEL attach in isolation.

### 4. Attached value vs fees

| Path | Condition | Fee behavior |
|------|-----------|--------------|
| **STAKE** | `context().value == required` (exact) | Player harness uses `SendMode.PAY_GAS_SEPARATELY \| IGNORE_ERRORS` (mode 3) so exact stake arrives |
| **CANCEL** | `myBalance() >= …` (inequality) | No exact attach check; oracle adapter `createTransfer` does **not** set `sendMode` → library default **NONE (0)** → fees can come out of attach |
| **SETTLE** | `myBalance() >= winner+owner+0.05` | Same oracle send path |

### 5. Live comparison (explains 0.020 vs 0.025)

From V.2D.2 Scenario B @ 0.02 after failed CANCEL (stake still held):

```text
remainingBalanceTon ≈ 0.105737315
≈ 3·0.02 + 0.05 − G  ⇒  G ≈ 0.0043 TON
```

At CANCEL require (if attach had been accepted into balance):

```text
myBalance ≈ 0.1057 + 0.02 = 0.1257
needed    = 0.05 + 0.08 = 0.13
0.1257 < 0.13  → require fails  → refundMask stays 0
```

At 0.025 with similar `G`:

```text
myBalance ≈ 3·0.025 + 0.05 − G + 0.025 ≈ 0.15 − G ≥ 0.13  → PASS
```

**Source formula explains the observed boundary.** Missing cost component is prior escrow gas burn `G` plus any `SendMode.NONE` attach shortfall on oracle messages—not an undocumented second reserve.

### 6. STAKE vs CANCEL economics

| | STAKE | CANCEL |
|---|-------|--------|
| Required value | Exact registered `stake_i` (live tests: **0.05**) | None on `context().value` |
| Gate | Equality | `myBalance` vs refunds + **0.08** |
| Why 0.02 oracle ValueTon still allows STAKE | STAKE attach is the **player stake 0.05**, independent of oracle `V` | CANCEL success depends on **accumulated** oracle attaches + stakes vs **0.08** cushion |

### 7. Theoretical minimums (uniform V, S=0.05)

Using live-inferred `G ≈ 0.0043` and `V′ ≈ V`:

| Scenario | pendingRefund | Need myBalance ≥ | Approx. uniform V floor `(0.08+G)/4` | Known live |
|----------|-------------:|-----------------:|------------------------------------:|------------|
| A — 0 paid | 0 | 0.08 | ~**0.021** | 0.05 PASS; 0.02 A PASS (V.2D.1) |
| B — 1 paid | 0.05 | 0.13 | ~**0.021** | **0.025 PASS / 0.020 FAIL** |
| C — 3 paid | 0.15 | 0.23 | ~**0.021** | 0.025 PASS |

```text
theoretical minimum (uniform V, this G):  ~0.021 TON
confirmed live minimum (A+B+C):           0.025 TON
remaining uncertainty:                    exact G and V′−V shortfall vary by network load;
                                          0.021–0.024 not live-tested
```

### 8. Server adapter

`TonGameContractAdapter.cancel()` → `_sendOracleMessage({ operation: "CANCEL", valueTon: resolveOracleValueTon("CANCEL") })`.

Production: always **0.05** unless `TEST_VALUETON_OVERRIDE=true`.

### 9. Audit conclusion

```text

   a lower boundary exists and should be tested.
```

Useful **unexecuted** candidates (uniform V, Scenario B focus):

```text

```

(`0.021` is too close to the inferred floor; treat as optional stretch only.)

Do **not** change production `0.05`.
