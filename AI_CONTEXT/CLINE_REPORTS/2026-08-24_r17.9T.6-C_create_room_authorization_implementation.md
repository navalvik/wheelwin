# R17.9T.6-C — Telegram-Only CREATE_ROOM Authorization Implementation

Date: 2026-08-24

Task: Restrict CREATE_ROOM to authenticated Telegram Mini App identities; enforce one active created room per Telegram user; eliminate unauthenticated room-creation flooding.

## 3. Architecture Findings

1. The EventBus envelope for `LOBBY_CREATE_ROOM_REQUEST` carries only `socketId`; the bridge has no direct access to Socket.IO or `socket.data`.
2. All room teardown paths funnel through `_closeRoom(roomId, reason)` plus the setup-expiry "room already gone" branch and the empty-room destroy branch in `_removePlayerFromLobby`; `_roomCreators.delete(roomId)` marks each site.
3. Two create-failure paths (`create_player_failed`, `add_player_failed`) destroy the freshly allocated room directly.
4. Existing admission order in `_handleCreateRoom`: duplicate socket → drain → global capacity → RoomManager.createRoom → PlayerManager.

## 4. Lifecycle Flow

CREATE_ROOM now resolves:

duplicate-socket check → **Telegram identity check** → **one-active-room-per-user check** → drain → global capacity → RoomManager allocation → PlayerManager allocation/binding → quota occupied (`telegramUserId → roomId`).

Quota release occurs at every site where `_roomCreators.delete(roomId)` runs, plus both create-failure destroy paths, plus `shutdown()`.

## 5. Ownership Boundaries

- Trusted identity source: a server-side resolver function wired into the bridge (`configureTelegramIdentityResolver` / constructor option `telegramIdentityResolver`). Production resolver must read ONLY `io.sockets.sockets.get(socketId)?.data?.telegramUserId ?? null` — the value set by SocketGateway's initData validation middleware.
- Client payloads are never consulted. `telegramUserId → playerId → socketId` layers remain separate; `_roomCreators` (playerId-based creator ownership) is preserved unchanged.
- Quota map `_activeRoomsByTelegramUser` is runtime-only, owned by RoomLobbyBridge.

## 6. Risks

### Critical
None remaining after implementation (unauthenticated flooding eliminated).

### High
**Production wiring gap**: `app.js` must call
`this._roomLobbyBridge.configureTelegramIdentityResolver((socketId) => this._socketGateway.getIO()?.sockets?.sockets?.get(socketId)?.data?.telegramUserId ?? null)`
after bridge construction. This file is outside the approved two-file scope, so it was NOT modified. Until wired, the bridge fails closed: ALL CREATE_ROOM requests (including Telegram) receive `ROOM_CREATION_REQUIRES_TELEGRAM`. Security is preserved; Telegram room creation is disabled until the one-line wiring lands.

### Medium
Restart gap: the quota map is runtime-only. After a server restart, previously created rooms do not survive anyway (rooms are ephemeral), so no stale quota can block users; but a restart also resets quota occupancy for any rooms restored by future recovery work. See section 13.

### Low
Resolver exceptions are swallowed and treated as "no identity" (fail-closed).

## 7. Recommendations

1. Next stage: add the one-line `configureTelegramIdentityResolver(...)` wiring in `app.js` (smallest required architecture decision; no other file changes needed).
2. When recovery gains cross-restart room restoration, extend the Recovery Data Contract with the creator's telegramUserId so the quota can be rebuilt without touching PlayerManager.
3. Consider rate limiting as a separate later stage (explicitly out of scope here).

## Restart Limitation

The current architecture cannot rebuild the Telegram user quota after restart without changing PlayerManager or persistence (creator telegramUserId is not part of the persisted/recoverable state). Per instructions, no workaround was invented. Practical impact today is nil because rooms themselves are ephemeral and do not survive restarts; flagged for the future recovery milestone.
