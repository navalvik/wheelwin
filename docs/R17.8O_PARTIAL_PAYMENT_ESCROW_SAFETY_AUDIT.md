## 1. Executive summary

**Question:** If two players reach `PAYMENT_CONFIRMED` and a third fails or times out, can already-paid funds become locked after `ROOM_DESTROYED`?

**Answer:** **Yes — funds can remain locked in the deployed GameEscrow contract.** WheelWin has **refund observation** infrastructure (R7.69C) but **no automatic on-chain cancel/refund** when a payment session fails or a room is destroyed mid-payment. `TonGameContractAdapter.cancel()` (EMERGENCY_CANCEL) exists but is **never invoked** from production lifecycle handlers.

| Risk | Severity |
|------|----------|
| Paid stakes remain in escrow after room teardown | **High** |
| No mandatory refund before `ROOM_DESTROYED` | **Confirmed gap** |
| Backend clears in-memory contract/session without chain unwind | **Confirmed behavior** |
| Manual oracle cancel required to release funds | **Current state** |

**Verdict:** Partial-payment failure is **not escrow-safe** today without operator/oracle intervention.

## 4. Current payment lifecycle

### 4.1 Happy path (abbreviated)

```text
PAYMENT_CONNECTION_READY
        ↓
PaymentSessionManager.createAndRequest()
        ↓
PAYMENT_SESSION_CREATED / WAITING_FOR_PAYMENTS
        ↓
GameContractManager deploy → initGame → openPayments
        ↓
GAME_CONTRACT_READY_FOR_PAYMENTS
        ↓
PAYMENT_REQUEST (per seat)
        ↓
Player STAKE on-chain → GAME_ESCROW_STAKE_CONFIRMED
        ↓
Participant PAYMENT_CONFIRMED
        ↓
(more seats) → PARTIALLY_PAID after first confirmed seat (_maybeCompleteSession)
        ↓
all confirmed → FULLY_PAID → PAYMENT_SESSION_COMPLETED
        ↓
Game start authorization → GAME_INITIALIZED
```

### 4.2 Partial payment (`PARTIALLY_PAID`)

Triggered in `PaymentSessionManager._maybeCompleteSession()` when `confirmedCount() > 0` but not `allConfirmed()`:


## 5. Required lifecycle diagram — what actually happens

### 5.1 Path A — Payment session timeout / explicit failure (via `failSession`)

```text
PAYMENT_READY
        ↓
PAYMENT_SESSION_CREATED (WAITING_FOR_PAYMENTS)
        ↓
Deploy + openPayments + PAYMENT_REQUEST
        ↓
2× STAKE confirmed → PARTIALLY_PAID
        ↓
Payment deadline expires (_onExpiry)
        ↓
PaymentSessionManager.failSession(roomId, "payment_timeout")
        ↓
session.markTimedOut() → PAYMENT_TIMEOUT
        ↓
PAYMENT_SESSION_FAILED emitted
        ↓
GameContractManager.destroyContract()     ← in-memory only, NO chain cancel
        ↓
RoomLobbyBridge._handlePaymentSessionFailed → _closeRoom("payment_timeout")
        ↓
RoomManager.destroyRoom() → ROOM_DESTROYED
        ↓
PaymentSessionManager.destroySession()      ← if !shouldPreserveFinancialEvidence
        ↓
Archive: finalStage=PAYMENT, payment may show PARTIALLY_PAID or PAYMENT_TIMEOUT
```

**No step sends EMERGENCY_CANCEL. No refund watch is registered automatically.**

### 5.2 Path B — Room closed without `failSession` (e.g. `creator_left`)

```text
PARTIALLY_PAID (2 confirmed, 1 awaiting)
        ↓
Creator leaves pre-game → RoomLobbyBridge._closeRoom("creator_left")
        ↓
NO failSession / NO PAYMENT_SESSION_FAILED
        ↓
ROOM_DESTROYED
        ↓
destroyContract + destroySession (typical pre-GAME_INITIALIZED)
        ↓
Archive retains payment.status = PARTIALLY_PAID   ← matches incident pattern
```

## 6. GameEscrow on-chain lifecycle (backend view)

| Step | Backend | On-chain effect |
|------|---------|-----------------|
| **deploy** | `GameContractManager._beginDeploy` → `TonGameContractAdapter.deployContract` | Escrow contract created |
| **initGame** | After deploy success (game mode) | Game initialized |
| **openPayments** | `openPayments({ contractAddress, players })` | Payment window opened |
| **collectStake** | Player wallets → escrow STAKE tx | Funds move **into** escrow; `paidMask` updates |
| **cancelGame** | `TonGameContractAdapter.cancel()` → EMERGENCY_CANCEL | **Exists but uncalled from lifecycle** |
| **refund** | Contract returns stake to paid seats after cancel | Observed by `BlockchainMonitor.watchGameEscrowRefunds` |
| **settlement** | After FULLY_PAID + game completion | Not reached in partial-failure scenario |

## 7. Critical questions

### Q1 — Blockchain state when A+B paid, C failed?

**When stakes were confirmed on-chain (typical GameEscrow path after `openPayments`):**

| Component | State |
|-----------|--------|
| Escrow contract | **Exists**, active, payments were **opened** |
| Contract activity | **Not settled**; game not started |
| Player A/B funds | **Locked in escrow** (paid seats in `paidMask`) |
| Player C | No stake (still `AWAITING_PLAYER_CONFIRMATION`) |
| Refundability | **Refundable only after EMERGENCY_CANCEL** on-chain |
| Automatic backend action on failure | **None** — no cancel tx sent |

**Not** “no contract exists” unless deploy never succeeded (different failure class).

### Q2 — Is there any automatic refund mechanism?

| Mechanism | File | Function | Trigger | Sends cancel? |
|-----------|------|----------|---------|---------------|
| Payment timeout | `PaymentSessionManager.js` | `failSession` / `_onExpiry` | Deadline | **No** |
| Deploy failure | `PaymentSessionManager.js` | subscriber on `GAME_CONTRACT_DEPLOY_FAILED` | Deploy fail | **No** |
| Room close | `RoomLobbyBridge.js` | `_closeRoom` | Many reasons | **No** |
| Contract cleanup | `GameContractManager.js` | `destroyContract` | `PAYMENT_SESSION_FAILED`, `ROOM_DESTROYED` | **No** (registry only) |
| Cancel API | `TonGameContractAdapter.js` | `cancel()` | **No production caller** | Would send EMERGENCY_CANCEL |
| Refund sync | `PaymentSessionManager.js` | `syncFromGameEscrow` | Manual reconnect / recovery | **No** (sync only) |
| Refund watch | `BlockchainMonitor.js` | `watchGameEscrowRefunds` | Recovery / tests | **No** (observe only) |
| Recovery restart | `TonFinancialRecovery.js` | `_registerRefundWatchFromSession` | Server restart | **No** (re-watch only) |

**Conclusion:** Refund handling is **reactive observation** after cancel already happened on-chain. **No automatic refund** on partial payment failure or room destruction.

### Q3 — Who owns responsibility?

| Concern | Owner today |
|---------|-------------|
| Payment session state | **PaymentSessionManager** |
| Room teardown | **RoomLobbyBridge** → **RoomManager** |
| In-memory contract registry | **GameContractManager** |
| On-chain fund custody | **GameEscrow smart contract** |
| EMERGENCY_CANCEL execution | **Oracle / deployer wallet** via `TonGameContractAdapter.cancel()` — **not wired to failure paths** |
| Refund confirmation | **BlockchainMonitor** + **PaymentSessionManager** sync |
| End-to-end “return player money on partial fail” | **None (gap)** |

## 12. Recommended next stage

**R17.8O.1 — Partial payment failure escrow unwind (implementation planning)**

Proposed scope (planning only until approved):

1. **Preflight gate:** Before `ROOM_DESTROYED` when `confirmedCount > 0` and session not `FULLY_PAID`, require either:
   - successful `EMERGENCY_CANCEL` + refund watch, or
   - explicit “no funds on chain” proof.
2. **Wire `TonGameContractAdapter.cancel()`** from a single owner (recommend **GameContractManager** or dedicated **PaymentAbortService**) on `PAYMENT_SESSION_FAILED` / controlled room close during payment.
3. **Register `watchGameEscrowRefunds`** immediately after cancel broadcast.
4. **Block or delay `_closeRoom`** until cancel submitted or timeout with operator alert.
5. **Persist** cancel tx + refund mask in `TonFinancialPersistence` for recovery.
6. **Tests:** partial pay → timeout → cancel tx → refund confirmed → then `ROOM_DESTROYED`.

Alternative smaller stage: **R17.8O.0 — Operator runbook** for manual oracle cancel on `PARTIALLY_PAID` archives (mitigation, not fix).
